## Why

После принятой `completion_retracted` карточка уже показывает уменьшенный текущий прогресс, но SQL-фильтры очереди и этапы дашборда продолжают считать любой исторический `item_completed`. Один объект поэтому одновременно выглядит находящимся на разных этапах.

Срез: сотрудник с `objects.read`; oracle — действующая проекция текущего checklist state на актуальном `main`; публичные seams — чтение очереди/карточки и операционного дашборда. Ценность релиза — единое определение этапа без изменения append-only истории.

## What Changes

- SQL-фильтры этапов используют последнее принятое состояние каждого пункта в порядке `accepted_revision`, затем `id`.
- Карточка, строка очереди, total/pagination, stage drill-down и диаграмма этапов согласуются после выполнение → отмена → повторное выполнение.
- Сохраняются веса, порог 85%, правила ПТО/декларации, приоритет `Требуется изменение` и отсутствие автоматического переоткрытия документально завершённых дел.
- Не меняются writers checklist, offline sync, история, ОТиЗ, документы, редактор, фото, readiness, сроки или справки.

## Capabilities

### New Capabilities

- `installation/current-checklist-stage`: согласованный этап объекта по текущему принятому состоянию пунктов checklist во всех read-проекциях.

### Modified Capabilities

Нет.

## Impact

Минимальное изменение read-side SQL в `MariaDbYiiObjectQueue` и `MariaDbYiiOperationalDashboard` либо общей существующей read-семантике, используемой ими. Миграций, новых таблиц, materialized status и API-изменений нет.
