## ADDED Requirements

### Requirement: календарь использует действующие реквизиты объекта

Система SHALL разрешать адрес, подъезд и регистрационный номер каждого события календаря через существующий effective-values контракт.

#### Scenario: поправка видна во всех типах событий

- **WHEN** пользователь с `objects.read` открывает календарь после действующей поправки реквизитов
- **THEN** события `inspection`, `planned_start` и `planned_end` показывают исправленные значения
- **AND** карточка и реестр продолжают показывать те же значения

#### Scenario: ключ поправки отсутствует

- **WHEN** отдельный ключ отсутствует в текущей поправке
- **THEN** календарь показывает legacy-значение этого поля

#### Scenario: значение явно пустое

- **WHEN** текущая поправка содержит JSON `null` или пустую строку для отдельного поля
- **THEN** календарь показывает пустое значение и SHALL NOT подставлять legacy-значение

#### Scenario: поправка заменена новой ревизией

- **WHEN** текущая поправка заменена более поздней ревизией
- **THEN** следующий GET/reload календаря показывает новые значения без переимпорта
- **AND** даты, идентичность, количество и порядок событий не меняются

### Requirement: чтение остаётся ограниченным и без побочных эффектов

Система SHALL сохранить действующие лимиты, overflow/error semantics, авторизацию и read-only поведение календаря и SHALL NOT выполнять отдельное чтение поправки для каждого объекта.

#### Scenario: повторное чтение

- **WHEN** пользователь повторяет GET или HEAD календаря
- **THEN** DB/history/job/outbox записи не создаются

#### Scenario: граница источника превышена

- **WHEN** один из существующих bounded источников или их объединение превышает лимит
- **THEN** календарь сохраняет действующий безопасный отказ без частичного результата
