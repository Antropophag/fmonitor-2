## Purpose

Устанавливает единый наблюдаемый визуальный и интерактивный договор для всех активных Yii2-экранов FMonitor без изменения предметных правил, прав доступа, истории и протоколов записи.

## ADDED Requirements

### Requirement: Исполнимый authenticated baseline
До визуальной миграции система SHALL позволять изолированным canonical Yii fixtures успешно аутентифицироваться и достигать существующих installers, users, preopening и ОТиЗ HTTP routes без необъяснённого 503 или падения до UI assertions. Исправление MUST сохранять production authorization и MUST NOT подменять отсутствующую зависимость фиктивным GREEN.

#### Scenario: Existing browser journey достигает предметного экрана
- **WHEN** canonical isolated fixture запускает существующий authenticated browser journey на exact candidate
- **THEN** journey проходит setup/login и достигает первого предметного UI assertion; любой дальнейший RED однозначно относится к проверяемому visual behavior

#### Scenario: Baseline 503 имеет отдельную причину и regression guard
- **WHEN** диагностический loop воспроизводит прежний 503 на минимальном authenticated GET
- **THEN** regression test падает на установленной причине до исправления и проходит после минимальной коррекции без ослабления permission checks

### Requirement: Единая оболочка активного приложения
Система SHALL показывать на каждом активном Yii2-экране одну общую оболочку, которая владеет навигацией, единственным `main` landmark, skip-link, доступной областью контента и нижними безопасными отступами. Предметная страница MUST NOT изменять геометрию `body`, sidebar или общей оболочки неявным селектором, зависящим от её содержимого.

#### Scenario: Клавиатурная навигация по оболочке
- **WHEN** авторизованный пользователь открывает любой активный Yii2-маршрут и использует клавиатуру
- **THEN** skip-link переводит фокус в единственный `main`, focus indicator видим, а sidebar или bottom navigation не перекрывают последний доступный control

#### Scenario: Вариант ширины страницы
- **WHEN** предметной странице требуется отличающаяся доступная ширина или фон
- **THEN** система применяет явный общий вариант оболочки, не передавая странице владение `body`, sidebar или глобальным overflow

### Requirement: Единая композиция списков данных
Система SHALL представлять табличные реестры через единый договор data list с заголовком, строками, ячейками, локальным scroll-wrapper, числовыми/status/action вариантами, empty state и пагинацией. Колонки и предметное содержимое остаются специфичными для страницы; различная плотность MUST быть явным общим вариантом.

#### Scenario: Плотная таблица на узкой доступной ширине
- **WHEN** таблица не помещается в workspace на ширине 320, 390, 768, 1024, 1280, 1440 или 1920 CSS px, в том числе при раскрытом sidebar
- **THEN** таблица прокручивается внутри подписанного контейнера, весь документ не получает горизонтальный overflow, а все значения и действия остаются доступны

#### Scenario: Полное финансовое значение
- **WHEN** таблица показывает большое денежное значение, ноль или неизвестное значение
- **THEN** видимый или доступно раскрываемый текст сохраняет полное значение и его смысл без необратимого обрезания многоточием

#### Scenario: Простая таблица преобразуется в карточки
- **WHEN** для простого каталога выбран явный narrow-screen card variant
- **THEN** каждая карточка сохраняет подписи, значения, статус, действия, порядок и доступное имя исходной строки

#### Scenario: Пустой источник и пустой поиск
- **WHEN** источник данных пуст либо фильтр не находит строки
- **THEN** система показывает разные по смыслу состояния и сохраняет доступ к разрешённым действиям сброса фильтра или создания записи

### Requirement: Однозначная композиция полей
Система SHALL собирать text, search, date, select, textarea и file controls как полное поле с одной видимой подписью, control, help и error slots. Одно логическое поле MUST NOT содержать вложенную вторую полную field-композицию.

#### Scenario: Фильтр монтажников
- **WHEN** пользователь открывает фильтры реестра монтажников
- **THEN** каждый combobox имеет ровно одну видимую подпись, одно доступное имя и не находится внутри другого полного field-контейнера

#### Scenario: Ошибка ввода
- **WHEN** сервер отклоняет значение поля
- **THEN** сообщение ошибки находится рядом с полем, программно связано с control, не заменяет введённое значение и доступно без зависимости только от цвета

#### Scenario: Длинное значение и popover
- **WHEN** поле содержит длинный русский текст, email или имя файла либо открывает список вариантов
- **THEN** значение остаётся читаемым, а popover не обрезается поверхностью или overflow-родителем

### Requirement: Полноценное модальное поведение
Система SHALL использовать единый modal/drawer договор для общеупотребительных overlays: заголовок, body, footer, close target, scroll и один владелец управления фокусом. Domain-specific checklist, gallery и offline states MAY сохранять предметную композицию, но MUST использовать общие доступные примитивы.

#### Scenario: Открытие и закрытие modal
- **WHEN** пользователь открывает modal или drawer
- **THEN** фокус входит в overlay, Tab и Shift+Tab остаются в модальном контексте, фон не интерактивен, Escape и cancel закрывают без записи, а фокус возвращается к инициатору

#### Scenario: Подтверждение выплаты
- **WHEN** пользователь открывает подтверждение фиксации внешней выплаты и затем отменяет действие
- **THEN** система не отправляет финансовую команду, сохраняет существующий payload и no-JS fallback и возвращает фокус к инициатору

#### Scenario: Окно выбора монтажников на телефоне
- **WHEN** пользователь открывает окно выбора при ширине 320 или 390 CSS px, малой высоте, длинных ФИО и большом выбранном составе
- **THEN** responsive-геометрия применяется к фактическому dialog, header/actions остаются достижимы, а содержимое прокручивается внутри окна

### Requirement: Различимые feedback и operational states
Система SHALL представлять empty, loading, success, warning, denied, field error, retryable error, final error, offline pending, conflict и sent состояния согласованными примитивами без потери предметного различия. Действия MUST оставаться доступны без hover-only поведения.

#### Scenario: Offline checklist states
- **WHEN** checklist operation локально сохранена, ожидает отправки, конфликтует, завершилась ошибкой или отправлена
- **THEN** пользователь различает каждое состояние по тексту и семантике, а система не сводит их к одному success notification

#### Scenario: Ограниченное разрешение
- **WHEN** пользователь не имеет права на действие или раздел
- **THEN** система сохраняет действующую серверную авторизацию и показывает предусмотренное denied/absent состояние без появления рабочего запрещённого control

### Requirement: Сохранение продуктового поведения
Визуальная унификация MUST сохранять существующие маршруты, query/page/filter state, ссылки и кнопки по их семантике, роли, payloads, idempotency, append-only histories, расчётные формулы, даты, статусы процесса, исторические snapshots, offline storage/protocol и server/no-JS fallbacks. Она MUST NOT добавлять новый state-changing seam.

#### Scenario: Повтор визуальной команды
- **WHEN** пользователь повторяет существующее сохраняющее действие после таймаута или повторного клика
- **THEN** действующий idempotency/concurrency contract остаётся неизменным и визуальный слой не создаёт дополнительную запись

#### Scenario: Исторические и финансовые данные
- **WHEN** пользователь просматривает или выполняет разрешённое действие в ОТиЗ, completion, original или object card
- **THEN** формулы, суммы, даты, причины, редакции, snapshots и append-only history совпадают с поведением до визуальной миграции

#### Scenario: Закреплённая карточка объекта
- **WHEN** пользователь открывает и редактирует object card
- **THEN** сохраняются двухзонная компоновка, небольшая кнопка-карандаш, одно окно с двумя группами, набор редактируемых реквизитов и запрет ручного ввода Кшах

### Requirement: Проверяемая адаптивность и доступность
Система SHALL проходить общие browser-инварианты на репрезентативных потребителях и точечные regression cases V02, V03, V04, V06 и V09. Приёмка MUST проверять фактическую доступную ширину workspace, открытые overlays, короткую высоту, длинные данные, touch и 200% browser zoom/reflow; DPR simulation MUST NOT считаться доказательством zoom.

#### Scenario: Owner device matrix для всех активных экранов
- **WHEN** каждый из 25 активных Yii2 views и его доступные overlay/open states проверяются на 15″ laptop 1366×768 и 1536×864, Redmi Pad 2 Pro landscape 1280×800 и portrait 800×1280, mobile 360×800 и 390×844 CSS px
- **THEN** документ не получает горизонтальный overflow, shell/navigation не перекрывают content, тексты и controls не пересекаются и не выходят за surface, touch targets остаются достижимы, а широкие data lists сохраняют полный смысл через явно локализованный scroll либо согласованный card variant

#### Scenario: Широкий viewport и узкий workspace
- **WHEN** sidebar открыт на laptop/tablet и фактическая ширина workspace меньше viewport
- **THEN** responsive решение определяется доступной шириной owning container, а не только viewport breakpoint; таблица не сжимает заголовки и значения до пересечения и не расширяет весь документ

#### Scenario: Промежуточная ширина и breakpoint
- **WHEN** browser test проверяет ширину до, на и после фактически оставшегося breakpoint, включая 760–769px
- **THEN** нет горизонтального overflow документа, скрытых действий, перекрытий или обрезания критичных данных

#### Scenario: Touch target закрытия карточки
- **WHEN** пользователь взаимодействует с карточкой на touch viewport
- **THEN** визуально согласованный close target 40×40 px имеет удобную целевую область не менее 44×44 CSS px

#### Scenario: Before/after evidence
- **WHEN** exact-source candidate готов к финальному review
- **THEN** reviewer получает просмотренные before/after изображения на одной среде и данных, результаты focused checks и CI; snapshots не обновлены автоматически ради GREEN

### Requirement: Полный охват активных Yii2-представлений
Система SHALL применить единый договор ко всем 25 активным представлениям и связанным partials, перечисленным в аудите: objects, construction-control, installers, users, roles, object-card, completion, checklist, selection, original, original-history, execution, deadline-certificates, otiz, otiz-snapshot, `_otiz-snapshot-list`, `_otiz-nav`, calendar, dashboard, feedback, feedback-confirmation, feedback-admin, preopening-error, login и activate.

#### Scenario: Проверка реестра охвата
- **WHEN** candidate передаётся на независимый финальный review
- **THEN** для каждого представления записан статус миграции, применённые общие композиции, сохранённые исключения с обоснованием и соответствующее focused либо representative evidence

#### Scenario: Удаление заменённых правил
- **WHEN** страница переведена на общий договор
- **THEN** заменённые локальные CSS/JS-компенсации удалены, а не перекрыты новым хвостовым override
