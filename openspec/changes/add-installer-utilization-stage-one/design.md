## Context

См. `proposal.md` и delta-spec. На свежем `main` уже есть штатный справочник монтажников, native assignment-order read/write seams, факты открытия и ПТО, а PR #260 занял migration v34. Отклонённая ветка содержит экспериментальную read-модель и UI, но основана на старом main и не является контрактом или готовым кандидатом. Параллельные #249/#250 могут менять смежные источники; writers и общий UI остаются вне границ.

## Goals / Non-Goals

**Goals:**

- Один read-only владелец семантики текущей/предстоящей загрузки и периодов участия.
- Одинаковая DTO-проекция для справочника, карточки и picker.
- SQL-first фильтры, count и pagination без загрузки полного кадрового набора в PHP.
- Переиспользование существующих публичных фактов применённого состава, открытия, ПТО и эффективной идентичности.
- Рабочий Yii-маршрут от справочника к карточке и объекту, плюс контекст в существующем picker.

**Non-Goals:**

- Daily snapshots, dashboard charts, forecast, auto-allocation, performance/overload scoring.
- Изменение assignment writers, calendar reader, финансов, приглашений, общего shell/UI или стенда 8093.
- Эвристическая группировка адресов, массовый исторический импорт и новая финансовая модель.

## Decisions

### 1. Workforce владеет read-only проекцией

Новый порт/проекция в `app/Workforce` объединяет существующие публичные read-факты и возвращает стабильные строки/детали. Yii controllers только валидируют query, авторизацию и отображают результат; AssignmentOrderComposition picker потребляет компактную проекцию через локальную регистрацию. Альтернатива — повторить SQL в трёх controllers — отвергнута из-за расхождения правил.

### 2. Лифт идентифицируется каноническим effective key

Join и distinct выполняются по эффективному object/lift identity существующих фактов, не по адресу. Эффективные реквизиты служат только отображению. Альтернатива — нормализовать строки домов — запрещена постановкой и соединяет независимые лифты.

### 3. Текущая и предстоящая загрузка — два независимых набора

Current = applied composition ∩ factual opening − active PTO на том же лифте. Upcoming = confirmed original − factual opening. Draft/template не входят. DTO допускает несколько элементов обоих типов и отдельно выражает unknown/ unavailable. Альтернатива — единый enum статуса человека — теряет одновременную текущую и будущую работу.

### 4. История этапа выводится из доступных неизменяемых фактов

Карточка показывает реконструируемые периоды применённого участия и их известные границы; чтение ничего не сохраняет. Если существующих фактов недостаточно для даты, выводится неизвестность. Новая snapshot-таблица не создаётся: она относится к этапу 2.

### 5. Серверная выборка имеет парные list/count запросы

Одинаковые predicates применяются до LIMIT/OFFSET к list и count. Сортировка имеет стабильный tie-breaker. Query-параметры ограничены allowlist и передаются в возврат карточки. Альтернатива — фильтрация готовой страницы — не соответствует #258.

### 6. Схема по умолчанию не меняется

Этап сначала реализуется поверх существующих фактов. Если Gate 2 докажет неизбежную нехватку read-факта, scope возвращается root для пересмотра; v34 не используется. Production migrations, backup/restore и schema fingerprint поэтому сейчас неприменимы.

### 7. Интеграционные границы

Разрешены минимальные регистрации factory/config/route и точечные изменения существующих views. `rapid-pilot/` не меняется и не получает доменную логику. Изменения `app/PilotHttp` не планируются; если появятся, обязательна отдельная HTTP qualification check. Architecture inventory и Quality Graph обновляются только для фактически добавленных границ/проверок.

## Risks / Trade-offs

- [Доступные legacy-факты могут не дать полную дату старого периода] → показывать unknown и покрыть mixed native/legacy fixtures; не синтезировать даты.
- [Большие joins ухудшат справочник] → ограниченные SQL predicates, индексы только после evidence, EXPLAIN/набор больше страницы в focused проверке.
- [Параллельные изменения #249/#250 сдвинут reader] → перед Gate 2 повторно fetch/diff; зависеть от публичного read seam, не от writer internals.
- [Порт старой ветки перенесёт отклонённый UX] → переносить адресно только совпадающие алгоритмы/tests после сравнения с новым spec; UI реализовать заново в текущих поверхностях.
- [Частично недоступный источник выдаст ложный ноль] → fail-closed availability marker на всей строке/поверхности и тест недоступности.

## Migration Plan

1. Подготовить executable spec/tests и planner package на свежем base.
2. После требуемого Gate 3 отдельный executor реализует read projection и три поверхности.
3. Выполнить focused DB/HTTP/browser checks в disposable окружении без изменения рабочего стенда.
4. Провести exact-source Gate 5, один CI run, затем открыть PR; merge/deploy не выполнять.
5. Rollback — удалить read-only регистрацию/routes/views; бизнес-факты и schema не изменяются.
