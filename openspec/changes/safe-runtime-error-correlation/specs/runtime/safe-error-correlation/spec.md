## Purpose

Позволяет безопасно сопоставить выбранный HTTP 5xx с одной ограниченной журнальной записью, не меняя предметный результат запроса и не раскрывая чувствительные данные.

## ADDED Requirements

### Requirement: Server-owned error ID
Для каждого выбранного 5xx система SHALL сгенерировать новый непрозрачный error ID на сервере и вернуть его в фиксированном безопасном HTTP-заголовке. Значение одноимённого или сходного клиентского заголовка MUST NOT влиять на ID.

#### Scenario: Подмена клиентским заголовком
- **WHEN** запрос содержит пустой, слишком длинный, управляющий или произвольный client-supplied ID и выбранная обработка завершается 5xx
- **THEN** ответ содержит корректный server-generated ID, отличный от клиентского значения

#### Scenario: Неизменный успешный или ожидаемый ответ
- **WHEN** запрос завершается успехом либо ожидаемым 4xx
- **THEN** статус, тело, заголовки и предметные факты остаются прежними, а новая failure-запись не создаётся

### Requirement: Одна безопасная коррелированная запись
Система SHALL записать ровно одну компактную структурированную запись для выбранного failure с тем же ID, UTC-временем, ограниченным компонентом/шаблоном маршрута, HTTP-статусом, ограниченной категорией и доверенной build version либо `unknown`.

#### Scenario: Поиск записи по ответу
- **WHEN** выбранная bootstrap- или controller-ошибка сформировала 5xx
- **THEN** ID из заголовка находит ровно одну запись этого failure в штатном журнале

#### Scenario: Ошибка проходит через несколько слоёв
- **WHEN** один failure наблюдается controller boundary и глобальным обработчиком
- **THEN** журнал содержит одну, а не несколько диагностических записей этого failure

### Requirement: Доказуемая категоризация
Система SHALL различать `configuration`, `database`, `dependency`, `storage` и `unexpected` только по известному типу/коду или явному месту сбоя. Она MUST NOT выводить категорию из произвольного exception message; неопределённая причина SHALL оставаться `unexpected`.

#### Scenario: Известный bootstrap failure
- **WHEN** bootstrap подтверждённо не может применить configuration либо подключиться к database/dependency
- **THEN** запись содержит соответствующую ограниченную категорию и безопасный bootstrap component

#### Scenario: Storage и неизвестный controller failure
- **WHEN** выбранный controller получает известный storage failure либо неизвестное исключение
- **THEN** записи категоризированы соответственно как `storage` и `unexpected`, а не как database по тексту сообщения

### Requirement: Privacy allowlist
Новый ответ и новая запись MUST содержать только контрактные allowlisted fields. Они MUST NOT содержать exception message, stack trace, SQL/параметры, DSN/credentials/tokens/cookies, query string, request body, персональные данные, исходные имена или содержимое документов.

#### Scenario: Canary secrets во всех входах
- **WHEN** уникальные canary secrets присутствуют в exception message, query, cookies, headers, body, SQL/DSN и document metadata
- **THEN** ни HTTP-ответ, ни фактическая диагностическая запись не содержат ни один canary secret

### Requirement: Совместимость исходного результата
Диагностика SHALL сохранять текущий HTTP-статус, JSON/HTML reason и смысл неизвестного результата операции, защитные заголовки и `Retry-After`. Очистка заголовков глобальным handler MUST сохранить новый error-ID header.

#### Scenario: Неизвестный результат принятой операции
- **WHEN** controller возвращает существующий безопасный 503 после возможного принятия операции
- **THEN** текст/JSON и отсутствие автоматического повтора сохраняются, а добавляется только безопасный error-ID header

#### Scenario: Глобальная очистка ответа
- **WHEN** глобальный error handler очищает потенциально опасные заголовки перед отправкой 5xx
- **THEN** Location/cookies и прочие запрещённые данные отсутствуют, а server-generated error-ID header остаётся в отправленном ответе

### Requirement: Fail-safe logging
Ошибка создания или записи журнала MUST NOT менять исходный безопасный ответ, повторять команду, отменять принятую операцию, создавать domain facts или запускать рекурсивное журналирование. Bootstrap-диагностика SHALL работать без исправной БД и инициализированного Yii.

#### Scenario: Logger недоступен
- **WHEN** logger отказал при выбранном failure
- **THEN** клиент получает исходный безопасный статус/envelope с корректным server-generated ID, а бизнес-команда не повторяется

#### Scenario: Bootstrap до Yii и БД
- **WHEN** failure происходит до успешной инициализации Yii и database
- **THEN** ограниченный штатный fallback пытается записать allowlisted запись без зависимости от них и сохраняет безопасный ответ при собственном отказе
