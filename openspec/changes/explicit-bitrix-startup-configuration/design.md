## Context

См. proposal.md. Make вызывает legacy exporter; Compose монтирует `.local/bitrix-workforce.json`. `rapid-pilot/workforce-worker.sh` уже вызывает `bin/fmonitor2-sync-workforce.php`, который принимает этот файл через `WorkerConfiguration::fromFile`. Новый алгоритм синхронизации не нужен. `.dockerignore` исключает `.local`, но не `.env`.

## Goals / Non-Goals

**Goals:** один явный путь `.env` → подготовка в контейнере → существующий Docker secret → штатный CLI. Удалить exporter и зависимость от хостового PHP.

**Non-Goals:** менять HTTP, таблицы, права приложения, scheduler или владельца кадровых фактов. Устаревший `hourly-bitrix-workforce.php` не относится к удаляемому пути конфигурации и не расширяет этот PR.

## Decisions

1. Вход: `FMONITOR_BITRIX_WEBHOOK_URL` и `FMONITOR_BITRIX_DEPARTMENT_IDS_JSON`. Безопасный пример: `https://example.invalid/rest/1/replace_me/` и `[101,102]`, реальные значения вводятся только локально. Документировать кавычки и правила Compose `.env`; не исполнять `.env` через shell source и не интерполировать токен в команду Make.
2. Тонкий CLI подготовки в `bin/` запускается контейнером без зависимостей на БД/worker. Локальный `.env` монтируется read-only как файл для контейнерного разбора: Bitrix-поля однострочные, литеральные, без интерполяции или escape-последовательностей; допускаются значения без кавычек, в одинарных или двойных кавычках. Остальные переменные обрабатывает Compose. Конфигурация сериализуется в существующий формат `baseUrl`/`departments` и проверяется через `WorkerConfiguration::fromFile`; второй валидатор вебхука не создаётся. Альтернатива — передавать URL в environment worker — излишне расширяет доступ к секрету через container inspection.
3. Подготовка использует тот же образ PHP приложения; сборка предшествует подготовке. Подготовка запускается через `docker run --network none`, до первого Compose-вызова, чтобы парсер Compose не успел вывести повреждённую строку вебхука. Сборка выполняется через `docker build`; имя образа совпадает с Compose. Вход `.env` и `.env.*` исключаются из build context, `.env.example` допускается. Bitrix worker входит в штатный Compose без отдельного профиля; `make up` сначала подготавливает конфигурацию, затем запускает весь стенд. Секретные значения не интерполируются в Compose.
4. Новый временный файл создаётся с приватными правами (каталог 0700, файл 0600), проверяется и атомарно заменяет итоговый файл. Ошибка возвращает только безопасную категорию; Make прекращает цепочку. Повторная подготовка обновляет конфигурацию без сброса volumes. После `compose up` базовых сервисов Make пересоздаёт только worker (`--no-deps --force-recreate`), чтобы bind-mounted Docker secret получил новый inode после атомарной замены. Конкурентные подготовки не должны отдавать частичный JSON; если нужна блокировка, она ограничивается файлом конфигурации.
5. Owning module: существующая конфигурационная граница Workforce; CLI владеет только локальной подготовкой. Допустимы зависимости на autoload, файловую систему и существующий parser/validator, без SQL и legacy include. Владелец бизнес-persistence — прежний `MariaDbWorkforceSynchronization`; rapid-pilot остаётся запускающим адаптером. Architecture baseline не ослаблять, новые DDL/SQL/hotspot исключения не нужны.

## Risks / Trade-offs

- Различия синтаксиса `.env` → документированный однострочный литеральный синтаксис Bitrix-полей; безопасная проверка `compose config --quiet` перед запуском, stderr проверки не выводится.
- Docker secret на локальном Compose является файлом, а не зашифрованным хранилищем → приватные права и существующие ignore-правила, отсутствие токена в runtime environment.
- Старый secret после ошибки → запуск новой синхронизации запрещается кодом выхода подготовки; рабочий стенд автоматически не останавливается.
- Основание сверено с main `1dd62c2e`; отдельная ветка содержит только этот срез.

## Migration Plan

Оператор добавляет новые переменные в локальный `.env` по инструкции; извлечение из легаси больше не предлагается. Удаляются exporter, соответствующая Make-зависимость и актуальные инструкции старого запуска. Исторические review/operations записи не переписываются.

Проверки выполняются на disposable Compose project, синтетических секретах и локальном HTTPS fixture, без реального Bitrix и без изменений установленного стенда. Откат кода сохраняет volumes и приватные файлы; их содержимое не копируется в Git.
