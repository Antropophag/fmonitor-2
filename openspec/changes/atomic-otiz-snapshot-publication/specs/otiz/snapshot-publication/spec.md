## Purpose

Сотрудник ОТиЗ получает полностью построенный черновик расчёта; технический сбой
не оставляет неполный результат, доступный для принятия. Срез OTIZ-SNAPSHOT-PUBLICATION-001.

Простыми словами: подготовка либо сохраняет расчёт целиком, либо не публикует его.
Принятие остаётся отдельным действием. Формулы и правила выплат здесь не меняются.

## ADDED Requirements

### Requirement: Atomic draft publication

Система SHALL публиковать черновик на выбранную дату только вместе со всеми
входами, объектами, распределениями, замечаниями, итогами, версией правил и
подтверждением завершённости. История содержит одно событие публикации с actor,
time и identity. Отказ до публикации SHALL сохранять прежние факты неизменными.

#### Scenario: Complete result
- **WHEN** уполномоченный сотрудник готовит расчёт по двум допустимым объектам
- **THEN** результат содержит оба объекта, все их распределения и замечания,
  финальные итоги и одно событие; черновик доступен для просмотра, но ещё не принят.

#### Scenario: Controlled failure
- **WHEN** подготовка прерывается после создания заголовка, после первого объекта
  или непосредственно перед публикацией
- **THEN** ни один частичный новый расчёт не доступен другому пользователю для
  просмотра как готовый или для принятия; прежняя история остаётся неизменной,
  событие успешной публикации отсутствует.

#### Scenario: Concurrent input change
- **WHEN** другой пользователь изменяет исходные факты во время подготовки
- **THEN** опубликованный расчёт использует один согласованный срез входов,
  а не смесь версий до и после изменения.

### Requirement: Reject incomplete acceptance

Система SHALL принимать только завершённый опубликованный черновик без открытых
блокирующих замечаний. Отсутствие blockers само по себе не подтверждает полноту.
Отказ SHALL не менять статус, строки, итоги или историю принятия.

#### Scenario: Legacy interrupted draft
- **WHEN** пользователь пытается принять существующий draft с pending hash
  либо без доказательства завершённой публикации
- **THEN** получает SNAPSHOT_INCOMPLETE и предложение подготовить новый расчёт;
  старый draft сохраняется для просмотра и не становится accepted.

#### Scenario: Stored result is incomplete
- **WHEN** у опубликованного draft отсутствует обязательная сохранённая строка
  либо его сохранённое содержимое не соответствует подтверждению публикации
- **THEN** принятие даёт SNAPSHOT_INCOMPLETE без изменения истории; проверка
  использует фактическое сохранённое содержимое, а не само подтверждение.

#### Scenario: Complete draft and concurrent acceptance
- **WHEN** два пользователя одновременно принимают один завершённый draft без blockers
- **THEN** сохраняется одно принятие и одно событие; повтор сообщает неизменяемое
  состояние, не создавая второго принятия или события.

#### Scenario: Existing rejection behavior
- **WHEN** принятие запрошено для отсутствующего, уже принятого или содержащего
  открытые blockers среза
- **THEN** сохраняется соответствующий отказ not-found, immutable или blockers;
  прежние accepted facts и документы не меняются.

### Requirement: Authorization and replay

Система SHALL проверять активного пользователя и действующее otiz.manage внутри
прикладной команды; HTTP SHALL дополнительно проверять CSRF. Build SHALL принимать
устойчивую identity операции, одинаковую при повторе после потери ответа.

#### Scenario: Denied actor or invalid input
- **WHEN** нет полномочия, либо HTTP CSRF недействителен, либо reportDate не является
  действительной календарной датой YYYY-MM-DD
- **THEN** операция отвергается соответственно как forbidden, invalid-request или
  invalid-date без новых расчётов, строк или событий успешной публикации.

#### Scenario: Repeat and conflicting reuse
- **WHEN** запрос подготовки повторяется с той же identity и датой, в том числе параллельно
- **THEN** возвращается один и тот же полный snapshot и сохраняется одно событие;
  повтор той же identity с другой датой даёт OPERATION_CONFLICT без изменений.

### Requirement: Compatible history and request execution

Система SHALL сохранять текущие формулы, ролевой доступ, просмотр и экспорт ранее
принятых срезов. Обычный HTTP запрос SHALL работать без прав CREATE/ALTER/DROP;
неподготовленная схема SHALL давать readiness-ошибку без попытки создавать таблицы.

#### Scenario: Historical accepted snapshot
- **WHEN** после миграции открывается или экспортируется ранее принятый срез
- **THEN** его сохранённые значения, документы и история не пересчитываются и не удаляются.

#### Scenario: Runtime without DDL
- **WHEN** сотрудник проходит calculate → snapshot → accept → export с DML-only DB account
- **THEN** маршрут работает на заранее мигрированной схеме с прежним UI;
  при отсутствующей обязательной схеме запрос завершается readiness-ошибкой.
