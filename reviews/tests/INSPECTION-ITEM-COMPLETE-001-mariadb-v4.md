## MDB4-01 — BLOCKER: valid prepared execution is rejected by the COMMAND check

The oracle requires every matching process-list row to have
`COMMAND === 'Query'`. I ran the default path against current production as an
integration observation. It failed the same overlap assertion even though an
independent admin observer repeatedly saw both exact published runtime-user
connections continuously blocked for more than 300 ms with:

```text
COMMAND = Execute
STATE   = Statistics
INFO    = SELECT revision_no FROM `ic…_fm2_checklist_revisions`
          WHERE installation_case_id=? FOR UPDATE
```

This is the real prepared-statement execution generated by current production
on MariaDB 11.4.7. Both exact worker ids, private table and prepared predicate
were stable across approximately three seconds of 100 ms samples while the
coordinator held the fetched row lock. The test nevertheless set `$exact=false`
solely because `Execute !== Query` and finally failed after its ten-second
deadline.

Thus the controlled break proves the predicate can fail, but not that it accepts
a genuine overlap; in its current form it always rejects the production's
prepared query. The v4 evidence statement that rows must be `COMMAND=Query` is
inconsistent with observed MariaDB metadata.

Action required: correlate command representation with normalized SQL rather
than requiring only `Query`. At minimum, accept the exact pair
`COMMAND=Execute` plus the prepared `?` statement observed on this MariaDB, and
retain `COMMAND=Query` only for the exact literal `4512` form if that form is
actually supported. Do not accept broad commands or arbitrary SQL. Then
demonstrate both:

1. default path observes the two exact worker ids continuously for 300 ms and
   advances to the already reviewed behavioral assertions;
2. `FMONITOR_IIC_BREAK_OVERLAP=1` still produces the controlled missing-overlap
   RED with full cleanup.

Append corrected metadata evidence and request fresh independent rereview.
