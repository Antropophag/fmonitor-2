# FMonitor 2.0 — спецификация пилота

## 1. Цель

Пилот доказывает, что объект монтажа нельзя превратить в редактируемую строку: закрепление людей возникает только через распоряжение, а чек-лист становится доступен только после отдельного открытия работ сотрудником ФКР.

Официальный расчёт премии, автоматическая интеграция с 1С ДО и полный процесс инспекций не входят в первый инкремент.

## 2. Контур

- Объекты монтажа уже находятся в FMonitor.
- В пилот попадают объекты монтажа с ещё не открытыми работами и плановой датой начала с 1 октября 2026 года.
- Одно распоряжение относится ровно к одному объекту монтажа.
- Дата распоряжения фиксируется FMonitor при формировании; 1С ДО присваивает номер, который вручную возвращается в FMonitor.
- Открытие разрешено только по актуальному распоряжению в статусе `registered`. В пилоте статус подтверждается ручным вводом регистрационного номера, в будущем — интеграцией с 1С ДО.

## 3. Роли пилота

### Сотрудник ФКР

- видит очередь объектов монтажа по плановой дате;
- открывает один объект монтажа;
- выбирает одного или нескольких монтажников;
- выбирает одного инженера строительного контроля;
- формирует и скачивает проект распоряжения;
- относит документ в 1С ДО;
- временно указывает номер 1С ДО в карточке распоряжения до появления интеграции;
- отдельно открывает работы и указывает фактическую дату начала;
- инициирует изменяющее распоряжение при изменении состава.

### Инженер строительного контроля

- является пользователем FMonitor;
- выбирается сотрудником ФКР при подготовке распоряжения;
- после открытия работ получает объект монтажа в своей очереди;
- в следующих инкрементах фиксирует инспекции, наблюдаемый состав и прогресс.

### Руководитель

- видит просроченные распоряжения;
- видит состояние регистрации внутри карточки распоряжения, не как отдельный этап процесса;
- видит возраст незавершённых задач.

### Системный администратор

- управляет пользователями и ролью инженера строительного контроля;
- просматривает закрытый security-аудит в пределах отдельного полномочия;
- не исправляет процессные состояния через универсальную таблицу.

## 4. Источники данных

| Данные | Источник | Изменение в пилоте |
|---|---|---|
| Объект монтажа, адрес, подъезд, регномер, плановые даты | существующий FMonitor / текущая интеграция объектов | read-only в процессе распоряжения |
| Монтажники | `ЗУП → Битрикс → FMonitor` | выбор без ручного создания |
| Инженеры строительного контроля | пользователи FMonitor с соответствующей ролью | выбор без свободного ввода ФИО |
| Дата распоряжения | FMonitor | автоматически и неизменно при формировании |
| Номер распоряжения | 1С ДО | ручной ввод после регистрации |
| Фактическая дата начала | сотрудник ФКР | обязательный ввод при открытии работ |
| Дата Акта ПТО | существующий FMonitor, `ptoactdate` | обязательный реквизит факта Акта ПТО; наличие даты блокирует обычную подготовку, изменение и открытие |
| Файл Акта ПТО | существующий FMonitor / загрузка документа | необязательное вложение; отсутствие файла не отменяет факт, подтверждённый датой |

## 5. Основной сценарий

1. Сотрудник ФКР открывает экран **«Объекты монтажа»**.
2. Система показывает сначала просроченные объекты монтажа, затем ближайшие по плановой дате начала.
3. Пользователь открывает карточку одного объекта монтажа.
4. Система показывает данные объекта и текущую причину следующего действия.
5. Пользователь нажимает компактную кнопку **«Сформировать распоряжение»**.
6. В мастере он выбирает монтажников и инженера строительного контроля.
7. Система проверяет обязательные данные и кадровую допустимость.
8. Пользователь просматривает документ и подтверждает формирование.
9. FMonitor фиксирует версию проекта и предоставляет файл для скачивания.
10. В карточке распоряжения доступен временный ручной ввод номера 1С ДО; отдельный экран, вкладка или этап для него не создаётся.
11. При открытии работ пользователь указывает фактическую дату начала.
12. FMonitor переводит монтажное дело в работу и разблокирует чек-лист.
13. Если номер 1С ДО ещё не внесён, это видно в реквизитах документа, но не создаёт отдельного состояния или очереди процесса.
14. После регистрации пользователь указывает номер в карточке версии; документ получает признак регистрации без отдельного процессного перехода.

Допустимость шагов 11–12 до появления номера определяется отдельной политикой открытия. При любом варианте номер остаётся реквизитом документа, а не самостоятельным процессным обязательством.

## 6. Состояния монтажного дела

| Состояние | Что означает | Доступное основное действие |
|---|---|---|
| Требуется распоряжение | по объекту монтажа нет актуального проекта | Сформировать распоряжение |
| Распоряжение подготовлено | состав зафиксирован, файл сформирован | Указать номер в строке документа |
| Готов к открытию | актуальное распоряжение имеет статус `registered`, но работы ещё не открыты | Открыть работы |
| В работе | работы открыты; статус регистрации показан отдельно в документе | Перейти к чек-листу |
| Требуется изменение | состав должен измениться | Подготовить изменение |

Наличие номера — реквизит документа, а право открыть работы определяется статусом документа. Только актуальное распоряжение со статусом `registered` допускает открытие.

## 7. Команды и проверки

### Сформировать распоряжение

Требует:

- один объект монтажа;
- заполненные адрес, подъезд, регномер и плановые даты;
- минимум одного монтажника из актуального каталога;
- одного активного пользователя с ролью инженера строительного контроля;
- отсутствие Акта ПТО/завершения;
- отсутствие другого актуального проекта, который пользователь пытается молча перезаписать.

Результат:

- неизменяемая версия проекта;
- PDF/DOCX и приложение;
- назначения в состоянии ожидания регистрации;
- видимый в карточке документа статус регистрации в 1С ДО.

### Указать номер 1С ДО в карточке документа

Это временное ручное действие до появления интеграции. Оно подтверждает переход версии из `prepared` в `registered`, но не имеет отдельного экрана, вкладки, очереди или состояния монтажного дела. Будущая интеграция выполняет тот же переход статуса.

Требует:

- подготовленный проект;
- номер распоряжения;
- отсутствие другого документа с тем же номером в допустимой области уникальности.

Результат:

- зарегистрированная версия распоряжения;
- окончательно подтверждённые назначения;
- обновлённые реквизиты той же версии без создания отдельного состояния монтажного дела.

### Открыть работы

Требует:

- актуальное распоряжение в статусе `registered`;
- обязательную фактическую дату начала;
- фактическую дату не раньше даты распоряжения и не позже текущей даты;
- минимум одного допустимого монтажника;
- одного инженера строительного контроля;
- отсутствие завершения/Акта ПТО;
- отсутствие блокирующих кадровых конфликтов.

Результат:

- состояние «В работе»;
- запись фактической даты начала;
- аудит пользователя и точного времени открытия;
- доступный чек-лист;
- объект монтажа в очереди выбранного инженера.

### Подготовить изменение

Не редактирует действующий состав. Создаёт новую версию проекта, в которой явно указаны прекращаемые и начинающиеся назначения. Исторические пункты чек-листа не перепривязываются к новым людям.

## 8. Экраны первого инкремента

1. **Очередь объектов ФКР** — компактный список по срочности, без широкой Excel-таблицы.
2. **Карточка объекта монтажа** — контекст, документ, состав, статус и компактная панель действий.
3. **Мастер распоряжения** — выбор монтажников и инженера, проверки, предпросмотр.
4. **Открытие работ** — небольшой диалог фактической даты начала и итогового подтверждения.
5. **Справочник монтажников** — статус, действующие закрепления и доступность.
6. **Карточка монтажника** — кадровые данные, текущие и исторические назначения.
7. **Очередь руководителя** — доказуемые нарушения сроков и зависшие процессные обязательства.

Временный ввод номера расположен в карточке документа и не образует отдельный экран или вкладку.

Кнопки имеют стандартный размер `shlz-ui`. Процессная приоритетность выражается порядком и доступностью действий, а не размером элементов.

## 9. Запреты

- Нельзя начать чек-лист до открытия работ.
- Нельзя сформировать распоряжение без монтажника или инженера.
- Нельзя ввести монтажника свободным текстом.
- Нельзя выбрать инженера вне пользователей требуемой роли.
- Нельзя изменить состав обычным редактированием карточки.
- Нельзя молча заменить сформированный проект новой версией.
- Нельзя переписать исторических исполнителей выполненного пункта чек-листа.
- Нельзя превращать временный ручной ввод номера 1С ДО в отдельный этап, вкладку или самостоятельно закрываемую процессную задачу.
- Нельзя открыть или изменить работы после Акта ПТО обычным сценарием.

## 10. Критерии приёмки пилота

1. Сотрудник ФКР проходит основной сценарий по одному объекту монтажа без обращения к универсальной таблице.
2. Проект распоряжения воспроизводимо формируется из данных объекта и выбранного состава.
3. Невозможно сформировать документ без монтажника и инженера.
4. Невозможно открыть чек-лист до команды открытия работ.
5. Открытие требует фактическую дату начала и фиксирует отдельный аудит действия.
6. Статус регистрации виден в карточке распоряжения, но не создаёт отдельного состояния монтажного дела.
7. Изменение состава создаёт новую версию и не меняет исторические доказательства.
8. Справочник монтажника показывает действующие закрепления из новой модели.
9. Штатный пользователь не использует широкую Excel-подобную таблицу ни в одном шаге сценария.
10. Все действия, доступные через UI, проходят те же проверки при вызове из интеграции или служебной команды.

## 11. Открытые решения

- Можно ли сотруднику ФКР указывать фактическую дату начала в прошлом и в каких пределах.
- Нужно ли прикладывать финальный файл из 1С ДО или достаточно номера.
- Какая роль может исправить ошибочно введённый номер и каким документом это оформляется.
