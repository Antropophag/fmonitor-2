# Миграция истории завершённых объектов FMonitor → FMonitor 2.0

Статус: **проект продуктового решения, ожидает согласования Gate 1**  
Дата: 29.08.2026

## 1. Решение в одном абзаце

Завершённый объект переносится не как одна «правильная» строка и не как свободно
редактируемая копия legacy-данных, а как **дело исторической реконструкции**.
FMonitor 2.0 неизменно сохраняет исходный снимок legacy, строит из него
предлагаемую временную линию прогресса и состава, сопоставляет её с независимыми
сведениями ОТиЗ о фактических выплатах, показывает расхождения и позволяет
уполномоченным сотрудникам создавать датированные корректирующие факты. После
проверки ОТиЗ фиксируется версия подтверждённой истории; исходник и все прежние
версии остаются доступными. Только подтверждённая версия участвует в штатных
ретроспективных расчётах FMonitor 2.0.

## 2. Почему прямой перенос опасен

В legacy одновременно существуют данные разной доказательности:

- текущие поля `fm_maintable.installator{,2,3,4}` показывают последний известный
  состав, но не доказывают состав в прошлую дату;
- `fm_install_checklists_values_log` содержит события включения и отмены пунктов
  чек-листа и является лучшим доступным источником прогресса на дату;
- `fm_install_checklists_values_installators_log` содержит исполнителей пункта,
  но часть записей связана с отметкой на одну секунду позже, часть содержит
  `999999/000000`, часть отсутствует;
- `ctime` основной строки чек-листа может быть датой создания, а не датой
  фактического подтверждения работы;
- текущий кадровый статус и текущий состав нельзя превращать в исторический факт;
- «рассчитано ранее FMonitor» не равно «фактически выплачено»;
- акты, декларации и текущее состояние объекта дают контрольные точки, но не
  восстанавливают автоматически помесячную динамику выполнения.

Следовательно, миграция должна хранить различие между **импортированным
утверждением**, **автоматической гипотезой**, **независимым свидетельством** и
**подтверждённым фактом**.

## 3. Предметные понятия

### Дело исторической реконструкции

Ограниченный процесс сверки одного завершённого монтажного дела. Он начинается
с неизменяемого импорта и заканчивается подтверждённой версией исторической
линии либо статусом «не удаётся подтвердить».

### Исходный снимок миграции

Неизменяемый набор извлечённых legacy-строк с временем извлечения, идентификатором
источника, контрольной суммой и версией правил чтения. Снимок отвечает на вопрос
«что именно было в legacy при миграции», а не «что действительно произошло».

### Утверждение об историческом факте

Кандидат на факт: прогресс, исполнитель, состав, дата завершения, расчёт или
выплата. Утверждение всегда имеет источник, период применимости, уровень
доказательности и ссылку на исходные данные.

### Подтверждённая историческая версия

Неизменяемая согласованная линия фактов по объекту. Новая информация не меняет
её: создаётся следующая версия с причиной и различиями.

### Расчётная контрольная точка ОТиЗ

Запись о том, что за период `от–по` ОТиЗ фактически выплатил определённую сумму
конкретному монтажнику по конкретному объекту. Это независимое свидетельство
для сверки, но не автоматическое доказательство конкретных выполненных пунктов
чек-листа.

## 4. Границы решения

В первой очереди переносим только объекты, завершённые до даты ввода их в
штатный процесс FMonitor 2.0. Для них:

- не создаём задним числом распоряжения, инспекции или пользователей, которых
  не было в источнике;
- не смешиваем реконструированную историю с новым operational-процессом;
- не редактируем legacy-базу;
- не считаем текущие поля доказанной историей;
- не требуем восстановить каждый пункт, чтобы сохранить сам объект;
- не объявляем выплату доказательством физического выполнения: она является
  сильной контрольной точкой для обнаружения несовместимости данных.

|---|---|

| `installation_case_id` | монтажное дело FMonitor 2.0 |


### `fm2_history_facts`

Унифицированный реестр реконструированных фактов. Денежные строки хранятся в
специализированных таблицах ниже, но также получают ссылку на версию.

| Поле | Назначение |
|---|---|
| `id`, `history_version_id` | идентичность и версия |
| `fact_type` | `work_started`, `checklist_completed`, `checklist_cancelled`, `crew_membership`, `pto_completed`, `declaration_registered`, `deadline_changed` |
| `subject_type`, `subject_id` | объект факта: дело, пункт, монтажник |
| `effective_from`, `effective_to` | предметное время/интервал |
| `recorded_at` | когда факт появился в источнике |
| `value_json` | типизированное значение и снимки реквизитов |
| `evidence_grade` | уровень доказательности |
| `derivation_rule` | точное правило вывода, nullable для прямого факта |
| `source_snapshot_id`, `source_record_key` | происхождение |
| `replaces_fact_id` | какой факт исправляет эта версия |
| `decision_id` | ручное решение, если факт не принят автоматически |

Уровни доказательности:

1. `direct` — прямой датированный журнал/подписанный документ/реестр выплаты;
2. `correlated` — однозначное техническое сопоставление, например назначение на
   `+1` секунду тому же пункту тем же пользователем;
3. `inferred` — согласованная эвристика, например единственный кандидат в
   текущем составе;
4. `asserted` — ручное утверждение ОТиЗ/ответственного лица с основанием;
5. `unknown` — факт необходим, но не восстановлен.

`evidence_grade` не задаёт автоматический приоритет истины. Конфликт двух прямых
источников всё равно требует решения.

## 6. Алгоритм первоначальной реконструкции

### 6.1. Извлечение

Для каждого завершённого legacy-объекта одним согласованным cutoff извлекаются:

- идентификационные поля объекта, договорные и скорректированные сроки;
- дата акта ПТО и номер декларации без попытки извлечь дату из номера;
- все события `fm_install_checklists_values_log` до cutoff;
- журнал исполнителей пункта;
- текущие назначения пунктов;
- история четырёх полей состава из `fm_data_changelog`;
- текущий состав только как слабое свидетельство;
- известная кадровая история и отдельно первое наблюдение увольнения;
- характеристики для норматива и коэффициент шахты;
- доступные legacy-расчёты только с меткой `calculated`, не `paid`.

Извлечение повторяемо и не меняет источник. Повторный запуск с тем же содержимым
даёт тот же `content_sha256` и не создаёт новую рабочую версию.

### 6.2. Восстановление состояния чек-листа на дату

События сортируются по `(ctime, id)`. Для пары `объект + пункт` на выбранную дату
берётся последнее событие: `1` включает вес, `0` отменяет его. Время основной
строки `fm_install_checklists_values.ctime` для этого не используется.

Исполнители события связываются каскадом:

1. пакет с тем же `checklist_value_id` и точным `ctime` — `direct`;
2. при его отсутствии пакет ровно на одну секунду позже, тот же пользователь —
   `correlated`;
3. однозначная последующая замена `999999/000000` реальным табельным номером —
   `correlated`, с явным правилом деривации;
4. единственное текущее назначение конкретного пункта — `inferred`;
5. единственный реальный монтажник текущей бригады — только ручная предлагаемая
   гипотеза `inferred`, не принимаемая автоматически;
6. иначе создаётся проблема `HISTORICAL_INSTALLER_UNKNOWN`.

Техническая заглушка никогда не становится монтажником FMonitor 2.0.

### 6.3. Квып и вклад

На дату `t`:

```text
Квып(t) = Σ весов пунктов, последнее состояние которых на t равно «выполнен»

Вклад монтажника i(t) =
  Σ вес пункта / количество подтверждённых исполнителей пункта
```

Неизвестный исполнитель не распределяется молча между известными людьми. Его
доля остаётся `unallocated` и блокирует автоматическое подтверждение строки.

### 6.4. Сопоставление с ОТиЗ

Реестр ОТиЗ загружается отдельно и сначала сопоставляется по устойчивым ключам:

1. регистрационный номер оборудования + табельный номер;
2. при отсутствии — подтверждённая ручная привязка объекта/человека;
3. ФИО или адрес сами по себе не дают автоматического совпадения.

Для каждой строки ОТиЗ `period_from–period_to` система строит две контрольные
точки прогресса и воспроизводит историческую методику:

```text
дельта Квып = Квып(period_to) − Квып(день перед period_from)

накопленное право(period_to)
− фактически выплачено до period_from
= расчётная дельта периода
```

Точная денежная формула вызывается версионированным `PremiumCalculation`
модулем. Для действующей исследованной методики он учитывает норматив,
коэффициент шахты, накопленный Квып, фактический вклад, Ксс, КТУ и предыдущие
фактические выплаты. Импорт не копирует сумму как будто она рассчитана по
текущим правилам.

Сверка классифицирует расхождение, но не предлагает произвольную дату/процент,
которые математически «подгонят» сумму выплаты.

## 7. Рабочий экран ОТиЗ

Нужен отдельный экран **«Сверка исторических объектов»**, а не режим
редактирования карточки объекта.

### Очередь

Группы:

- готовы к подтверждению;
- не сопоставлены выплаты;
- расходится сумма;
- неизвестен исполнитель;
- не восстанавливается дата/динамика;
- подтверждены;
- невозможно подтвердить.

Строка показывает объект, диапазон исторических дат, число выплат, долю прямых/
восстановленных/неизвестных фактов, сумму расхождения и следующее действие.

### Карточка сверки

Три синхронных представления:

1. временная линия Квып и состава;
2. выплаты ОТиЗ по периодам и монтажникам;
3. расхождения с раскрываемой трассировкой до пунктов чек-листа и источников.

Допустимые действия:

- сопоставить неоднозначную строку выплаты;
- заменить дату факта;
- назначить или разделить исполнителей пункта;
- признать факт неизвестным;
- исключить строку из сверки с причиной;
- пересчитать рабочую версию;
- передать на подтверждение;
- подтвердить версию целиком.

ОТиЗ не меняет исходный снимок и не правит подтверждённую версию. Для нового
решения система создаёт новую draft-версию и показывает diff.

## 8. Командный интерфейс глубокого модуля

Предлагается отдельный модуль `HistoricalReconstruction`; он не входит внутрь
`InstallationProcess` и не записывает его таблицы напрямую.

```text
importCompletedCase(legacyObjectId, cutoffAt, actorId)
importOtizPaymentRegister(artifactId, actorId)
matchPaymentEvidence(paymentEvidenceId, installationCaseId, installerTabId, actorId)
proposeReconstruction(migrationCaseId, rulesetVersion, actorId)
recordHistoricalDecision(migrationCaseId, draftVersion, decision, actorId)
recalculateReconciliation(migrationCaseId, draftVersion, actorId)
submitHistoryForConfirmation(migrationCaseId, draftVersion, actorId)
confirmHistoricalVersion(migrationCaseId, version, actorId)
markHistoryUnableToConfirm(migrationCaseId, reason, actorId)
getHistoricalReconciliation(migrationCaseId)
```

Импорт, UI и пакетный job вызывают эти команды; прямое обновление таблиц
реконструкции запрещено.

## 9. Полномочия и принцип четырёх глаз

- технический импортёр может создать снимок, но не принять спорный факт;
- сотрудник ОТиЗ может сопоставлять выплаты и готовить решения;
- подтверждение версии требует отдельного capability
  `historical_reconstruction.confirm`;
- рекомендовано запретить подтверждение пользователем, который внёс ручные
  решения в эту версию; если организация не может выделить второе лицо, это
  должно быть явным управляемым исключением, а не скрытым послаблением;
- системный администратор не получает предметных полномочий автоматически.

Каждая команда сохраняет пользователя, точное время, основание, старое и новое
представление и хэш версии.

## 10. Инварианты

1. Legacy и исходные снимки не изменяются.
2. Подтверждённая версия и факты выплаты append-only.
3. В одном деле одновременно только одна редактируемая draft-версия.
4. Новый факт коррекции ссылается на заменённый факт и решение-основание.
5. Текущий состав/статус не превращается автоматически в исторический direct-факт.
6. `999999/000000` не является монтажником.
7. Неизвестность хранится явно и не заменяется нулём, текущей датой или текущим
   пользователем.
8. Сумма ОТиЗ не используется для математической подгонки прогресса.
9. Одна выплата не может быть дважды учтена в разных строках сверки.
10. Расчёт всегда воспроизводим по хэшам входов и версии правил.
11. Изменение ruleset не пересчитывает подтверждённую историю молча, а создаёт
    новую кандидатную версию.
12. Обычные экраны объекта читают только актуальную подтверждённую версию;
    непроверенные данные показываются отдельно с явным статусом.

## 11. Пример

По объекту 10001 legacy показывает:

- 31.01 — Квып 20%, исполнитель пункта Иванов;
- 15.02 — ещё 30%, исполнитель отсутствует;
- текущий состав: Иванов и Петров;
- ОТиЗ: за 01.02–29.02 Иванову выплачено 60 000 ₽, Петрову 40 000 ₽.

Система не распределяет отсутствующие 30% пропорционально выплатам. Она создаёт
проблему неизвестного исполнителя и показывает, что текущий состав даёт двух
кандидатов. ОТиЗ открывает первичную ведомость/служебную записку и принимает
решение: 18 п.п. Иванову, 12 п.п. Петрову, с документом-основанием. Создаётся
новая версия фактов, расчёт воспроизводится и сравнивается с 60/40 тыс. Если
совпадение достигнуто, это следствие подтверждённого решения, а не алгоритмической
подгонки. После второго подтверждения версия становится источником исторической
проекции объекта.

## 12. Пакетная стратегия миграции

### Волна 0 — профилирование без записи

- зафиксировать cutoff и контрольные количества;
- классифицировать объекты по качеству: A — полностью direct/correlated, B —
  нужны однозначные решения, C — неоднозначны, D — нет платежных данных;
- получить шаблон и выгрузки ОТиЗ, подтвердить устойчивые ключи и смысл дат;
- сверить агрегаты: объекты, пункты, Квып, люди, суммы.

### Волна 1 — теневой импорт

- загрузить снимки и построить draft-версии;
- ничего не показывать как подтверждённую историю штатным расчётам;
- параллельно воспроизвести несколько закрытых периодов и сравнить результаты.

### Волна 2 — контрольная выборка

- 10–20 объектов всех классов сложности;
- ручная сверка ОТиЗ до первичных платёжных оснований;
- согласование допустимых reason codes, допусков и обязательных доказательств.

### Волна 3 — промышленная сверка

- сначала A, затем B; C обрабатываются вручную;
- D можно сохранить как `unable_to_confirm`, не выдумывая историю;
- подтверждать объект целиком, не отдельные удобные строки.

### Волна 4 — ввод проекции

- только после подтверждения переключить историческое чтение объекта на FMonitor
  2.0;
- сохранить legacy read-only как источник аудита;
- вести отчёт расхождений и выборочный постконтроль.

## 13. Метрики готовности и остановки

Перед массовым подтверждением должны быть видимы:

- доля фактов `direct`, `correlated`, `inferred`, `asserted`, `unknown`;
- число несопоставленных и неоднозначных выплат;
- сумма расхождений до и после решений;
- число объектов без независимых данных ОТиЗ;
- число ручных решений на объект и по сотруднику;
- воспроизводимость повторного импорта и пересчёта;
- контроль, что итог фактических выплат не изменён миграцией.

Массовая волна останавливается при изменении схемы legacy, неожиданном росте
неоднозначных сопоставлений, несовпадении агрегатов или обнаружении правила
методики, не зафиксированного в `ruleset_version`.

## 14. Предлагаемые вертикальные спецификационные срезы

После согласования решения работу следует вести по SSD + TDD отдельно:

1. `HISTORY-IMPORT-001` — неизменяемый идемпотентный снимок одного завершённого
   объекта;
2. `HISTORY-REBUILD-001` — состояние чек-листа на дату и безопасное связывание
   исполнителей exact/+1 секунда;
3. `HISTORY-PAYMENT-IMPORT-001` — неизменяемая строка фактической выплаты и
   идемпотентность внешнего ключа;
4. `HISTORY-RECONCILE-001` — сравнение одной строки ОТиЗ с воспроизводимым
   расчётом;
5. `HISTORY-DECISION-001` — ручная корректировка создаёт новую версию, не меняя
   источник;
6. `HISTORY-CONFIRM-001` — подтверждение целой версии с проверкой полномочий и
   открытых блокеров;
7. `HISTORY-SUPERSEDE-001` — новая подтверждённая версия заменяет проекцию, но
   сохраняет прежнюю;
8. `HISTORY-QUEUE-001` — очередь ОТиЗ по статусам и следующему действию.

Для каждого среза обязательны отдельные red-тест, независимое ревью теста,
минимальная реализация и независимое code review согласно
`docs/development-process.md`.

## 15. Решения, которые нужно подтвердить до Gate 1

1. Какой документ ОТиЗ считается первоисточником фактической выплаты и содержит
   ли он стабильные ключи объекта, табельного номера, периода и платежа?
2. `period_from` включителен? Сравниваем ли Квып на конец предыдущего календарного
   дня или с точной контрольной точкой предыдущего среза?
3. Кто готовит и кто независимо подтверждает историческую версию?
4. Допустимо ли подтверждение с `unknown`, и какие типы неизвестности являются
   блокирующими?
5. Есть ли согласованный денежный допуск, правила округления и обработки
   отрицательной дельты?
6. Нужно ли переносить суммы только как факты выплат или также утверждённые
   расчётные ведомости/КТУ/дисциплинарные поправки?
7. Где хранятся оригиналы документов-оснований и каков срок их хранения?
8. Какая дата является границей: объект полностью исторический либо уже
   управляется штатным процессом FMonitor 2.0?

До ответов схема пригодна для теневого импорта и профилирования, но не для
массового подтверждения истории.
