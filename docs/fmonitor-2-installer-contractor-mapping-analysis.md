# Сопоставление монтажников с субподрядчиками

Статус: аналитика и проект продуктового решения, ожидает согласования  
Дата: 29.08.2026

## Вывод

Отдельный справочник организаций, отдельный справочник монтажников и связь между
ними — правильная модель. Однако связь нельзя хранить простым полем
`contractor_id` в карточке монтажника: монтажник может перейти в другую
организацию, одновременно привлекаться несколькими организациями или иметь
неподтверждённую принадлежность в legacy-истории.

Целевая модель:

```text
Монтажник 1 ─── 0..N Принадлежностей 0..N ─── 1 Монтажная организация
                              │
                       период + источник + статус
```

В обычном случае у монтажника одна действующая основная принадлежность. Модель
при этом сохраняет прошлые периоды и способна явно показать конфликт нескольких
одновременных связей.

## 1. Что уже есть в legacy

### Субподрядчик объекта

В `fm_maintable.subsuplier` хранится ID значения списка `fm_fields_values` для
поля 7. Именно этот справочник содержит АЕДИ, ПСК, СМЛ, МЕКС и другие монтажные
организации. Поле `contractor`/field 85 относится к другому процессу и не должно
использоваться для этой связи. Следствия:

- устойчивого идентификатора юридического лица нет;
- ИНН/КПП в самой ссылке подрядчика не участвуют;
- варианты написания могут создавать дубли;
- `subsuplier` относится к объекту, а не непосредственно к монтажнику;
- история изменений может частично восстанавливаться через
  `fm_data_changelog`, но полнота не гарантирована.

Некоторые значения поля 7 кодируют две организации, например `ООО "АЕДИ"
(ООО "ПСК")`. До предметного подтверждения первая организация считается
непосредственным субподрядчиком-кандидатом, а значение в скобках — контекстом
цепочки. Таблица `clients` не является справочником поля 7: совпадающие числовые
ID дают ложные названия организаций.

### Монтажники объекта

Текущие `installator{,2,3,4}` и история их изменений показывают назначение людей
на объект. Журналы чек-листа дают фактический вклад в работы. Ни один из этих
источников не утверждает напрямую, что организация является работодателем или
постоянной организационной принадлежностью монтажника.

### Что можно вывести

Если на объекте одновременно известны подрядчик и монтажник, возникает
**кандидат сопоставления**:

```text
монтажник работал на объекте X
объект X связан с подрядчиком Y
→ возможно, монтажник относился к Y в этот период
```

Это полезная гипотеза для массовой сверки, но не подтверждённая принадлежность.
Она может означать разовую бригаду, аренду персонала, ошибку в карточке объекта
или подрядчика другого уровня.

## 2. Терминология

Рекомендуемый канонический термин для справочника — **монтажная организация**,
а не «субчик». «Субподрядчик» — роль организации в конкретном договоре или
монтажном деле, тогда как одна и та же организация может выступать подрядчиком,
субподрядчиком или иной стороной в разных делах.

Связь человека с организацией называется **принадлежность монтажника к монтажной
организации**. Она не обязательно равна трудоустройству: юридическая природа
отношений может быть неизвестна FMonitor.

Нужно различать три связи:

1. принадлежность монтажника к организации;
2. роль организации в монтажном деле;
3. назначение монтажника на монтажное дело.

Из двух последних нельзя без дополнительного основания автоматически создавать
первую.

## 3. Целевая схема данных

Названия предварительные; важны инварианты.

### `fm2_organizations`

Единый справочник организаций. Отдельный справочник только «субподрядчиков»
привёл бы к дублированию одной организации при смене её роли.

| Поле | Назначение |
|---|---|
| `id` | внутренняя идентичность организации |
| `legal_name` | полное юридическое наименование |
| `short_name` | отображаемое наименование |
| `inn`, `kpp` | устойчивые реквизиты, если известны |
| `ogrn` | дополнительный идентификатор, nullable |
| `status` | `active`, `inactive`, `unknown` |
| `source_system`, `source_external_id` | первоисточник и внешний ключ |
| `source_updated_at` | свежесть данных источника |
| `created_at`, `updated_at` | технический аудит |

Роль `subcontractor` не хранится в этой таблице как постоянный тип организации.

Правила идентичности:

- при наличии ИНН + КПП они являются главным ключом сопоставления;
- одинаковое название не является достаточным основанием для автоматического
  слияния;
- ручное объединение дублей сохраняет алиасы и provenance, а не удаляет следы
  исходных значений.

### `fm2_organization_aliases`

| Поле | Назначение |
|---|---|
| `organization_id` | каноническая организация |
| `source_system`, `source_value_id` | legacy ID или внешний ID |
| `name_snapshot` | исходное написание |
| `valid_from`, `valid_to` | период известности, если восстанавливается |
| `match_method` | `external_id`, `tax_id`, `manual`, `name_candidate` |
| `confirmed_at`, `confirmed_by` | аудит ручного решения |

### `fm2_installer_organization_affiliations`

Датированная many-to-many связь монтажников и организаций.

| Поле | Назначение |
|---|---|
| `id` | идентификатор связи |
| `installer_tab_id` | монтажник из кадрового каталога |
| `organization_id` | монтажная организация |
| `relationship_kind` | `member`, `engaged`, `unknown` |
| `valid_from`, `valid_to` | включительный период принадлежности |
| `is_primary` | основная организация в период, если подтверждено |
| `status` | `proposed`, `confirmed`, `rejected`, `superseded` |
| `evidence_type` | тип основания |
| `evidence_ref` | документ, интеграционный факт или решение |
| `confidence` | `direct`, `correlated`, `inferred`, `asserted` |
| `confirmed_at`, `confirmed_by` | аудит подтверждения |
| `created_at`, `created_by` | аудит создания |
| `supersedes_affiliation_id` | исправляемая предыдущая связь |

`relationship_kind = member` используется только если источник действительно
подтверждает организационную принадлежность. Совместная работа на объекте создаёт
только `proposed + inferred`, а не `confirmed + member`.

### `fm2_case_organization_roles`

Отдельно хранит участие организации в монтажном деле.

| Поле | Назначение |
|---|---|
| `installation_case_id` | монтажное дело |
| `organization_id` | организация |
| `role` | `general_contractor`, `contractor`, `subcontractor`, `installation_organization` |
| `valid_from`, `valid_to` | период роли |
| `basis_type`, `basis_ref` | договор/письмо/импортированный источник |
| `status` | `proposed`, `confirmed`, `superseded` |
| `source_snapshot_id` | происхождение |

Это позволяет одной организации иметь разные роли в разных делах и не смешивает
роль на объекте с принадлежностью людей.

### `fm2_affiliation_candidates`

Проекция для миграционной сверки; не источник истины.

| Поле | Назначение |
|---|---|
| `installer_tab_id`, `organization_id` | кандидат связи |
| `observed_from`, `observed_to` | диапазон совместных объектов/работ |
| `installation_case_count` | число объектов, поддерживающих гипотезу |
| `checklist_event_count` | число событий фактического вклада |
| `conflicting_organization_count` | сколько иных организаций видно в периоде |
| `evidence_summary_json` | объекты, даты и источники |
| `candidate_status` | `unreviewed`, `accepted`, `rejected`, `ambiguous` |

Принятие кандидата выполняется предметной командой и создаёт affiliation; строка
кандидата сама по себе нигде не показывается как факт.

## 4. Как получить первоначальные кандидаты

### Шаг 1. Нормализовать организации

1. Выгрузить все значения legacy-поля 7 с ID и написанием.
2. Собрать используемые значения `subsuplier` по объектам и историю изменений.
3. Отдельно исследовать смысл организаций в скобках и `generalcontractor`.
4. Сопоставлять автоматически только по устойчивому внешнему ID или ИНН/КПП.
5. Совпадения только по нормализованному названию отправлять на ручную сверку.

### Шаг 2. Построить наблюдения монтажника

Для каждого объекта сформировать интервалы:

- когда организация выполняла роль на объекте;
- когда монтажник был назначен на объект;
- когда монтажник имел подтверждённые пункты чек-листа.

Пересечение интервалов создаёт наблюдение `installer + organization + case +
period`.

### Шаг 3. Агрегировать гипотезы

Кандидат считается сильнее, если:

- одна и та же пара повторяется на нескольких объектах;
- есть фактические события чек-листа, а не только текущий слот объекта;
- в тот же период не встречаются другие организации;
- источник подрядчика и даты назначения исторически определены.

Но даже десять совместных объектов остаются корреляцией. Для автоматического
подтверждения нужен прямой организационный источник: кадровая интеграция,
договорный реестр, утверждённый список бригад или ручное решение владельца данных.

### Шаг 4. Сверить с владельцем данных

Рабочая ведомость должна показывать:

- монтажника и табельный номер;
- предлагаемые организации;
- объекты и периоды, из которых сделан вывод;
- конфликты и разрывы;
- возможные дубли организаций;
- действие «подтвердить», «отклонить», «указать другую организацию», «оставить
  неизвестным».

## 5. Карточка монтажника

Карточка отвечает на вопрос «с какой организацией человек связан сейчас и как
это известно?».

Минимальное представление:

- текущая основная монтажная организация;
- вид связи и период;
- источник, свежесть и статус подтверждения;
- прошлая история организаций;
- параллельные связи и конфликты;
- текущие и исторические назначения на объекты;
- действие изменения принадлежности только через новую датированную запись.

Если подтверждённой связи нет, карточка показывает «Организация не установлена».
Предлагаемый legacy-кандидат отображается отдельно и не маскируется под факт.

## 6. Карточка монтажной организации

Минимальное представление:

- юридические реквизиты, алиасы и источник;
- роль и статус организации;
- действующие монтажники;
- бывшие монтажники с периодами;
- предложенные, но не подтверждённые кандидаты;
- объекты, где организация участвует, с ролью и периодом;
- конфликты: монтажник одновременно основной в нескольких организациях,
  неизвестные периоды, дубли организации.

Список монтажников строится из действующих `confirmed`-принадлежностей, а не
хранится массивом внутри организации.

## 7. Команды и права

Предлагаемый модуль `OrganizationDirectory` предоставляет намерения, а не CRUD:

```text
registerOrganization(requisites, source, actorId)
mergeOrganizationAlias(aliasId, organizationId, reason, actorId)
proposeInstallerAffiliation(installerTabId, organizationId, period, evidence, actorId)
confirmInstallerAffiliation(affiliationId, actorId)
rejectInstallerAffiliation(affiliationId, reason, actorId)
changeInstallerAffiliation(installerTabId, newOrganizationId, effectiveDate, basis, actorId)
assignOrganizationRoleToCase(caseId, organizationId, role, period, basis, actorId)
getInstallerOrganizationHistory(installerTabId)
getOrganizationInstallers(organizationId, asOfDate)
```

Рекомендуемые capabilities:

- `organization_directory.read`;
- `organization_directory.manage`;
- `installer_affiliation.propose`;
- `installer_affiliation.confirm`.

Технический администратор не получает право предметного подтверждения
автоматически. Для массовой миграции желательно разделить подготовку кандидата и
подтверждение.

## 8. Инварианты

1. Монтажник и организация существуют независимо от их связи.
2. Связь всегда имеет период, источник и статус доказательности.
3. Изменение организации закрывает старую связь и создаёт новую; история не
   переписывается.
4. Одновременно может существовать несколько связей, но не более одной
   подтверждённой основной связи без зафиксированного конфликта/исключения.
5. Участие на одном объекте не подтверждает постоянную принадлежность.
6. Название организации не является уникальной юридической идентичностью.
7. Роль субподрядчика относится к монтажному делу/договору, а не является
   вечным типом организации.
8. Удаление/деактивация организации не изменяет исторические назначения,
   документы и расчёты.
9. Распоряжение сохраняет снимок организации и состава, использованный при
   выпуске.
10. Неизвестная организация хранится как отсутствие подтверждённой связи, а не
    как специальная организация «Не выбрано».

## 9. Сценарии, проверяющие модель

### Переход монтажника

Иванов до 31.03 относится к ООО «А», с 01.04 — к ООО «Б». Старые объекты и
распоряжения продолжают показывать «А», новые — «Б».

### Разовое привлечение

Иванов принадлежит «А», но на одном объекте привлечён организацией «Б».
Принадлежность остаётся «А»; отдельная связь с «Б» имеет вид `engaged` и период
конкретной работы.

### Два подрядчика на объекте

На объекте последовательно работали «А» и «Б». Текущее поле legacy содержит
только «Б». Без истории поля нельзя приписать всех ранних монтажников «Б».

### Дубли названий

`ООО Монтаж`, `ООО «Монтаж»` и `Монтаж ООО` могут быть одной организацией, но
до ИНН/КПП или ручного решения остаются отдельными кандидатами.

### Прямой сотрудник ШЛЗ

Если монтажник не относится к субподрядчику, это не «неизвестно». Для него может
быть подтверждена принадлежность к собственной монтажной организации либо явно
зафиксирован вид связи, согласованный владельцем процесса.

## 10. Рекомендуемая последовательность внедрения

1. Выполнить read-only профилирование legacy-значений подрядчика и их дублей.
2. Найти нормативный первоисточник организаций и принадлежности людей.
3. Утвердить термины, виды связи и владельца подтверждения.
4. Создать справочник организаций и алиасы.
5. Импортировать организации без создания подтверждённых принадлежностей.
6. Построить кандидатов по объектам и чек-листам.
7. Проверить выборку конфликтных и однозначных случаев с владельцем данных.
8. После этого реализовать карточки и штатное управление датированными связями.

## 11. Предлагаемые SSD/TDD-срезы

После продуктового согласования:

1. `ORGANIZATION-DIRECTORY-001` — регистрация организации с устойчивыми
   реквизитами и защитой от дубля внешнего ключа;
2. `ORGANIZATION-ALIAS-001` — ручное сопоставление legacy-алиаса;
3. `INSTALLER-AFFILIATION-001` — подтверждённая датированная принадлежность;
4. `INSTALLER-AFFILIATION-CHANGE-001` — переход без переписывания истории;
5. `INSTALLER-AFFILIATION-CONFLICT-001` — конфликт основных связей;
6. `CASE-ORGANIZATION-ROLE-001` — роль организации в монтажном деле;
7. `AFFILIATION-CANDIDATE-001` — legacy-наблюдение создаёт только кандидата;
8. `INSTALLER-CARD-ORGANIZATION-001` — организация и история в карточке
   монтажника;
9. `ORGANIZATION-CARD-INSTALLERS-001` — монтажники на выбранную дату в карточке
   организации.

Каждый срез проходит обязательные Gate 1–5 из `docs/development-process.md`.

## 12. Что необходимо выяснить до утверждения

1. Где существует прямой источник связи: ЗУП, Bitrix, договорный реестр,
   таблица ФКР или документы субподряда?
2. Что означает организация в скобках поля `subsuplier`: вышестоящего
   субподрядчика, заказчика работ или иную сторону цепочки?
3. Может ли монтажник одновременно работать через несколько организаций?
4. Нужно ли различать трудоустройство, членство в бригаде и разовое привлечение?
5. Кто является владельцем справочника и подтверждает принадлежность?
6. Какие реквизиты обязательны: ИНН, КПП, внешний ID, полное наименование?
7. Нужно ли показывать только действующих монтажников или также бывших и
   предложенных кандидатов?

До получения прямого источника мы можем уверенно построить справочники и
кандидатов сопоставления, но не можем автоматически получить достоверный
справочник принадлежности монтажников к субподрядчикам.
