## 1. Итоговое заключение

FMonitor 2.0 — не одноразовый прототип, который следует выбросить, но и не завершённая промышленная платформа. В репозитории соседствуют достаточно тщательно спроектированные предметные операции и пилотный код, который одновременно обслуживает HTTP, читает и изменяет БД, рассчитывает суммы и формирует HTML.

Главная архитектурная проблема — **не размер репозитория и не PHP, а неравномерность гарантий и несколько мест владения одним пользовательским процессом**. Сильные гарантии оригиналов распоряжений пока нельзя автоматически переносить на ОТиЗ, календарь, развёртывание или восстановление. [S13–S21, S28–S29]

Рекомендация: сохранить PHP, MariaDB, серверный HTML и shlz-ui; довести систему до модульного монолита посредством законченных пользовательских операций. Сначала исправить риски целостности ОТиЗ и блокирующие сценарии пользователя, затем убрать пилотные эксплуатационные зависимости. Полное переписывание, обязательная SPA, микросервисы и брокер сообщений из проверенного состояния не следуют.

### Область достоверности

Это не построчный аудит каждого файла, не пентест и не доказательство отсутствия других дефектов. Обнаруженные сценарии сбоев не означают, что повреждение реальных данных уже произошло.

## 3. Фактическая архитектура

```text
Браузер: серверный HTML + shlz-ui + клиентский JS / IndexedDB / service worker
  → Compose pilot
    → docker-entrypoint: сетевые переходники + миграции + bootstrap
      → start.php: manifest пилота + встроенный PHP HTTP server
        → rapid-pilot/router.php
          → прямые обработчики пилота: ОТиЗ, календарь, планирование и др.
          → основная HTTP composition → предметные операции / адаптеры
          → последующая переделка готового HTML обработчиками пилота

MariaDB + постоянное закрытое файловое хранилище
Отдельный workforce worker из того же образа, но с зависимостью от manifest
```

Это одна система, но ещё не единая цепочка ответственности. Основной HTTP factory зависит от `rapid-pilot/LocalAuth.php`; router после исполнения основного приложения дополняет и изменяет его HTML. При изменении разметки можно затронуть поведение другого слоя, хотя предметная операция не менялась. [S10–S14]

Полезные решения, которые нужно сохранить: предметные проверки оригинала, явная авторизация, обработка повторов и неопределённого исхода сохранения; отделённое хранилище документов; целочисленные денежные величины и трасса расчёта; ролевые разрешения активных пользователей; локальная очередь чек-листа с идентификаторами операций и ревизиями; закреплённые зависимости и независимые CI категории. Ни один из этих плюсов не является общей сертификацией всех контуров. [S15, S17, S20, S24–S27, S04, S08]

## 4. Находки

Приоритет P1 означает исправление до использования затронутого контура как достоверного источника или до промышленного запуска; P2 — существенный долг следующего этапа. Приоритет не является оценкой CVSS. «Статически подтверждено» означает проверенную структуру кода; сценарий сбоя ещё требует исполняемого регрессионного теста.

### A01 · P1 · Неполный расчёт ОТиЗ может остаться доступным для принятия

**Основание:** `rapid-pilot/Otiz.php`, `calculate()` и обработчик принятия среза; `PilotOtizSchemaMigration.php`. [S18–S19]

`calculate()` сначала вставляет `draft` с нулевыми итогами и `content_hash='pending'`, затем получает входные данные и по частям записывает объекты, распределения и замечания. Общей транзакции вокруг этой последовательности нет. Итоговый hash и суммы обновляются в конце. Обработчик принятия проверяет наличие draft и отсутствие открытых blockers, но не завершённость построения, количество ожидаемых строк или финальный hash.

В стандартном режиме MariaDB отдельные изменения фиксируются автоматически; ошибка после первой вставки или посередине цикла оставляет частичный draft. Наличие InnoDB само по себе не делает всю прикладную последовательность одной транзакцией. [S39]

**Последствие:** неполный срез может пройти существующие условия принятия. Фактическое наличие таких срезов в пользовательской БД не установлено.

**Исправление:** атомарное построение/публикация среза либо явные состояния `building → ready → accepted`, недоступность промежуточного результата для принятия, проверка полноты и версии входных данных. Способ выбрать по измеренной длительности расчёта; не держать долгую глобальную блокировку без необходимости.

**Приёмка:** контролируемый сбой после создания среза, после первого объекта и перед публикацией не оставляет принимаемого неполного результата. Повторное исполнение не создаёт противоречивых срезов.

### A02 · P1 · Защита от повторной фиксации выплаты ограничена одним срезом

**Основание:** обработчик `payments/complete`, расчёт прошлых выплат и схема `fm2_pilot_otiz_payment_closures`. [S18–S20]

При завершении выплат блокируются текущий snapshot и его строки; уже закрытая сумма проверяется по `snapshot_id` и объекту. При этом исходный расчёт учитывал выплаты на момент создания среза. В проверенном пути завершения нет повторной проверки общего актуального остатка объекта через все срезы.

**Статический сценарий:** два среза одного объекта подготовлены до фиксации выплаты; оба содержат один доступный остаток. Выплата записана по первому, после чего завершение второго не видит её в своём snapshot. Схема не содержит уникальности, запрещающей два принятых среза на дату; имеющийся уникальный ключ относится к сторнированию.

**Последствие:** повторная фиксация выплаты или завышение учтённого погашения. Это не утверждение, что приложение автоматически отправит реальные деньги.

**Исправление:** единый владелец финансового остатка объекта; блокировка или версия именно финансового основания; повторная проверка актуального остатка при фиксации; явное устаревание/замещение среза; идемпотентность бизнес-операции, а не только HTTP-действия внутри snapshot. Старую историю не пересчитывать и не удалять автоматически.

**Приёмка:** два заранее созданных среза, последовательное и параллельное завершение, повтор запроса после потери ответа, сторнирование и позднее исправление. Ни один сценарий не увеличивает суммарную допустимую выплату из-за повтора.

### A03 · P1 для достоверности сумм · Остаток от округления распределений не отражён

**Основание:** цикл распределений в `calculate()` ОТиЗ и `PremiumCalculation`. [S18, S20]

Сумма отдельного монтажника рассчитывается через `intdiv(distributed * weight, sumWeights)`. При этом `distributed` записывается до суммирования фактических строк, а `undistributed` вычисляется как pool минус исходный distributed. Отдельной компенсации остатка в этом цикле нет.

Например, 100 копеек на три равных веса дают 33 + 33 + 33 = 99, хотя исходно распределяемая сумма равна 100. Это арифметический пример обнаруженного алгоритма, не результат теста на реальной БД.

**Исправление:** утвердить правило округления и судьбу остатка. Возможны детерминированное распределение остатка или его явный учёт как нераспределённого. Обязательный инвариант: сумма строк + явный остаток = распределяемый фонд. Не менять уже принятые исторические расчёты без отдельного правила исправления.

### A04 · P1 до разделения runtime-прав · DDL достижим из HTTP, но исключён из checker

**Основание:** конструктор ОТиЗ вызывает ledgers из `rapid-pilot/legacy-migration`; `MigratedEvidenceDecisionLedger::ensureSchema()` выполняет `CREATE TABLE IF NOT EXISTS` и вызывает создание схемы projection store. Checker исключает `legacy-migration`. [S18, S21–S23]

Собственный bootstrap ОТиЗ уже проверяет readiness — приписывать ему оставшийся DDL было бы неверно. Дефект находится в вызываемом migration tooling. Документальное объяснение исключения каталога «не runtime» расходится с фактической достижимостью.

**Последствие:** веб-пользователь БД всё ещё связан с DDL; отсутствие миграции может скрываться до первого запроса; зелёный checker не контролирует именно этот путь.

**Исправление:** вынести DDL в канонические миграции, runtime readers оставить в прикладных/инфраструктурных модулях, дать HTTP и worker учётные записи без DDL после подготовки схемы. Расширить проверку на фактически используемые зависимости. Не перегенерировать baseline ради зелёного результата.

**Приёмка:** обычный запрос ОТиЗ работает без CREATE/ALTER/DROP; неприменённая схема даёт ясную readiness-ошибку; миграция выполняется отдельно; regression test защищает достижимость исключённых каталогов. Уже относится к #24/#32, а не требует второго архитектурного эпика.

### A05 · P2, структурно высокий · Несколько владельцев поведения и чрезмерно широкие обработчики

**Основание:** router, HTTP factory, ОТиЗ, календарь и планирование. [S13–S14, S18, S28–S29]

ОТиЗ объединяет доступ, SQL, транзакции, расчёт, HTML и XLSX. Планирование пишет предметные данные непосредственно из HTTP-обработчика и переставляет уже сформированные строки HTML. Основной factory использует пилотную авторизацию. В `InstallationProcess` зависимость задана широким `object $environment`, что оставляет часть контракта неявной. [S16]

**Последствие:** изменения затрагивают несколько слоёв и неодинаковые маршруты, тесты вынуждены учитывать устройство временных обёрток, постепенное удаление пилота становится труднее.

**Исправление:** #32 фиксирует владельцев и границы транзакций; #24 переносит одну законченную операцию и удаляет заменённый путь. Не начинать с массового переименования каталогов или создания интерфейса на каждый низкоуровневый вызов. Форматирование и содержательные типы важнее прохождения лимита в 150 строк сжатым кодом.

### A06 · P1 до production · Runtime остаётся демонстрационным

**Основание:** entrypoint запускает socat, миграции и bootstrap; `start.php` требует manifest/generation и запускает `php -S` с четырьмя workers. [S09–S11]

PHP прямо не рекомендует встроенный сервер для production. Четыре workers не превращают его в промышленный сервер. При этом опубликованный Compose привязывает порт к loopback; отсюда не следует, что пользовательский стенд сейчас открыт в интернет. [S38, S09]

**Исправление:** #33 — штатный HTTP runtime, например web server + PHP-FPM, прямое подключение к БД, явная конфигурация, одна версия web/CLI, отдельный deployment step миграций с блокировкой конкурентного запуска. Сохранить пути/volumes и проверить переключение без сброса данных.

**Приёмка:** restart, недоступная БД, завершение процессов, PDF/фото, auth/session под HTTPS/reverse proxy, корректные cookie и доверенные заголовки. Контейнер не должен требовать пилотного manifest для определения производственной конфигурации.

### A07 · P1 для достоверности интеграций · Здоровье worker не означает свежие данные

**Основание:** worker создаёт ready-файл после успеха, но не удаляет его после последующих ошибок; Compose проверяет только существование этого файла. Worker запускается от root и получает prefix из pilot manifest. [S09, S12]

**Последствие:** после первой удачной синхронизации контейнер может оставаться healthy при последующих отказах. Это маскирует устаревший кадровый справочник. Фактическая длительная остановка синхронизации на пользовательском стенде не устанавливалась.

**Исправление:** раздельно учитывать жизнь процесса, последнюю попытку, последний успех, ошибку и допустимый возраст данных; не сводить внешний outage к бесконечным автоматическим рестартам. Убрать необоснованный root. Быструю диагностику существующего sync не откладывать до полной #34. Общий механизм исполнения — #34, операторский экран — #30, конфигурация — #42/#33.

### A08 · P1 перед ростом объёма · Пагинация и пределы календаря

**ОТиЗ:** основной список делает выборку без LIMIT, затем `fetch_all`, дополнительное чтение прогресса для всех ID и формирование строк. В просмотре среза есть запросы закрытий внутри цикла по объектам. Это подтверждённая актуальность #17, а не только жалоба из старого аудита. [S18]

**Календарь:** загружает период от 30 дней назад до шести месяцев вперёд. Для источника установлен предел 5 000 строк; выборка делает LIMIT 5 001, а превышение вызывает exception и HTTP 503. Это лучше скрытого обрезания данных, но не решение масштабирования. [S28]

**Исправление:** специализированные SQL-модели чтения, фильтр доступа и поиска до LIMIT, стабильный порядок, ограниченная страница/диапазон календаря. Итоги рассчитывать по всему отфильтрованному набору отдельным запросом, а не суммой видимой страницы. Массовый экспорт отделить от интерактивного списка; не запускать построчно весь предметный процесс для чтения.

**Приёмка:** репрезентативные 10/50 тысяч объектов в изолированном контуре, p50/p95, число запросов, память, объём HTML/JSON, EXPLAIN, стоимость COUNT отдельно. Это предлагаемый испытательный набор, а не измеренная текущая производительность.

### A09 · P2, риск при обновлении · Сложный frontend без ясной границы source/build

**Основание:** `checklist.js` непосредственно содержит минифицированную модель, работу с IndexedDB, очередь запросов, обработку конфликтов и DOM. Service worker управляет поколениями кэша и пользовательскими документами; IndexedDB имеет собственную версию. [S26–S27]

Уже есть полезные гарантии: scope операций включает пользователя/устройство/объект; операции имеют UUID и ревизии; документы кэша различаются по пользователю. Не следует уничтожать это переписыванием экрана ради framework.

**Исправление:** #35 — читаемые исходники, воспроизводимый build, отделённые model/storage/sync/view; явная совместимость версий клиента и сервера. Сначала определить сохранность уже существующих offline-операций и фото, затем решать, нужен ли точечный Vue. Полная SPA не является необходимым результатом.

**Приёмка:** обновление с непустой очередью, offline → online, потеря ответа и повтор, конфликт ревизий, смена пользователя, неуспешная миграция локального хранилища. Обнаруженная связанность не доказывает, что эти данные уже терялись.

### A10 · P1 для доверенной поставки · CI успешен, но обязательность и интеграционный контекст не закреплены

**Основание:** API main сообщает `protected=false`, required checks отключены; доступный список rulesets пуст. Workflow проверяет PR head, а не синтетический результат объединения с актуальной base; push-trigger отсутствует. [S05, S36–S37]

Это не опровергает успешный CI текущего дерева. Риск относится к последующим поставкам: при параллельных ветках или ручном обходе нет подтверждённого технического запрета попадания непроверенной комбинации в main.

**Исправление:** отдельное решение владельца о required check, актуальности base, допустимых bypass и проверке фактически интегрируемого дерева. Не включать защиту автоматически в рамках аудита и не смешивать разрешения publisher с обычным запуском тестов. Согласовать #37 с уже поставленной матрицей, не возвращая постоянное двойное исполнение полного harness.

### A11 · P2, до пользовательского запуска — предметные дефекты · Доступ, закрепления и приглашения требуют общей модели

**Основание:** #38–40, #45–46; роль проверяется через AccessPolicy, но отдельные экраны/действия сами выбирают данные. Например, календарная выборка не принимает user/scope; планирование проверяет `inspection.schedule`, но не содержит сравнения автора с закреплённым инженером. [S24, S28–S29, S35]

Это точка обязательной сверки политики, а не доказанная здесь утечка: текущая роль может намеренно иметь общий доступ. Для #14/#45 нужно явно определить и проверить доступ к конкретному объекту, а не ограничиться разрешением открыть раздел.

Различать: актуальное операционное закрепление; состав подтверждённого распоряжения; право читать объект; право выполнить действие; попадание в рабочую очередь. #40 показывает важное различие — инженер должен видеть готовый объект ещё до открытия, поскольку именно он его открывает.

Для #46 предпочтительна явная операция перевыпуска с отзывом прежнего токена. Текущая активация ищет приглашение по hash; возвращать возможность работы администратора хранением всех ссылок открытым текстом не следует. Проверить гонку принятия старого приглашения с перевыпуском и сохранение ролей/идентичности пользователя. [S25]

### A12 · P1 до production / P2 для документации · Восстановление и текущий статус не доказаны одним GREEN

#36 остаётся задачей на согласованное восстановление БД, PDF/фото и истории. В просмотренных материалах не найдено достаточного выполненного restore drill для текущего релизного кандидата. Это не утверждение об отсутствии любых backup-файлов.

## 5. Безопасность и тестирование: что можно и чего нельзя заключить

В просмотренном коде есть серверные ролевые проверки активных пользователей, CSRF для ключевых операций, хеширование паролей/приглашений, HttpOnly/SameSite cookie, отделённое файловое хранилище документов и обработка недоступности session storage. Это хорошие механизмы, но не доказательство полного соответствия безопасности. [S15, S24–S25]

Не проверялись на реальном окружении сетевой периметр, TLS/proxy, все object-level authorization, полный жизненный цикл сессий, антивирусная обработка загрузок, восстановление, уязвимости всех транзитивных зависимостей и инфраструктурные секреты. Пилотные значения конфигурации нельзя автоматически называть утёкшими production-секретами.

Текущий CI содержит полезные функциональные и интеграционные проверки. Нельзя из числа scripts или literal VERIFY_OK выводить процент покрытия, отсутствие денежных дефектов или готовность восстановления. PHP syntax check — не type analysis. В текущей матрице PHPStan и систематическая source-mutation проверка описаны как будущие ограниченные эксперименты, не как уже работающая защита. [S04]

Рекомендуемый новый набор регрессий сосредоточить на A01–A03, рабочем маршруте #40, приглашениях #46, запрете runtime DDL, свежести worker, непротиворечивости разных представлений одного объекта и upgrade с offline-очередью. Не возвращать многократный полный harness после каждой маленькой правки.

## 7. Чего не хватает в бэклоге

Общие #24 и #29 затрагивают ОТиЗ, но не заменяют явных задач на новые нарушения инвариантов. Предлагаются три самостоятельных исправления:

| Атомарное построение и публикация среза ОТиЗ | Failure injection в трёх фазах; неполный срез неприменим; безопасный повтор | Не менять формулу и не переносить весь модуль заодно |

## 8. Рекомендуемая целевая архитектура

**Топология:** web server с HTTPS/статикой → PHP HTTP; отдельные CLI worker/scheduler из того же source/image; MariaDB; закрытое хранилище PDF/фото. Миграции — отдельная команда этапа развёртывания. Frontend собирается в ресурсы, постоянный Node-сервис не требуется. Конкретный HTTP server и механизм запуска scheduler принять в #32.

**Модули по владельцам фактов, а не по техническим слоям всего репозитория:**

| Область | Ответственность |
|---|---|
| Монтажное дело / распоряжения | Состав, оригинал, применение, фактическое открытие и процессные переходы |
| Инспекции | План, факты выполнения, материалы и исправления; план не становится фактом автоматически |
| Завершение / документы | Основания документального закрытия; допустимо оставить внутри монтажного модуля, если граница окажется искусственной |
| ОТиЗ | Входные основания расчёта, срез, принятие, распределение, финансовые записи/сторно |
| Доступ и пользователи | Роли, полномочия, приглашения, сессии; идентичность пользователя не равна кадровому монтажнику |
| Кадровые и внешние сведения | Синхронизация, нормализованные факты источников, соответствия, provenance и свежесть |
| Уведомления | Намерения доставки, шаблоны и транспорт; не владеет состоянием монтажа |

Внутри модуля: HTTP/CLI вызывает прикладную операцию; предметные правила не знают о разметке; SQL, файловое хранилище и внешние сервисы находятся в адаптерах. Межмодульные записи идут через владельца факта. Для списков допустимы прямые специализированные SQL JOIN-модели чтения — не нужно загружать полный предметный агрегат для каждой строки.

Одна БД допустима. Очередь в MariaDB — соразмерная начальная рекомендация, а не уже принятое ADR. Задание имеет тип/версию payload, доступность по времени, lease, попытки и терминальный результат. Намерение событийного уведомления сохраняется вместе с предметным изменением; сеть вызывается после commit. Для email не обещать безусловное exactly-once при сбое между принятием письма провайдером и локальным подтверждением.

Не требуются без отдельного доказательства: микросервисы, полное event sourcing, универсальная платформа интеграций, отдельный framework для каждого модуля, новый интерфейс на каждый вызов `fclose`, полный переход в SPA или массовая смена структуры каталогов.

#34/#30 дают общий механизм заданий и наблюдаемость; затем #12/#15 и потребители #13/#11/#16. #14/#45, минимальный #21 и #31 можно делать раньше независимо, когда их предметные источники и scope уже определены. #35 ведётся отдельным потоком после фиксации offline-контракта. #26 проверяет фактическую масштабируемость готовых моделей чтения. #19/#28 развиваются по пользовательским сценариям, не как техническое переписывание.

Порядок задаёт зависимости, а не календарные сроки. Не нужно ждать закрытия всего #18 для очередного полезного пользовательского инкремента.

## 10. Условия промышленной готовности

Заключение о production-ready требует отдельного доказательства: рабочий пользовательский путь и роли; исправленные денежные инварианты; отсутствие runtime DDL; промышленный HTTP runtime и актуальное здоровье worker; подтверждённое согласованное восстановление; проверенная доставка exact tree/image с понятным gate; выдержанный репрезентативный объём данных; совместимость обновления с offline-очередью. Сейчас часть этих гарантий поставлена, часть относится к открытому бэклогу, часть не проверена на рабочем окружении.

**Главный управленческий вывод:** не начинать ещё одну глобальную перестройку и не измерять прогресс количеством gates, классов или строк. Ближайший результат должен быть понятен пользователю: объект виден нужному инженеру до открытия, приглашение можно безопасно перевыпустить, расчёт нельзя принять недостроенным, а одна и та же сумма не фиксируется повторно через другой срез. Затем эти законченные сценарии закрепляются за единственными владельцами и получают надёжный runtime.
