## Подтверждённые решения

### Контур пилота

- Используются уже загруженные, ещё не открытые заказы с плановым началом с 1 октября 2026 года.
- Один заказ — одно распоряжение. Пакетный выпуск в пилот не входит, хотя исторические документы могли быть многообъектными.
- Официальный расчёт премии, полноценные инспекции и автоматическая интеграция с 1С ДО не входят в первый инкремент.

### Основной пользователь

Сотрудник ФКР:

1. Смотрит компактную очередь заказов по плановой дате.
2. Открывает один заказ.
3. Выбирает одного или нескольких монтажников.
4. Выбирает одного инженера строительного контроля.
5. Формирует распоряжение.
6. Относит файл в 1С ДО.
7. Возвращает в FMonitor присвоенный номер.
8. Отдельной командой открывает заказ и указывает фактическую дату начала.

### Люди

- Монтажники выбираются только из полного каталога `ЗУП → Битрикс → FMonitor`.
- Ручное создание монтажника и свободный ввод ФИО запрещены.
- Инженеры строительного контроля уже заведены как пользователи FMonitor.
- Инженер выбирается только среди активных пользователей соответствующей роли.
- Поле `responsstroicontrol` существует в legacy и может предзаполнить инженера, но выбор нужно подтвердить.
- Один монтажник означает индивидуальную форму труда, несколько — бригадную; отдельного переключателя нет.

### Распоряжение и даты

- FMonitor фиксирует неизменяемую дату распоряжения при формировании документа.
- 1С ДО присваивает только номер; сотрудник вручную вводит его в FMonitor.
- Состав, инженер и дата сформированной версии не редактируются молча.
- Изменение состава или инженера создаёт новую версию/изменяющее распоряжение.
- Формирование документа не открывает заказ и не разблокирует чек-лист.
- Сотрудник ФКР отдельно нажимает обычную компактную кнопку открытия заказа.
- При открытии он указывает фактическую дату начала.
- Фактическая дата начала не может быть раньше даты распоряжения или позже текущей даты.
- В пилоте заказ можно открыть до получения номера 1С ДО; отсутствие номера остаётся явной задачей и блокером окончательного расчёта.

### UX

- Штатный пользователь не работает в широкой Excel-подобной таблице.
- Основная навигация функциональная: «Моя работа», «Объекты монтажа», «Распоряжения», «Инспекции», «Монтажники», «Расчёты», «Нарушения».
- Для пилота главный экран ФКР — очередь заказов, требующих действия.
- Таблица допустима только как компактный список поиска/очередь без inline-editing.
- Действия имеют стандартный размер `shlz-ui`; process-driven означает правильное действие в правильном состоянии, а не гигантские CTA.
- `shlz-ui` находится в `../shlz-ui` и GitHub `Antropophag/shlz-ui`. Для PHP подходят `@shlz/styles` и progressive-enhancement `@shlz/behaviors`.

## Техническая рекомендация

Выбран вариант «модульный монолит рядом с legacy»:

- новый глубокий модуль `InstallationProcess` владеет распоряжениями, назначениями, открытием и задачами;
- UI, cron и интеграции вызывают один процессный интерфейс;
- `fm_maintable` временно остаётся источником идентификационных данных заказа и совместимой read-only проекцией;
- `installator..installator4` не считаются достоверной историей;
- каскадное переписывание исторических исполнителей чек-листа должно прекратиться после перехода заказа под управление FMonitor 2.0.

## Следующая работа

Спроектировать экранный поток без кода:

1. Очередь заказов сотрудника ФКР.
2. Карточка заказа.
3. Мастер формирования распоряжения.
4. Диалог внесения номера 1С ДО.
5. Диалог открытия заказа с фактической датой.
6. Справочник и карточка монтажника.
7. Очередь выбранного инженера.
8. Очередь руководителя по просрочкам.

Для каждого экрана определить: роль, задача, входное состояние, минимальные данные, команды, блокировки, успешный результат и переход. Использовать реальные примитивы `shlz-ui`, проверив `../shlz-ui/docs/component-taxonomy.md` и package exports. Не выбирать визуальный мир и не писать UI-код до подтверждения структуры пользователем.

## Открытые вопросы

Поднимать по одному, только когда блокируют текущий экран:

- Нужен ли обязательный финальный файл из 1С ДО или достаточно номера?
- Кто и каким процессом исправляет ошибочно введённый номер?
- Кто именно нажимает открытие заказа, если сотрудник, сформировавший распоряжение, отсутствует?
- Какой конкретный шаблон должен генерироваться для однообъектного распоряжения: адаптация исторического № 12-Р или форма из Положения № 178?
- Какие роли видят расчётные сведения в карточке монтажника?
