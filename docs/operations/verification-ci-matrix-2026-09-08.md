# Матрица проверок #25

Матрица явно принята владельцем 2026-09-08 в текущей сессии. Основная полная команда по отдельному решению владельца — `make test`.

| Изменение / событие | Локально | GitHub |
|---|---|---|
| README и текстовые docs, кроме architecture и development-process | Затронутая проверка | Fast; полный набор явно skipped с reason=docs-only |
| Код, тесты, конфигурация, CI, specs, OpenSpec, policy, неизвестные пути | Focused test / категория | Fast и весь набор категорий один раз |
| Пустой diff, отсутствующая base, ошибка определения влияния | Focused при возможности | Консервативный full |
| Schedule, workflow_dispatch, release | По задаче | Full |

Fast защищает syntax, architecture, корректность каталога и selection/aggregation. Категории — unit, integration, e2e, governance. Каждая имеет явный состав; ни один тест не классифицируется поиском строк в исходниках. Изменение mapping проходит review как изменение проверочной композиции.

Integration и E2E исполняются на отдельных GitHub VM, со своими MariaDB, портами и файлами. Внутри job тесты последовательны. Одинаковый номер порта на разных VM не означает общую БД. Always teardown сохраняется после отказов. Unit/governance используют только необходимые зависимости; тяжёлый ci-setup не размножается во все jobs.

Итоговый job `verify` сохраняет имя для существующих потребителей, но не повторяет тесты. Он проверяет ожидаемые результаты всех jobs: отсутствие/failure/cancelled/неожиданный skipped не могут дать успех. `VERIFY_OK` означает полный набор; `DOCS_VERIFY_OK` — только явно согласованный docs-only путь. Исторические маркеры сохраняются, основное имя команды — test.

Полный local test → полный CI не является обязательной последовательностью. Для обычного PR локальные focused proofs и независимый review предшествуют одному авторитетному CI. При выпуске без GitHub или проверке локального окружения используется `make test`/`make fresh-test`. Изменение самой матрицы, checker, тестов или неизвестная область всегда требует full CI. Merge/release ready нельзя объявлять по одним быстрым проверкам, если выбран full.

Когда эта ветка интегрируется, QG должен ссылаться на те же fast/category/aggregate команды и evidence exact head; второй параллельный полный harness удаляется только после проверки parity. Нельзя обновить unmerged QG в main добавлением другого скрытого runner. Эта матрица — согласованный контракт интеграции, не ложное заявление уже выполненного merge PR37.

## Оценка дополнительных анализаторов

PHP syntax check не является type/static analysis. Следующий кандидат — ограниченный PHPStan pilot на одном предметном модуле с явной автозагрузкой, числом полезных findings и измеренным временем. [PHPStan позволяет выбирать уровни и применять baseline](https://phpstan.org/user-guide/rule-levels); автоматическая генерация подавлений ради GREEN здесь не разрешается. Решение включать в каждый PR принимается после измерения полезных ошибок и бюджета, без миграции всего проекта в этом PR.

Infection не включается автоматически в каждый PR: [он требует поддерживаемый test framework и coverage runtime](https://infection.github.io/guide/), тогда как здесь самостоятельные PHP scripts. Сначала нужен небольшой adapter/pilot на чистом модуле и оценка выживших мутантов; частота — отдельный scheduled/manual эксперимент. [Большие функциональные наборы могут занимать часы и требуют изоляции процессов/БД](https://infection.github.io/guide/how-to.html). Fixture corruption tests проекта не называются mutation testing production source.

## Архитектурные guardrails

Текущие 7 ratchet rules и baseline сохраняются. В аудите подтверждены runtime-вызовы migration ledgers из Otiz и зависимость native auth от rapid-pilot; исключённый каталог не доказывает недостижимость. Перенос этих owners — #32/#24, не скрытое ослабление checker в #25. Ограничение 150 строк не оправдывает сжатие кода: предложенные критерии следующего архитектурного review — связность операции, размер публичного интерфейса, число затрагиваемых callers, тестируемость через этот интерфейс. Baseline не перегенерируется без отдельного review.

## Измерения

До изменений: успешный PR41, [run34206732488](https://github.com/Antropophag/fmonitor-2/actions/runs/34206732488), один job 17м10с с setup. Full harness: unit около90с, DB около609с, characterization около33с, E2E около67с. В DB дополнительно исполнялись standalone E2E и пять bootstrap children. Это baseline успешного прогона с закреплёнными инструментами; прежние FAIL-измерения issue25 сохраняются исторически и не используются как положительная parity.

Итоговые durations, runner minutes, источники и бюджеты добавляются после нового Actions. Ускорение ожидания и изменение суммарной вычислительной стоимости считаются отдельно. Длительности разных GitHub VM естественно варьируются; это сравнение одинаковой конфигурации hosted runners, не одного физического сервера.
