# Имя пользователя в истории объекта — 7 сентября 2026

Владелец сообщил, что история карточки показывает техническую подпись вида
«Пользователь 1» вместо реального пользователя.

Read-only headless Playwright на объекте 966 подтвердил дефект установленного
стенда: найдена одна подпись автора, `legacyNumeric=true`, при этом HTTP- и
JavaScript-ошибок не было. Имена, email и другие персональные значения runner не
выводил. Проверка не выполняла изменяющих действий.

RED сфокусированного синтетического теста завершился с `exit 255`: события не
содержали `actorName`. После исправления тест завершился с `exit 0` и
`PASS object card resolves immutable historical actor names`.

`MariaDbAppliedObjectCardReader` теперь обогащает события всех проходящих через
него карточек одной batch-проекцией локальных пользователей по distinct immutable
`actorId`. Статус пользователя не фильтруется, поэтому имя заблокированного или
неактивного пользователя остаётся доступно для истории. Используется сохранённое
`full_name`, при пустом имени — сохранённый email. Если локальная запись
отсутствует, `actorName` остаётся `null`; `actorId` не меняется.

`ProductionObjectCardRenderer` выводит экранированный `actorName`. Для отсутствующей
локальной записи используется правдивая подпись «Пользователь недоступен · ID N».
Текущий вошедший пользователь не подставляется вместо исторического автора.
Исторические события и профили пользователей не изменяются.

Синтетический тест проверяет автора события, отличного от viewer, inactive/blocked
пользователя, HTML-sensitive имя, email fallback, отсутствующего пользователя,
сохранность actor IDs и отсутствие старой цифровой подписи. Все затронутые PHP-
файлы прошли lint и имеют mode 0644; `git diff --check` прошёл.

Private read-only runner:
`~/.local/state/fmonitor2/manual-pilot-20260907/runtime/object966-history-actor.cjs`.
Его GREEN на стенде ожидается только после независимого review и установки нового
exact-source candidate; текущий RED относится к ранее установленному `78182e1`.

## Карточка после принятого оригинала

Дополнительный browser feedback показал, что возврат после успешной загрузки
попадал в карточку с устаревшим предложением повторно загрузить распоряжение.
Reader теперь проецирует ещё не применённый accepted current original вместе с
точным выбранным составом, revision/download и каноническим статусом «Готов к
открытию». Проекция явно хранит `applicationId=null`; таблица applications и
opening facts чтением не изменяются.

По последнему решению владельца отдельный пользовательский шаг «Применить состав»
удалён. Для пользователя с `installation.open` карточка сразу показывает форму
«Открыть работы» и отправляет в новый атомарный command `open_confirmed` trusted
64-символьный CSRF, UUID request, exact order/revision, ожидаемую application
sequence и фактическую дату. Пользователь без полномочия видит принятый оригинал,
но не получает форму. GET ничего не применяет и не открывает; upload остаётся
чистой загрузкой. Сфокусированный тест подтвердил applications count 0, пустые
opening facts, точный документ/состав и полный набор полей формы без отдельного
apply CTA.
