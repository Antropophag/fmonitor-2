# Автоматическое заполнение округа и района по адресу

Дата исследования: 7 сентября 2026. Исследование основано только на публичной
документации; реальные адреса в сторонние сервисы не отправлялись, API и платные
методы не вызывались.

## Рекомендация для пилота

Для московских объектов заполнять два явно названных производных поля:

- **административный округ Москвы** — из `city_area`;
- **административный район Москвы** — из
  `divisions.administrative.city_district.name`, с fallback на `city_district`.

DaData прямо определяет `city_area` как административный округ только для Москвы,
а `city_district` — как район города. Она также возвращает `house_fias_id`, уровень
найденного объекта `fias_level`, актуальность адреса и показатели качества.
[Документация стандартизации адреса DaData](https://dadata.ru/api/clean/address/).

Не следует называть `federal_district` округом объекта: это федеральный округ,
другой уровень иерархии. Аналогично, `area` — район в регионе, а не район Москвы.

Главный открытый продуктовый вопрос: под словом «район» владельцу нужен
**административный район Москвы** или **муниципальный округ**. Для текущего
интерфейса разумный default — административный район, потому что он образует
понятную пару с административным округом. Если нужен муниципальный округ, его
следует хранить отдельным полем и брать только из `divisions.municipal`, не
переименовывая административный район. DaData документирует отдельные режимы
`administrative` и `municipal` и возвращает обе гранулярные иерархии в
`divisions` для выбранного результата.
[Документация подсказок и делений DaData](https://dadata.ru/api/suggest/address/).
Официальный портал ФИАС также отдельно предлагает муниципальное и
административно-территориальное деление.
[Поиск Государственного адресного реестра ФНС](https://fias.nalog.ru/Search).

## Условие автоматического принятия

Автоматически публиковать округ/район только когда одновременно выполнены условия:

1. страна — Россия, а для московских полей регион однозначно Москва
   (`region_iso_code=RU-MOW` и московский `region_fias_id`);
2. найден конкретный дом: есть `house_fias_id`, либо подтверждён эквивалентный
   house-level результат; для DaData уровень ФИАС 8 означает дом;
3. нормализованный дом, корпус/строение и исходный адрес не противоречат друг другу;
4. адрес актуален, а не удалён; переименованный или переподчинённый адрес требует
   сохранения соответствующего quality marker;
5. нужный компонент округа/района присутствует и имеет ожидаемый тип.

DaData указывает, что `qc_house=2` означает дом, найденный в ФИАС; отсутствие дома
в ФИАС при наличии результата на картах имеет отдельный код и не должно получать
такую же степень доверия. `unparsed_parts` также нельзя игнорировать.
[Поля качества clean/address](https://dadata.ru/api/clean/address/#response).

Результат только по улице, ближайшему дому или нескольким кандидатам переводить в
`requires_review`. Район нельзя выводить из названия улицы: улица может пересекать
границу, иметь одноимённые варианты или не задавать дом. Для адресов вне Москвы
`city_area` неприменим; нужно показывать типизированную региональную/городскую
иерархию либо оставлять московские поля пустыми.

## Поток данных

```text
immutable address snapshot
        │ address SHA-256
        ▼
server-side enrichment owner ──► provider adapter
        │                         DaData clean/address
        │                         GAR/FIAS adapter later
        ▼
append-only derived fact ──► accepted projection / review queue
```

Предлагаемый application seam: `enrichObjectAdministrativeLocation(objectId,
sourceAddressSha256)`. HTTP-экран, импорт и cron только вызывают его. Provider
adapter получает адрес здания, возвращает нормализованный адрес, идентификаторы,
две типизированные иерархии и quality fields. Ключи и секреты остаются только на
сервере: документация DaData отдельно запрещает вызывать clean/address из браузера,
чтобы не раскрывать секретный ключ.
[Ограничения clean/address](https://dadata.ru/api/clean/address/#restrictions).

Существующий `fm2_pilot_object_details` хранит immutable JSON, `contentSha256`,
`capturedAt` и provenance исходных полей (`sourceTable`, `sourceColumn`, field и
dictionary IDs). Округ и район не следует дописывать в этот JSON или в подписанные
snapshot-поля распоряжения. Новый результат должен быть отдельным append-only
derived fact со следующими данными:

- `objectId`, `sourceAddressSha256`, нормализованный адрес и `house_fias_id`;
- административные округ/район и отдельно муниципальные компоненты, если нужны;
- provider, время ответа, версия/дата справочника при наличии;
- quality codes, actuality state, hash нормализованного ответа;
- состояние `accepted`, `requires_review` или `rejected`;
- ссылка на предыдущий derived fact при обновлении.

Проекция показывает только последний принятый факт для того же address hash.
Изменился исходный адрес — старое обогащение остаётся в истории, но перестаёт быть
текущим. Ручное исправление сохраняется отдельным фактом с пользователем, временем
и причиной; повторная автоматическая загрузка его не перезаписывает.

## Кэш и обновления

До установления идентичности дома кэшировать по `provider + addressSha256`. После
надёжного совпадения переиспользовать результат по `provider + house_fias_id +
division mode`, одновременно сохраняя исходный hash каждого объекта. Это позволяет
не оплачивать одинаковый дом многократно и не смешивать административный ответ с
муниципальным.

Границы и подчинённость меняются. Кэш должен иметь `observedAt`, actuality marker и
срок повторной проверки; новая классификация добавляет факт, а не исправляет старый.
Объекты с переименованием, переподчинением, исчезнувшим районом или изменившимся
house ID отправляются на review.

## Выбор источника

1. **DaData clean/address — быстрый pilot adapter.** Метод предназначен для
   серверной стандартизации одной строки, возвращает GAR/FIAS house identity,
   московский округ, район и quality codes. Suggest API удобен для интерактивного
   выбора, но сама документация говорит, что подсказки не предназначены для
   автоматической обработки базы или файла; для batch нужен clean/address.
2. **Прямой GAR/FIAS — целевая государственная authority.** Он явно различает
   административное и муниципальное деление и даёт официальную адресную
   идентичность, но потребует отдельного adapter, обновления справочника/API,
   сопоставления и эксплуатационного контроля.
   [Условия открытых API ФИАС](https://fias.nalog.ru/docs/%D0%A3%D1%81%D0%BB%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F%20%D0%B8%D1%81%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F%20API-%D1%81%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D0%BE%D0%B2%20%D0%A4%D0%98%D0%90%D0%A1.pdf).
3. **Yandex Geocoder — fallback для ручной сверки.** Он возвращает `kind`,
   `precision` и иерархические address components; `precision=exact` означает
   точное совпадение номера дома, тогда как `number`, `near`, `range`, `street` и
   `other` слабее. Однако компонент `district` обозначен просто как район города
   и не заменяет явное разделение административной и муниципальной иерархий.
   [Формат ответа Yandex Geocoder](https://yandex.ru/maps-api/docs/geocoder-api/response.html).

Для первого pilot slice достаточно DaData clean/address, review queue и ручного
подтверждения неоднозначных результатов. Перед реализацией нужно получить ответ
только на один вопрос: «район» в карточке — административный район или
муниципальный округ Москвы.
