# ORDER-PREPARE-002 — успешная подготовка однообъектного распоряжения

- Статус: `APPROVED`
- Версия: `0.1`
- Дата: `2026-08-27`
- Актор: сотрудник ФКР с полномочием `assignment_order.prepare`
- Публичный командный шов: `InstallationProcess.prepareAssignmentOrder(installationObjectId, installerTabIds[], controlEngineerUserId, actorId)`
- Публичный шов наблюдения: результат команды и `InstallationProcess.getInstallationObjectProcess(installationObjectId)`

## 1. Цель среза

Подготовить первую неизменяемую версию распоряжения по одному объекту монтажа, если выбран один допустимый монтажник и один допустимый инженер строительного контроля, а все необходимые факты объекта монтажа известны.

Срез доказывает один минимальный успешный путь с индивидуальной формой организации труда. Бригадный успешный пример, отдельные отказы по каждому предусловию и изменяющее распоряжение доставляются последующими вертикальными срезами.

## 2. Предусловия

- объект монтажа `installationObjectId` существует, доступен актору и входит в контур пилота;
- монтажное дело имеет состояние `needs_assignment_order`, ещё не открыто и не завершено;
- подготовленных или зарегистрированных версий распоряжения по объекту монтажа нет;
- дата Акта ПТО `ptoactdate` отсутствует;
- заполнены обязательные снимки объекта монтажа: адрес, подъезд/секция, регистрационный номер объекта, актуальные плановые даты начала и завершения;
- выбранный монтажник присутствует в актуальном кадровом каталоге и трудоустроен на бизнес-дату распоряжения;
- в кадровом снимке нет уже известной даты увольнения раньше актуальной плановой даты завершения;
- выбранный инженер является активным пользователем FMonitor с ролью инженера строительного контроля;
- кадровый каталог, каталог пользователей, часы и renderer доступны;
- конкурентного изменения монтажного дела нет.

Предусловия являются принятыми фактами успешного примера. `ORDER-PREPARE-001` продолжает нормативно определять отказы обязательного состава и авторизации. Точные отказы остальных предусловий не входят в этот срез и не должны угадываться реализацией.

## 3. Входные данные

| Поле | Контракт |
|---|---|
| `installationObjectId` | устойчивый идентификатор одного legacy-объекта монтажа |
| `installerTabIds` | список табельных идентификаторов; в этом срезе после нормализации содержит ровно одного монтажника |
| `controlEngineerUserId` | идентификатор одного пользователя FMonitor |
| `actorId` | идентификатор сотрудника ФКР, запросившего подготовку |

Публичная сигнатура и нормализация обязательного состава остаются определёнными `ORDER-PREPARE-001`.

## 4. Источники и снимки

### 4.1. Объект монтажа

Подготовленная версия сохраняет значения, использованные документом:

| Значение снимка | Источник пилота |
|---|---|
| `address` | `fm_maintable.ordadr_address` |
| `entrance` | `fm_maintable.entrance` |
| `objectRegistrationNumber` | `fm_maintable.regnumber` |
| `plannedStartDate` | актуальная плановая дата начала из LegacyInstallationObject adapter |
| `plannedFinishDate` | актуальная плановая дата завершения из LegacyInstallationObject adapter |

Приоритет исходной и скорректированной legacy-даты является обязанностью адаптера и должен быть утверждён до его production-реализации. Команда получает уже определённую актуальную дату и не выбирает между legacy-колонками сама.

### 4.2. Монтажник

Для выбранного монтажника версия сохраняет табельный номер, ФИО, должность, кадровый статус, известные границы трудовых отношений, источник и время кадрового снимка. Будущее трудоустройство не предполагается: команда опирается только на факты, известные на момент подготовки.

### 4.3. Инженер

Для выбранного инженера версия сохраняет идентификатор пользователя, ФИО и должность из каталога пользователей. Значение `responsstroicontrol` может быть подсказкой интерфейса, но не заменяет переданный и проверенный выбор.

## 5. Действие

После прохождения проверок `prepareAssignmentOrder` одной атомарной операцией:

1. определяет бизнес-дату распоряжения в часовой зоне `Europe/Moscow` по серверному моменту команды;
2. создаёт первую неизменяемую версию распоряжения со статусом `prepared`;
3. сохраняет снимки объекта монтажа, монтажника и инженера;
4. вычисляет форму организации труда `individual` для одного монтажника;
5. формирует основной документ и приложение по производному контракту примера № 12-Р;
6. сохраняет для каждого артефакта имя, media type, размер и SHA-256 фактически сформированных байтов;
7. закрывает текущую задачу подготовки; ожидаемое подтверждение регистрации показывается как действие в строке этой точной версии документа, но не создаёт отдельную процессную задачу, состояние или навигационный раздел;
8. добавляет один append-only факт успешной подготовки и аудит автора/времени.

Подготовка не открывает работы и не делает чек-лист доступным.

## 6. Наблюдаемый результат

Результат успешной команды:

```text
accepted = true
assignmentOrderVersion = 1
status = prepared
assignmentOrderDate = YYYY-MM-DD
organizationType = individual
```

`getInstallationObjectProcess(installationObjectId)` показывает:

- состояние монтажного дела `assignment_order_prepared`;
- актуальную версию `1` в статусе `prepared` без регистрационного номера 1С ДО;
- неизменяемую бизнес-дату распоряжения;
- снимки объекта монтажа, монтажника и инженера;
- два сформированных артефакта с контрольными суммами;
- недоступность открытия работ и чек-листа;
- закрытую задачу `prepare_assignment_order`; отдельной задачи подтверждения регистрации нет, а доступное действие привязано к строке версии `1`;
- одно событие `assignment_order_prepared`.

Повторное чтение возвращает те же факты. Изменение исходных legacy-значений после команды не меняет снимок подготовленной версии.

## 7. Сохранённые факты и аудит

Событие `assignment_order_prepared` содержит минимум:

| Поле | Значение |
|---|---|
| `installation_object_id` | идентификатор объекта монтажа |
| `order_version` | `1` |
| `actor_id` | аутентифицированный актор |
| `occurred_at` | серверный момент команды |
| `order_date` | дата этого момента в `Europe/Moscow` |
| `installer_tab_ids` | нормализованный список выбранных табельных номеров |
| `control_engineer_user_id` | выбранный пользователь |
| `organization_type` | `individual` |
| `artifact_sha256` | контрольные суммы основного документа и приложения |

Версия, назначения, артефакты, закрытие задачи подготовки и событие сохраняются атомарно: при ошибке renderer или сохранения успешного результата и частичных процессных фактов нет.

## 8. Отказы этого среза

Этот срез не добавляет новых кодов отказа. Отказы `INSTALLER_REQUIRED`, `CONTROL_ENGINEER_REQUIRED` и `FORBIDDEN` остаются определены `ORDER-PREPARE-001` и должны происходить до успешного пути.

Коды и сообщения для отсутствующих реквизитов объекта монтажа, Акта ПТО, недопустимого монтажника, недопустимого инженера, существующей версии, ошибки renderer и конкурентного изменения требуют отдельных утверждённых срезов. До их появления production-реализация не должна вводить произвольные публичные причины.

## 9. Исполняемый пример A — один монтажник

Серверный момент:

```text
2026-08-26T21:30:00+00:00
```

Он соответствует бизнес-дате `2026-08-27` в `Europe/Moscow`.

Команда:

```text
installationObjectId = 4512
installerTabIds = [1042]
controlEngineerUserId = 73
actorId = 18
```

Снимок объекта монтажа:

```text
address = "Москва, ул. Примерная, д. 10"
entrance = "2"
objectRegistrationNumber = "77-000123"
plannedStartDate = 2026-10-05
plannedFinishDate = 2026-12-20
ptoActDate = null
```

Кадровый снимок монтажника:

```text
tabId = 1042
fullName = "Иванов Иван Иванович"
position = "Электромеханик по лифтам"
status = employed
employedFrom = 2024-02-01
employedTo = null
source = one_c_zup_via_bitrix
sourceUpdatedAt = 2026-08-26T18:00:00+03:00
```

Снимок инженера:

```text
userId = 73
fullName = "Петров Пётр Петрович"
position = "Инженер строительного контроля"
active = true
role = construction_control_engineer
```

Тестовый renderer по нормативно заданным входам возвращает два известных набора байтов:

```text
order artifact bytes = "ORDER-PREPARE-002 example A order document"
appendix artifact bytes = "ORDER-PREPARE-002 example A appendix"
```

Ожидаемый результат команды:

```text
accepted = true
assignmentOrderVersion = 1
status = prepared
assignmentOrderDate = 2026-08-27
organizationType = individual
```

Ожидаемые SHA-256, независимо вычисленные из буквальных байтов примера:

```text
order = 71656f4e5ff9503697a22a0cbbe44f7ddf626aa6293bc646eb0fb601216337c4
appendix = 6b662f08f20c3e5aab3c12ffa19dbccf7dfd38e3c2aaaea481be4fb077282fe7
```

После команды версия `1` имеет `status = prepared`, `registrationNumber = null`, `assignmentOrderDate = 2026-08-27`, `organizationType = individual` и точные снимки выше. `processState = assignment_order_prepared`, `installationOpened = false`, `checklistAvailable = false`. Текущая задача `prepare_assignment_order` закрыта; отдельной задачи регистрации нет, а действие ручного подтверждения доступно только в строке версии `1`. Событие `assignment_order_prepared` ссылается на те же версию, автора, момент, состав и контрольные суммы.

## 10. Не входит в срез

- успешная подготовка бригадного состава;
- точные отказы по состоянию объекта монтажа, обязательным реквизитам, Акту ПТО, кадровому каталогу и инженеру;
- алгоритм выбора между исходной и скорректированной legacy-датой;
- конфликт загрузки монтажника;
- генерация production PDF/DOCX конкретной библиотекой;
- подпись документа и выбор подписанта;
- номер либо финальный файл из 1С ДО;
- подтверждение регистрации;
- открытие работ и доступ к чек-листу;
- изменяющее распоряжение и замена монтажника;
- HTTP-маршрут и UI.

## 11. Решения и доказательства

- `PRODUCT.md` и `CONTEXT.md`: одно распоряжение относится к одному объекту монтажа; подготовленная версия неизменяема; изменение состава создаёт новое распоряжение.
- [`fmonitor-2-primary-spec.md`](../docs/fmonitor-2-primary-spec.md): публичный seam, `Europe/Moscow`, источники истины, кадровые и процессные инварианты.
- [`order-template-required-inputs.md`](../docs/order-template-required-inputs.md): обязательные поля объекта монтажа и производный контракт примера № 12-Р.
- `ORDER-PREPARE-001`: авторизация, обязательный состав и порядок ранних отказов.
- Решение владельца продукта от `2026-08-27`: кадровая проверка использует известные на момент команды факты; замена оформляется новым распоряжением; факт Акта ПТО определяется обязательной датой, файл необязателен.
