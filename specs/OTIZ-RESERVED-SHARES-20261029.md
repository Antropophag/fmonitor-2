# ОТИЗ: исключения и сохранённые доли — решение владельца 29.10.2026

## Простыми словами

Если монтажник уволен на дату расчёта или ОТИЗ временно исключил его с причиной,
остальным выплачиваются их суммы. Его доля хранится отдельно. После разбирательства
ОТИЗ может выплатить эту долю ему, распределить между исходной бригадой или назначить
другому официально закреплённому монтажнику того же объекта. Старые выплаты и работы
не пересчитываются. Одна и та же доля не может быть распределена дважды.

## Подтверждённый контракт

R1. Новые расчёты используют версию recipient policy `reserved-shares-v1`.
Исторические accepted/paid projections и обязательства неизменны. Старый черновик
требует явного refresh перед утверждением по новой политике; не мигрировать его молча.
Явная replacement неоплаченного утверждения допустима существующим маршрутом.

R2. Кадровый статус определяется по последнему достоверному наблюдению не позднее
расчётной даты (МСК), либо по достоверной бизнес-дате увольнения. Текущий каталог
нельзя переносить в прошлое. Сохраняются источник, дата наблюдения, качество данных.
Неизвестный статус не считается трудоустройством: доля сохраняется отдельно и причина
видна. Дата синхронизации не становится датой увольнения. В production доступны
workforce_observations начиная с 26.09; дат увольнения нет.

R3. Сначала снижение за сроки и общие удержания, затем распределение исходного пула
по доказанным весам. Доля исключённого не переходит другим автоматически. Сохраняются
`reservedCents` у получателя, объекта и расчёта, отдельно от payable и deductions.
Резерв не является штрафом, выплатой или новыми работами. Полный резерв допускает
утверждение прав при нулевой выплате без фиктивной отметки оплаты.

R4. `saveDecision(...,'do_not_pay',reason,...)` для новой политики сохраняет долю
любого участника в резерв; reason обязателен, plain text, история/audit/actor/revision.
Возврат `pay` снимает ручное исключение только при допустимом кадровом статусе;
системное исключение уволенного не обходится простым POST. Личное удержание и
исключение того же участника требуют явного устранения конфликта без частичной записи.
Preview не меняет сохранённых сумм и revision; save — отдельное действие.

R5. Публичная команда создания черновика распределения резерва:
`createReserveReleaseDraft(actor, sourceCalculationId, sourceRevision, objectId,
sourceEmployeeId, recipients, reason, operationId)`.
`recipients` — список `{employeeId, weight}` с уникальными identities, положительными
целыми весами; распределяется весь доступный остаток выбранной доли. Причина обязательна.
Разрешены исходный получатель, остальные участники исходного расчёта этого объекта
или монтажник из актуального официального применённого состава этого объекта.
Для исходного получателя допустимо отдельное явное решение выплатить резерв даже при
увольнении; это не меняет правило автоматического формирования обычного расчёта.
Нельзя подставить произвольного сотрудника, имя, сумму или чужой объект через POST.

R6. Черновик распределения нейтрален. Его утверждение создаёт только новые обязательства
из выбранного резерва и неизменяемую связь с исходником. Повторное признание checklist,
ПТО, декларации, увеличение фонда, изменение прежних obligations/payments запрещены.
Исходник может быть уже выплачен остальным участникам. `remainingReservedCents`
считается отдельно от сохранённого исходного `reservedCents`; accepted распределение
потребляет резерв до оплаты. Старое распределение отменяется по существующим правилам
только если не оплачено; отмена освобождает соответствующий резерв с сохранением истории.

R7. Конкурирующие черновики не могут превысить резерв. Atomic acceptance блокирует
исходник/резерв и повторно проверяет остаток; второй получает предметный конфликт.
Replay UUID безопасен, другой payload конфликтует. Права otiz.manage, CSRF, revision,
admission, чужие identities, отказ без новых фактов и неизменность paid сохраняются.
Нельзя отменить/заменить исходник при действующем распределении резерва. Отказ
записи/конкуренция не теряют резерв и не создают половину обязательств.

R8. UI показывает к выплате, сохранённую долю, причину и доступный остаток раздельно.
ОТИЗ получает существующее действие решения для каждого монтажника, не только
уволенных. В обеих группировках доступны preview/save и создание отдельного
распределения резерва; однозначно указан объект и исходный расчёт. Прямой POST
проверяется тем же owner. Финальная выплата использует сохранённые обязательства.
XLSX содержит резерв и причину отдельными колонками/листом; платёжное приложение
содержит только положительные payable. Итоги экономики не теряют резерв и не считают
его выплаченным. История старых расчётов воспроизводится без новых предположений.

## Числовая приёмка (копейки)

A. Gross1000000, Ксс9000, общий штраф0; веса A60/B40, B dismissed.
Сроки100000; A payable540000, B payable0/reserve360000; total540000/reserve360000.
Утверждение признаёт исходные1000000 один раз, оплата540000 не закрывает резерв.

B. После оплаты A: распределить360000 B100% → новый payable B360000,
original payment540000 и исходные claims неизменны. После утверждения release
remainingReserve0 даже до его оплаты; другой release отклоняется.

C. Резерв360000 распределён A:B=2:1 → A240000/B120000; это отдельное явное решение.
Копейки распределяются детерминированно existing largest remainder + stable identity.

D. Оба employed, gross1000000/Ксс1: исходные600000/400000. Ручное исключение A с
причиной → A0/reserve600000, B400000. Снятие исключения до acceptance →600000/400000.
Пустая причина, неверная revision, чужой actor/employee оставляют все факты неизменными.

E. Если все исключены: payable0, reserve1000000; права сохраняются один раз,
payment запрещён ZERO_OBLIGATION, резерв доступен для отдельного решения.

F. Уволен по наблюдению15.10: расчёт10.10 берёт более раннее employed наблюдение,
расчёт20.10 — dismissed. Каталог20.10 не переопределяет расчёт10.10. При отсутствии
любых сведений на10.10 — unknown, явный резерв, не выдуманный статус или дата.

Root автор контракта/регрессий. Исполнитель отдельный sol/low, затем независимый
reviewer. Владелец разрешил короткий production цикл вместо обычных гейтов.
