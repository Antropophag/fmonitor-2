# OTIZ-OBJECT-REGISTER-PAGING-001

## Простыми словами

ОТиЗ получает одну страницу объектов, а поиск и фильтры ищут по всем объектам. Итоги по всему реестру, расчёты и история сохраняются.

## Public seam

`new FMonitor2\Otiz\ObjectRegister(mysqli $db, string $prefix, string $legacyPrefix)`; `read(int $actorId, array $query): array`.
Ответ: `query` (q,state,sort,page,pageSize), `page`, `pageSize`, `pages`, `total` (отфильтрованный count), `rows`, `summary`.
Rows сохраняют колонки старого objects(), плюс `state`, `premium_cents`, `shaft_bp`, `fund_cents`, `deadline_penalty_cents`, `display_progress_bp`, `display_progress_date`.
Summary keys: `total`, `fund`, `earned`, `paid`, `penalties`, `balance`, `blocked`, `calculated`; прежний global balance=SUM по объектам max(0,fund_i-paid_i-discipline_i-stored_deadline_i), penalties=SUM(discipline_i+trace_deadline_i). Отдельный row balance=max(0,fund_i-paid_i-discipline_i-trace_deadline_i); это различие сохраняется. Это characterization, не новая финансовая норма.
DomainException messages: REGISTER_QUERY_INVALID→HTTP400, REGISTER_PAGE_NOT_FOUND→404, REGISTER_FORBIDDEN→403. Read-only consistent transaction; вызывается вне чужой транзакции.

## Acceptance


### Requirement: Страница выбирается сервером после полного отбора

Активный пользователь с `otiz.manage` SHALL получать только запрошенную страницу доступных объектов; сервер MUST применять поиск, состояние и сортировку ко всему набору до ограничения страницы в хранилище. Система MUST NOT загружать весь реестр в память приложения или DOM ради разбиения на страницы. Прогресс SHALL загружаться только для объектов страницы; число DB запросов MUST быть ограничено константой независимо от числа объектов и размера страницы (нет N+1). Отдельная общая сводка может сканировать O(N) строк unbuffered, не накапливая их в массиве.

#### Scenario: Поиск за пределами первой страницы
- **WHEN** пользователь ищет регномер или адрес объекта, который без фильтра находится на третьей странице
- **THEN** объект возвращается на первой странице отфильтрованного набора, а количество учитывает весь результат

### Requirement: Параметры и порядок предсказуемы

По умолчанию SHALL возвращаться страница1 размера50; допустимы размеры25,50,100, максимум100. Поиск SHALL быть регистронезависимым буквальным вхождением в объединённые регномер и адрес после обрезки пробелов по краям, длиной не более120 символов. `%` и `_` MUST NOT становиться шаблонами. Состояния: все, planned,ready,blocked,no_new_amount,completed,missing_norm. Порядки: default (snapshot_id IS NULL ASC, FIELD(calculation_state,'blocked','ready','no_new_amount','completed') ASC, regnumber ASC, object_id ASC; NULL/неизвестное состояние имеет FIELD rank0), regnumber_asc,regnumber_desc; каждый MUST завершаться object_id ASC. Неверный тип/значение параметра SHALL давать400; страница за концом —404; пустой результат на странице1 —200.


`query` поддерживает q,state,sort,page,pageSize; неизвестные ключи игнорируются (совместимость GET tracking). q/state/sort при наличии только строки; пустые q/state допустимы, пустой sort не допустим. page/pageSize принимают положительный PHP int либо каноническую десятичную строку без знака/пробелов/ведущих нулей. Максимальный page=1 000 000, размеры только25/50/100. bool,null,float,array отклоняются для любого известного параметра. Отсутствие параметра даёт default: q='',state='',sort='default',page=1,pageSize=50. Сначала authorization: forbidden actor получает REGISTER_FORBIDDEN даже с неверными query; затем validation, затем page bound. q trim выполняется до ограничения длины120.

#### Scenario: Равные регномера
- **WHEN** пользователь проходит страницы при неизменных данных с одинаковыми регномерами
- **THEN** каждый объект встречается один раз в устойчивом порядке по object_id

#### Scenario: Некорректный запрос
- **WHEN** page=0, page имеет нецелый вид, pageSize=101, неизвестны state/sort либо q является массивом
- **THEN** сервер возвращает400 без записи фактов

### Requirement: Экономическая семантика сохраняется

Источником значений SHALL оставаться текущие карточки, последний расчёт по report_date/id и все сохранённые closure/reversal facts. `missing_norm` MUST иметь приоритет, затем planned при отсутствии расчёта, затем calculation_state; ready с pool>0 и закрытой суммой не меньше pool SHALL отображаться completed. Денежные формулы SHALL оставаться у существующего владельца NativePremiumNorms и извлечённой общей проекции. Глобальные итоги SHALL сохранять прежний смысл независимо от фильтра, сортировки и страницы.

#### Scenario: Неполная карточка и закрытый расчёт
- **WHEN** карточка не имеет норматива при готовом расчёте либо готовый расчёт полностью закрыт
- **THEN** фильтр выбирает соответственно missing_norm либо completed до пагинации

Глобальный balance SHALL быть SUM по объектам max(0,fund_i-paid_i-discipline_i-stored_deadline_i), penalties=SUM(discipline_i+trace_deadline_i). Отдельный row balance SHALL оставаться max(0,fund_i-paid_i-discipline_i-trace_deadline_i). Существующее различие сохраняется.

#### Scenario: Перепокрытый объект не уменьшает остаток другого
- **WHEN** два объекта имеют фонды100 и100коп и выплаты150 и0коп при нулевых удержаниях
- **THEN** общий остаток равен0+100=100коп, а не50коп

#### Scenario: Общая сводка
- **WHEN** пользователь переходит на другую страницу либо фильтрует реестр
- **THEN** фонд, начисления, выплаты, удержания, остаток и общие счётчики остаются теми же для неизменных данных

### Requirement: Навигация сохраняет контекст и доступность

HTTP SHALL сохранить существующие UI, роли, историю и маршруты подготовки выплат/выбранную дату расчёта. GET форма и ссылки MUST сохранять q,state,sort,pageSize; смена отбора SHALL начинать страницу1. Навигация MUST работать с клавиатуры и на узком экране. Пустая выдача SHALL объяснять изменение фильтров. Этот список не имеет выбора строк/массовых действий.

#### Scenario: Фильтр и переход
- **WHEN** пользователь отправляет GET форму и переходит на следующую страницу
- **THEN** параметры сохраняются в URL и контролах, текущая страница обозначена, данные прочитаны сервером

### Requirement: Чтение безопасно и измерено

Неактивный пользователь или пользователь без `otiz.manage` SHALL получить отказ до чтения реестра. Чтение MUST NOT изменять бизнес-факты, схему или создавать persistent projection. Проверка SHALL работать в отдельном синтетическом контуре на30 000 объектах и сохранять до/после время, размер HTTP ответа, число запросов и EXPLAIN; wall-clock SHALL быть измерением, не нестабильным CI assertion.

#### Scenario: Изолированная проверка масштаба
- **WHEN** измеряются первая/последняя страницы, поиск и состояния на30 000 объектах
- **THEN** HTTP содержит не более выбранного размера строк, приложение сохраняет ограниченную память, планы запросов и результаты опубликованы без private данных

## Independently determined examples

125 объектов без снимков с одинаковым регномером сортируются id ASC: страницы50/50/25, объединение содержит125 уникальных id. Объект с уникальным адресом на последней странице находится поиском на странице1. При pageSize25 доступны5 страниц. Поиск буквального `%` не находит все строки.

Норматив пассажирского лифта5 этажей/320кг:520 ×100000=52 000 000коп; железобетон10000bp → фонд52 000 000коп, кирпич11500bp →59 800 000коп. Три valid объекта с первым фондом дают156 000 000коп независимо от страницы. Неподдерживаемая грузоподъёмность501кг не имеет нормы; карточка без lift_type при320кг использует существующий fallback passenger. Источник: утверждённый Appendix4 contract NativePremiumNorms, формула не меняется.

Состояние ready,pool100,closures paid100→completed; ready,pool100,paid99→ready; отсутствие нормы поверх этих состояний→missing_norm. Последний snapshot определяется report_date, затем id, а не максимальным id при более ранней дате.

## Gates

Gate3 и Gate5 выполняет независимый reviewer. RED на отсутствующем публичном read seam/реальном старом HTTP превышении page size; GREEN focused; один fullCI на exact candidate. Browser проверяет фильтр за страницей1, URL, клавиатуру, пустой результат и узкий экран.30k evidence не ослабляет обычные money/history/auth assertions.

При двух фондах100 и100 и выплатах150 и0 общий остаток равен0+100=100, а не max(0,200-150)=50.
