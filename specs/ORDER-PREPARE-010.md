# ORDER-PREPARE-010 — результат подготовки не установлен после неизвестного commit

- Статус: `APPROVED`
- Версия: `0.1`
- Дата: `2026-08-28`
- Актор: сотрудник ФКР с полномочием `assignment_order.prepare`
- Публичный командный шов: `InstallationProcess.prepareAssignmentOrder(installationObjectId, installerTabIds[], controlEngineerUserId, actorId)`
- Публичный шов наблюдения: результат команды и `InstallationProcess.getInstallationObjectProcess(installationObjectId)`

## 1. Цель

Не сообщать ложный успех или безопасный отказ с предложением повтора, если persistence потерял подтверждение `COMMIT`, а однократный reconciliation по внутреннему `preparationOperationId` не нашёл сохранённый результат.

Пользователь получает отдельный неопределённый результат и должен обновить состояние объекта монтажа перед дальнейшими действиями. Команда не повторяет renderer, сохранение или всю бизнес-операцию автоматически.

## 2. Предусловия и порядок

- все проверки и renderer успешно завершены по правилам предыдущих срезов;
- модуль один раз создал внутренний `preparationOperationId`;
- atomic persistence получил полное изменение и этот идентификатор, но сообщил типизированный неизвестный исход `COMMIT`;
- модуль один раз запросил результат по тому же `preparationOperationId`;
- reconciliation вернул `not found`: на момент проверки сохранённый результат этой операции не установлен;
- persistence и reconciliation не раскрывают, был ли окончательно выполнен rollback, не завершится ли commit позднее и не появится ли результат после задержки репликации.

```text
all approved validations
→ create one internal preparationOperationId
→ renderer once
→ atomic persistence once
→ commit outcome unknown
→ reconcile once by the same preparationOperationId
→ result not found
→ return indeterminate result without retry or process audit write
```

## 3. Наблюдаемый результат

```text
accepted = false
violations = [
  {
    code: ASSIGNMENT_ORDER_RESULT_UNKNOWN,
    message: "Не удалось подтвердить результат формирования распоряжения. Обновите данные объекта монтажа перед дальнейшими действиями.",
    field: null
  }
]
```

Это не `ASSIGNMENT_ORDER_PERSISTENCE_FAILED`: команда не утверждает, что изменения откатились, и не предлагает немедленно повторить формирование.

Ответ не раскрывает `preparationOperationId`, SQL, имя таблицы, параметры подключения, exception message, stack trace или детали reconciliation.

## 4. Состояние и аудит

Команда не выполняет дополнительную запись в процессное хранилище после неизвестного исхода. В частности, она не:

- повторяет atomic persistence;
- создаёт новую версию или заменяет найденную позже версию;
- добавляет `assignment_order_prepare_rejected` либо второе событие успеха;
- закрывает или повторно открывает задачу;
- обновляет legacy-проекцию.

Публичная проекция после ответа отражает только то состояние, которое доступно обычному чтению. Отсутствие версии в немедленном чтении не доказывает rollback и не разрешает автоматический повтор. Техническая диагностика неизвестного исхода должна идти в отдельный инфраструктурный журнал; его контракт не входит в этот срез.

## 5. Исполняемый пример A

Сотрудник `18` вызывает `prepareAssignmentOrder(4512, [1042], 73, 18)`. Генератор один раз возвращает `prep-op-a71d`; renderer возвращает полный комплект. Atomic persistence один раз сообщает `commit outcome unknown`, не предоставляя подтверждения commit или rollback. Reconciliation один раз ищет `prep-op-a71d` и возвращает `not found`.

Команда возвращает точный результат раздела 3. Fixture показывает исходную публичную проекцию `needs_assignment_order` без распоряжения; модуль не добавляет в неё rejection audit и не использует это наблюдение как разрешение повторить запись. Renderer, atomic persistence, генерация ID и reconciliation вызваны ровно по одному разу.

Ожидаемые ответ и проекция задаются литералами этой спецификации, а не вычисляются из production-реализации.

## 6. Следующее действие пользователя

UI по коду `ASSIGNMENT_ORDER_RESULT_UNKNOWN` показывает сообщение раздела 3, прекращает состояние отправки и инициирует обычное перечитывание карточки. Кнопка не должна автоматически отправлять ту же команду повторно.

Если перечитанное состояние содержит подготовленную версию, UI показывает её как обычный сохранённый результат. Если версии по-прежнему нет, политика ручного повтора после дополнительной проверки задаётся отдельным transport/operations-срезом; этот срез не объявляет повтор безопасным.

## 7. Сквозной инвариант

Срез наследует безопасный повтор и конкретизирует уже утверждённое правило: когда применённый результат установить нельзя, система отклоняет устаревшее действие и требует перечитать состояние. Сквозную идемпотентность отдельно не согласовывают; Gate 1 требуется только для нового пользовательского кода, текста и следующего действия.

## 8. Не входит

- reconciliation недоступен или сам завершился ошибкой;
- найденный успешный результат (`ORDER-PREPARE-009`);
- подтверждённый rollback (`ORDER-PREPARE-008`);
- политика и срок повторных reconciliation;
- ручной или автоматический повтор после последующего чтения;
- transport idempotency key, HTTP и UI-реализация;
- production DB/legacy-адаптер;
- технический журнал и алертинг.

## 9. Решения и доказательства

- `docs/fmonitor-2-primary-spec.md`: при неизвестном результате система либо возвращает применимый результат, либо предлагает перечитать состояние.
- `ORDER-PREPARE-008`: retryable persistence-отказ допустим только после подтверждённого rollback.
- `ORDER-PREPARE-009`: найденный по operation ID commit возвращается как обычный успех.
- `docs/fmonitor-2-session-handoff.md`: без установления сохранённого результата нельзя предлагать безопасный повтор.
