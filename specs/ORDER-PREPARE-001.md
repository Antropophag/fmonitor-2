# ORDER-PREPARE-001 — обязательный состав распоряжения

- Статус: `APPROVED`
- Версия: `0.1`
- Дата: `2026-08-27`
- Актор: сотрудник ФКР с полномочием `assignment_order.prepare`
- Публичный командный шов: `InstallationProcess.prepareAssignmentOrder(installationObjectId, installerTabIds[], controlEngineerUserId, actorId)`
- Публичный шов наблюдения: результат команды и `InstallationProcess.getInstallationObjectProcess(installationObjectId)`

## 1. Цель среза

Не допустить появления проекта распоряжения без обязательных участников: хотя бы одного монтажника и ровно одного инженера строительного контроля.

Срез специфицирует только обязательность выбранного состава и авторизацию команды. Он не подтверждает допустимость конкретного человека, не формирует файл и не описывает успешную подготовку распоряжения целиком.

## 2. Предусловия

Во всех примерах, кроме проверки авторизации:

- объект монтажа `installationObjectId` существует и доступен актору;
- объект монтажа входит в контур пилота;
- монтажное дело ещё не открыто и не завершено;
- по делу нет Акта ПТО;
- актуальная подготовленная версия распоряжения отсутствует;
- обязательные реквизиты объекта монтажа заполнены;
- переданные идентификаторы людей, если они есть, существуют и допустимы;
- кадровый каталог и каталог пользователей доступны;
- конкурентного изменения монтажного дела нет.

Эти условия задаются как принятые факты примера. Их проверка относится к последующим спецификациям и не может подменять ожидаемый отказ этого среза.

## 3. Входные данные

| Поле | Контракт этого среза |
|---|---|
| `installationObjectId` | устойчивый идентификатор одного объекта монтажа |
| `installerTabIds` | список устойчивых табельных идентификаторов; пустой список означает, что монтажник не выбран |
| `controlEngineerUserId` | идентификатор пользователя FMonitor; `null` означает, что инженер не выбран |
| `actorId` | идентификатор пользователя, запросившего подготовку |

На публичном шве отсутствие массива `installerTabIds` нормализуется в пустой список. Отсутствие `controlEngineerUserId`, пустая строка и `null` нормализуются в `null`. Некорректный формат непустого идентификатора относится к валидации транспортного контракта и не входит в этот срез.

## 4. Действие

Актор отправляет команду `prepareAssignmentOrder` для одного объекта монтажа.

Система сначала проверяет полномочие `assignment_order.prepare`, затем определяет полный набор нарушений обязательного состава. Проверки допустимости выбранных людей выполняются только после прохождения проверок обязательности.

## 5. Наблюдаемый результат

### 5.1. Монтажник не выбран

Если `installerTabIds` пуст, команда отклонена с причиной:

```text
code: INSTALLER_REQUIRED
message: Выберите хотя бы одного монтажника.
field: installerTabIds
```

### 5.2. Инженер не выбран

Если `controlEngineerUserId` равен `null`, команда отклонена с причиной:

```text
code: CONTROL_ENGINEER_REQUIRED
message: Выберите инженера строительного контроля.
field: controlEngineerUserId
```

### 5.3. Оба участника не выбраны

Команда возвращает обе причины одним отклонённым результатом в стабильном порядке:

1. `INSTALLER_REQUIRED`;
2. `CONTROL_ENGINEER_REQUIRED`.

Пользователю не требуется повторно отправлять команду, чтобы узнать о втором нарушении.

### 5.4. Нет полномочия

Если актор не имеет полномочия `assignment_order.prepare`, команда отклонена единственной причиной:

```text
code: FORBIDDEN
message: У вас нет права формировать распоряжение.
field: null
```

При отказе авторизации система не раскрывает результаты проверки состава и не обращается к каталогам людей.

### 5.5. Участники выбраны

Если передан непустой `installerTabIds` и непустой `controlEngineerUserId`, проверки этого среза пройдены. Это не означает успех всей команды: следующие спецификации могут отклонить её из-за кадрового статуса, роли инженера, состояния объекта монтажа или другого инварианта.

## 6. Сохранённые факты и отсутствие частичного результата

При любом отказе из раздела 5:

- версия `AssignmentOrder` не создаётся;
- статус существующего распоряжения не меняется;
- назначения монтажников и инженера не создаются;
- документ и приложение не формируются;
- legacy-проекция не обновляется;
- следующая процессная задача не создаётся и текущая не закрывается.

`getInstallationObjectProcess(installationObjectId)` после отказа возвращает то же доменное состояние, которое возвращал до команды, и один новый аудиторский факт отклонения, если актору разрешено видеть аудит этого объекта монтажа.

## 7. Аудит

Каждая отклонённая команда сохраняет один append-only факт `assignment_order_prepare_rejected`:

| Поле | Значение |
|---|---|
| `installation_object_id` | запрошенный `installationObjectId` |
| `actor_id` | аутентифицированный актор |
| `occurred_at` | серверное время принятия решения |
| `reason_codes` | коды отказа в возвращённом порядке |
| `installer_count` | количество переданных уникальных непустых идентификаторов |
| `control_engineer_provided` | передан ли непустой идентификатор инженера |

ФИО, табельные номера, идентификатор выбранного инженера и полное тело команды в аудите отказа этого среза не сохраняются.

При `FORBIDDEN` аудит безопасности сохраняется независимо от права актора читать `getInstallationObjectProcess`; сам актор не получает через ответ сведения о состоянии объекта монтажа или составе.

## 8. Точные правила нормализации

- Повторяющиеся табельные идентификаторы удаляются до вычисления `installer_count`.
- Пустые строки и пробельные элементы массива не считаются выбранным монтажником.
- После нормализации список без идентификаторов считается пустым.
- Проверка «ровно один инженер» обеспечивается формой команды: она принимает одно скалярное значение, а не список.
- Порядок причин одинаков во всех точках входа: монтажник, затем инженер.

## 9. Примеры

### Пример A — нет монтажника

Дано:

```text
installationObjectId = 4512
installerTabIds = []
controlEngineerUserId = 73
actorId = 18 (имеет assignment_order.prepare)
```

Ожидается:

```text
accepted = false
violations = [
  { code: INSTALLER_REQUIRED,
    message: "Выберите хотя бы одного монтажника.",
    field: installerTabIds }
]
```

Доменное состояние объекта монтажа не меняется. Аудит содержит `reason_codes = [INSTALLER_REQUIRED]`, `installer_count = 0`, `control_engineer_provided = true`.

### Пример B — нет инженера

Дано:

```text
installationObjectId = 4512
installerTabIds = [1042]
controlEngineerUserId = null
actorId = 18 (имеет assignment_order.prepare)
```

Ожидается одна причина `CONTROL_ENGINEER_REQUIRED`, отсутствие доменных изменений и аудит с `installer_count = 1`, `control_engineer_provided = false`.

### Пример C — нет обоих участников

Дано:

```text
installationObjectId = 4512
installerTabIds = ["", "   "]
controlEngineerUserId = ""
actorId = 18 (имеет assignment_order.prepare)
```

Ожидается:

```text
accepted = false
violations = [
  { code: INSTALLER_REQUIRED,
    message: "Выберите хотя бы одного монтажника.",
    field: installerTabIds },
  { code: CONTROL_ENGINEER_REQUIRED,
    message: "Выберите инженера строительного контроля.",
    field: controlEngineerUserId }
]
```

Аудит содержит оба кода в том же порядке, `installer_count = 0` и `control_engineer_provided = false`.

### Пример D — нет полномочия

Дано:

```text
installationObjectId = 4512
installerTabIds = []
controlEngineerUserId = null
actorId = 91 (не имеет assignment_order.prepare)
```

Ожидается только `FORBIDDEN`. Причины `INSTALLER_REQUIRED` и `CONTROL_ENGINEER_REQUIRED` не возвращаются.

## 10. Не входит в срез

- успешное создание версии `prepared`;
- проверка существования и кадрового статуса монтажника;
- проверка активности и роли инженера;
- ограничение максимального количества монтажников;
- проверка конфликтующих назначений;
- обязательные реквизиты объекта монтажа;
- дата распоряжения и бизнес-часовая зона;
- Акт ПТО и завершение объекта монтажа;
- генерация, формат и содержимое документа;
- подтверждение регистрации в 1С ДО;
- открытие монтажных работ;
- HTTP-маршрут и визуальное представление ошибок.
