# ORDER-PREPARE-006 — конкурентная первая подготовка

- Статус: `APPROVED`
- Версия: `0.1`
- Дата: `2026-08-28`
- Актор: сотрудник ФКР с полномочием `assignment_order.prepare`
- Публичный командный шов: `InstallationProcess.prepareAssignmentOrder(installationObjectId, installerTabIds[], controlEngineerUserId, actorId)`
- Публичный шов наблюдения: результат команды и `InstallationProcess.getInstallationObjectProcess(installationObjectId)`

## 1. Цель

Не допустить создания двух первых актуальных версий распоряжения, если две допустимые команды одновременно начали подготовку одного объекта монтажа из состояния без распоряжения.

Обе команды могут пройти чтение и проверки. Сохранение версии выполняется атомарно относительно прочитанной сервером ревизии монтажного дела: только одна команда создаёт версию `1`; другая обнаруживает, что ревизия изменилась, и отклоняется без повторной отправки и без замены результата победившей команды.

## 2. Предусловия и вход

- обе команды вызывают утверждённый публичный шов для одного `installationObjectId = 4512`;
- обе команды авторизованы и передают обязательный допустимый состав;
- при первоначальном чтении обе видят `processState = needs_assignment_order`, отсутствие распоряжений и одну серверную ревизию монтажного дела;
- снимок объекта, каталоги людей и renderer доступны, все предметные проверки проходят;
- до атомарного сохранения первой команды другая команда также завершила проверки и подготовила свои артефакты;
- первая завершившая сохранение команда атомарно создаёт версию `1` по правилам `ORDER-PREPARE-002`;
- сохранение второй команды выполняется с уже устаревшей серверной ревизией.

Клиент не передаёт `lockVersion`: ревизию фиксирует сам `InstallationProcess` при чтении монтажного дела и передаёт внутреннему persistence-контракту. Публичная сигнатура команды не меняется.

## 3. Порядок и атомарность

```text
authorization
→ mandatory composition
→ current process/version check
→ installation object data and people catalogs
→ renderer
→ atomic persistence against the initially read process revision
```

Если до persistence уже видна актуальная версия, применяется `ORDER-PREPARE-005` и возвращается `ASSIGNMENT_ORDER_ALREADY_PREPARED` до каталогов и renderer.

`CONCURRENT_MODIFICATION` применяется только когда команда первоначально прочитала отсутствие версии, прошла проверки, но атомарное сохранение не состоялось из-за изменения ревизии после этого чтения.

Persistence не может частично сохранить версию, назначения, артефакты, событие успеха, закрытие задачи или legacy-проекцию проигравшей команды. Уже зафиксированный результат победившей команды не откатывается и не изменяется.

## 4. Наблюдаемый отказ проигравшей команды

```text
accepted = false
violations = [
  {
    code: CONCURRENT_MODIFICATION,
    message: "Объект монтажа изменился во время подготовки распоряжения. Обновите данные и повторите действие при необходимости.",
    field: null
  }
]
```

Команда не повторяет сохранение автоматически и не преобразует себя в изменяющее распоряжение.

## 5. Состояние и аудит

После конфликта публичная проекция содержит ровно одну актуальную версию `1`, сохранённую победившей командой. Её снимки, состав, назначения, артефакты, хэши, событие успеха, состояние дела и задачи остаются неизменными.

После отката неудачной транзакции проигравшей команды отдельная атомарная запись добавляет одно событие `assignment_order_prepare_rejected` в актуальную ревизию:

```text
reasonCodes = [CONCURRENT_MODIFICATION]
installerCount = <число нормализованных уникальных входных монтажников проигравшей команды>
controlEngineerProvided = true
observedProcessRevision = <устаревшая ревизия, прочитанная проигравшей командой>
currentProcessRevision = <ревизия после сохранения победившей команды>
```

Аудит не сохраняет входные табельные номера, выбранного инженера, ФИО, содержимое или хэши незафиксированных артефактов проигравшей команды. Если отдельная запись аудита сама встречает новую конкурентную ревизию, инфраструктура может безопасно повторить только append события; бизнес-команда и renderer повторно не выполняются.

## 6. Исполняемый пример A

Обе команды первоначально читают ревизию `7` объекта монтажа `4512` без распоряжения.

- команда актёра `17` с составом `[1042]`, инженер `73`, первой сохраняет утверждённую версию `1` и переводит ревизию в `8`;
- команда актёра `18` с составом `[2088]`, инженер `74`, пытается сохранить свою подготовленную версию относительно ревизии `7`;
- второй вызов возвращает точный отказ раздела 4;
- версия, назначения, артефакты и событие успеха актёра `17` остаются единственными успешными фактами;
- в конец `events` добавляется только событие отказа актёра `18` с `observedProcessRevision = 7` и `currentProcessRevision = 8`;
- ни один снимок человека или артефакт команды актёра `18` не появляется в публичной проекции.

Ожидаемые значения победившей версии берутся из независимо заданного fixture результата команды актёра `17`, а не вычисляются из production-реализации проигравшей команды.

## 7. Не входит

- повтор команды после неизвестного результата и idempotency key;
- конкурентность разных объектов монтажа;
- изменяющее распоряжение;
- исправление или регистрация номера 1С ДО;
- недоступность persistence и исчерпание повторов записи audit-события;
- очистка временных файлов renderer, если production renderer создаёт их до транзакции;
- UI и HTTP.

## 8. Решения и доказательства

- `docs/fmonitor-2-pilot-data-model.md`: параллельные команды не создают две актуальные версии.
- `docs/fmonitor-2-primary-spec.md`: доменные факты и аудит успеха сохраняются одной транзакцией; `CONCURRENT_MODIFICATION` означает устаревшую ревизию дела.
- `docs/fmonitor-2-screen-flow.md`: конкурентное изменение требует перечитать состояние без молчаливой повторной отправки.
- `ORDER-PREPARE-002`: точный контракт первой успешной версии.
- `ORDER-PREPARE-005`: версия, уже видимая до downstream-проверок, имеет более ранний и отдельный отказ.
