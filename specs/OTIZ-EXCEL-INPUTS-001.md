# OTIZ-EXCEL-INPUTS-001

## Простыми словами

Расчёт видит объекты, открытые через действующий Yii2-процесс, и получает плановый срок, справку, исправленный акт ПТО, прогресс и состав из их фактических источников. Старое зарегистрированное распоряжение больше не является обязательным условием попадания объекта в расчёт.

## Публичный контракт

`MariaDbNativePremiumInputs(mysqli $db,string $prefix,?string $legacyPrefix=null,?Closure $clock=null)::forDate(string $reportDate): array`. Clock возвращает ISO timestamp момента выполнения; default Europe/Moscow now. Reader не начинает/не завершает чужую транзакцию и работает внутри согласованного read view публикации. Не пишет фактов. Невалидная reportDate — DomainException INVALID_DATE.

Результат сохраняет действующую форму rows: id,caseId,reg,address,progress,deadline,pto,premium,shaft,team,issues,operands. Добавляется `sourceEvidence` с ключами `capturedAt`, `originalDeadline`, `certificate`, `completion`, `composition`, `progress`. Все source envelopes имеют label/locator/contentSha256. Canonical JSON использует JSON_UNESCAPED_UNICODE|JSON_UNESCAPED_SLASHES; hashes lower SHA256.

1. Выбираются native operational cases (созданные через native workflow без migration provenance, либо имеющие migration category native_candidate) со state working и actual_start_date<=reportDate, с существующим legacy object; сортировка object id. Отсутствие fm2_assignment_orders не исключает объект. Migration quarantine не включается.
2. Исходный срок — именно fm_maintable.plan_finish_date, считанный при forDate, никогда workdateendadjusted/order snapshot. `originalDeadline` = {value:ISOdate,capturedAt:ISOtimestamp,source:{label:'Исходный плановый срок',locator:'fm_maintable/<object>/plan_finish_date',contentSha256:SHA256(JSON({objectId,planFinishDate,capturedAt}))}}. Отсутствие/невалидный план добавляет DEADLINE_EVIDENCE_ABSENT и operands=null даже при справке. Новое чтение видит изменённый план; прежний возвращённый результат не меняется.
3. `certificate` — результат DeadlineTransferCertificates::currentEvidence(case) либо null; текущая справка выбирается независимо от даты документа/reportDate. Справка заменяет deadline, её source используется в operand. CERTIFICATE_EVIDENCE_INVALID превращается в blocker того же кода, не в fallback. Без справки deadline operand effectiveDate = дата capturedAt.
4. `completion` = {root:null|row,corrections:list<row>,source:{label,locator:'fm2_pilot_completion_facts/case/<case>/pto_act',contentSha256:SHA256(JSON({root,corrections}))}}. Rows представлены как реальные DB scalar strings/null, corrections по version_no. Эффективная дата акта ПТО берётся из последнего исправления даже после reportDate. Даты, последовательность version_no1..n, previous correction/version links проверяются; повреждение — COMPLETION_EVIDENCE_INVALID, operands=null. Отсутствие ПТО — доказанный null. Original root и corrections не изменяются. Completion operand effectiveDate — дата записи effective source, не report cutoff.
5. Состав читается из последнего неизменяемого applied composition (`fm2_assignment_order_applications`) текущего дела; pending/uploaded originals не являются applied composition. `composition` включает applicationId, sequence, source label='Применённый состав распоряжения', hash canonical JSON всей исходной строки и locator fm2_assignment_order_applications/<id>. Selected snapshot должен соответствовать сохранённому compositionSha256/installer IDs. Отсутствие/повреждение — CREW_EVIDENCE_ABSENT/COMPOSITION_EVIDENCE_INVALID. Не вводится новый writer composition.
6. Checklist progress uses immutable associated template, supporting current sections/items/weight and existing definitions/id/share formats. Verify actual payload SHA against stored SHA and operation template identity. Resolve accepted events in accepted_revision/id order with BOTH deviceTime and serverReceivedAt calendar date<=reportDate; completion_retracted cancels, item_installers_changed changes attribution. Missing/invalid template is DEFINITION_VERSION_UNPROVEN; unknown item CHECKLIST_ITEM_UNPROVEN; missing attribution CHECKLIST_ATTRIBUTION_ABSENT. Completed shares ×100 give0..8500bp. Each item's basis points divided between attributed installers with integer remainder in binary tab order, conserving contribution. `progress` evidence includes source plus active clientOperationIds and contributions, immutable template id/hash; its source hashes all selected operation rows, attribution rows and exact template payload. A future event cannot erase an earlier in-cut completion.
7. Documentary progress retains report cutoffs independently of the comparison-date exception: add1000bp for effective PTO date and recorded-at within reportDate, add500bp for effective declaration date and recorded-at within reportDate when PTO progress qualifies. Corrections effective after the report cutoff do not retroactively change documentary progress; resolve the root/corrections known within that cutoff. Maximum10000bp. Checklist and documentary provenance both belong to progress source. A future PTO may drive penalty without adding progress on an earlier report date.
8. Team uses applied selected installers with positive attributed contribution as weight. Если общий учитываемый progress равен нулю, отсутствие attribution даёт пустое распределение без `INSTALLER_ATTRIBUTION_ABSENT` и без invented weights. При положительном progress каждый selected installer без доказанного positive contribution сохраняет fail-closed `INSTALLER_ATTRIBUTION_ABSENT`; deterministic diagnostic называет safe case id, tab id и разрешённое display name каждого затронутого монтажника. Несколько нарушений не теряются из-за дедупликации только по коду. No inventing workforce membership. NativePremiumNorms/card logic remains, but recompute payload SHA rather than trusting a well-formed stored hash; corruption is OBJECT_CARD_PROVENANCE_INVALID. Six valid operand envelopes are passed to PremiumCalculationV2 without report-date rejection for certificate/PTO. Any blocker yields operands=null; row remains visible.

## Точная canonical evidence grammar

DB rows сохраняют SELECT * column order канонической схемы; скаляры string/null (числа тоже strings). Composition.source label=`Применённый состав распоряжения`, locator=`fm2_assignment_order_applications/<applicationId>`, SHA=JSON полной application row. Completion.source label=`История акта ПТО`; root/corrections — все current-known rows, corrections version_no/id ascending. recorded_at должен быть валидным ISO timestamp; invalid timestamp также COMPLETION_EVIDENCE_INVALID. Certificate envelope без изменений передаётся из certificate owner.

Progress.source label=`Подтверждённый прогресс на отчётную дату`, locator=`fm2_checklist_operations/case/<case>`, SHA=JSON exact ordered object `{reportDate,template,operations,attributions,completionFacts,completionCorrections}`. template — полная associated snapshot row; operations — все in-cut item_completed/item_installers_changed/completion_retracted rows, accepted_revision/id ascending; attributions — полные rows для этих operations, binary client_operation_id затем numeric installer_tab_id; completionFacts — полные текущие root rows дела по id; completionCorrections — их полные rows по root_fact_id/version_no/id (включая вне report cut, чтобы доказать применение cutoff). Additional progress fields: `templateId` integer, `templateHash` lower SHA, `clientOperationIds` active original completion IDs in numeric item_id order, `contributions` tab→integer bp in binary tab order. Полные известные documentary rows входят в digest даже когда cutoff исключает их из progress value. Reader сохраняет ровно шесть sourceEvidence keys в порядке capturedAt,originalDeadline,certificate,completion,composition,progress.
