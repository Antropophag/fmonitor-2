# ORDER-PREPARE-008 — ошибка сохранения подготовленного распоряжения

- Статус: `APPROVED`
- Версия: `0.1`
- Дата: `2026-08-28`
- Актор: сотрудник ФКР с полномочием `assignment_order.prepare`
- Публичный командный шов: `InstallationProcess.prepareAssignmentOrder(installationObjectId, installerTabIds[], controlEngineerUserId, actorId)`
- Публичный шов наблюдения: результат команды и `InstallationProcess.getInstallationObjectProcess(installationObjectId)`

## 1. Цель

Дать сотруднику понятный и безопасный результат, если все проверки и формирование полного комплекта документов завершились успешно, но атомарное сохранение подготовленного распоряжения не состоялось из-за ошибки persistence.

Ошибка сохранения не должна оставлять частичную версию, назначения, артефакты, событие успеха, закрытую задачу или ложное состояние успеха. После подтверждённого отката пользователь может повторить обычное действие.

## 2. Предусловия и порядок

- авторизация, обязательный состав, отсутствие актуальной версии, реквизиты объекта и допустимость людей успешно проверены;
- конкурентного изменения нет;
- renderer один раз вернул полный комплект распоряжения и приложения;
- persistence начинает одну атомарную операцию сохранения версии, назначений, метаданных артефактов, события успеха, состояния дела, задачи и legacy-проекции;
- persistence сообщает инфраструктурную ошибку и гарантирует, что эта атомарная операция полностью откатилась;
- после подтверждённого отката отдельная запись безопасного события отказа доступна и завершается успешно.

```text
all approved validations
→ renderer once
→ atomic persistence
→ on confirmed rollback: append rejection audit separately
→ return safe rejection
```

Команда не повторяет renderer или атомарное сохранение автоматически.

## 3. Наблюдаемый отказ

```text
accepted = false
violations = [
  {
    code: ASSIGNMENT_ORDER_PERSISTENCE_FAILED,
    message: "Не удалось сохранить распоряжение. Повторите действие позже.",
    field: null
  }
]
```

Ответ не раскрывает имя таблицы, SQL, параметры подключения, exception message, stack trace, путь к артефакту или устройство persistence.

## 4. Состояние и аудит

Монтажное дело остаётся в исходном состоянии `needs_assignment_order`. Не создаются версия распоряжения, назначения, сохранённые артефакты или хэши, событие успеха, открытие работ, доступ к чек-листу, закрытие исходной задачи или legacy-проекция.

После отката отдельной атомарной записью добавляется ровно одно событие `assignment_order_prepare_rejected`:

```text
reasonCodes = [ASSIGNMENT_ORDER_PERSISTENCE_FAILED]
installerCount = <число нормализованных уникальных входных монтажников>
controlEngineerProvided = true
```

Аудит не содержит идентификаторы и снимки людей, данные объекта, имена, содержимое или хэши сформированных документов, внутренний текст ошибки, SQL, путь, stack trace или конфигурацию persistence. Техническая диагностика может быть записана отдельным инфраструктурным журналом, который не входит в публичную процессную проекцию этого среза.

## 5. Исполняемый пример A

Сотрудник `18` вызывает `prepareAssignmentOrder(4512, [1042], 73, 18)`. Все проверки проходят. Renderer один раз возвращает утверждённые распоряжение и приложение. Атомарное сохранение относительно прочитанной ревизии `7` завершается ошибкой `database unavailable` и гарантированно откатывает все изменения.

Команда возвращает точный отказ раздела 3. Исходная проекция монтажного дела сохраняется; в `events` отдельной успешной записью добавляется только безопасное событие раздела 4. Ни один снимок человека, метаданные или хэш сформированного артефакта не появляется в публичной проекции.

Ожидаемые состояние, ответ и audit задаются литералами из этой спецификации, а не выводятся из production-реализации или результата renderer.

## 6. Повтор действия и сквозной инвариант

Подтверждённый откат означает, что подготовка не применена. После восстановления persistence сотрудник может повторить обычное действие; оно заново выполняет проверки и renderer и может создать версию `1`.

Для команды продолжает действовать утверждённый сквозной контракт безопасного повтора и конкурентности. Этот срез не создаёт исключение из него и не требует отдельного продуктового согласования идемпотентности.

## 7. Не входит

- неизвестный результат commit, когда persistence не может подтвердить ни commit, ни rollback;
- недоступность или исчерпание повторов отдельной записи audit-события отказа;
- автоматические инфраструктурные повторы транзакции;
- удаление временных файлов внутри конкретного renderer после отката;
- production DB/legacy-адаптер, UI и HTTP;
- ошибка persistence при других процессных командах.

Неизвестный результат commit нельзя преобразовывать в этот отказ без дополнительного установления фактически сохранённого результата: это могло бы предложить повтор уже применённой команды.

## 8. Решения и доказательства

- `PRODUCT.md`: каждый факт имеет основание; процесс не может показывать ложный успех или частичный документ.
- `docs/fmonitor-2-primary-spec.md`: доменные факты и аудит успеха сохраняются одной транзакцией; при отказе нет частичного результата и возвращается стабильная предметная причина.
- `docs/fmonitor-2-pilot-data-model.md`: версия, назначения, событие и задача сохраняются одной транзакцией; legacy-проекция не является источником истины.
- `ORDER-PREPARE-002`: успешная версия существует только с полным составом и двумя артефактами.
- `ORDER-PREPARE-006`: конкурентный отказ отличается от инфраструктурной ошибки persistence.
- `ORDER-PREPARE-007`: renderer уже успешно завершился; ошибка формирования документов к этому срезу не относится.
