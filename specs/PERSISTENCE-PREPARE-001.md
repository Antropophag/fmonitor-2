# PERSISTENCE-PREPARE-001 — сохранить первую подготовленную версию в production persistence

- Статус: `APPROVED`
- Версия: `0.3`
- Дата: `2026-08-28`
- Актор: сотрудник ФКР с полномочием `assignment_order.prepare`
- Публичный командный шов: `InstallationProcess.prepareAssignmentOrder(installationObjectId, installerTabIds[], controlEngineerUserId, actorId)`
- Публичный шов наблюдения: результат команды и `InstallationProcess.getInstallationObjectProcess(installationObjectId)` через новый экземпляр модуля

## 1. Цель

Подключить первый production persistence adapter к уже утверждённому сценарию подготовки распоряжения. Успешно подготовленная версия должна быть атомарно сохранена в процессных таблицах FMonitor 2.0 и читаться после завершения исходного PHP-запроса, без обращения к in-memory состоянию.

Срез является tracer bullet для реального MariaDB persistence. Он сохраняет один уже утверждённый успешный пример `ORDER-PREPARE-002`; новые бизнес-правила не вводятся.

## 2. Предусловия

- объект монтажа `4512` существует в legacy `fm_maintable`;
- для него создано монтажное дело FMonitor 2.0 без распоряжений, состояние `needs_assignment_order`, ревизия `1`;
- сотрудник `18` имеет полномочие `assignment_order.prepare`;
- актуальный legacy-снимок объекта содержит утверждённые обязательные реквизиты;
- монтажник `1042` присутствует в актуальном кадровом каталоге и трудоустроен на требуемый период;
- пользователь `73` активен и имеет роль инженера строительного контроля;
- renderer возвращает два детерминированных артефакта утверждённого примера;
- серверное время: `2026-08-26T21:30:00+00:00`, бизнес-дата `Europe/Moscow`: `2026-08-27`, как в утверждённом примере `ORDER-PREPARE-002`;
- production persistence adapter подключён к MariaDB с процессной схемой FMonitor 2.0;
- уже утверждённые снимки объекта монтажа, монтажника, инженера, полномочий, времени и документов предоставлены отдельными внутренними делегатами окружения. Их production-интеграция с legacy/Workforce/UserDirectory/renderer не входит в этот persistence-срез.

## 3. Действие

```php
$result = $process->prepareAssignmentOrder(4512, [1042], 73, 18);
```

После возврата результата исходный экземпляр `InstallationProcess` и adapter уничтожаются. Новый экземпляр с новым DB-соединением читает:

```php
$projection = $reloadedProcess->getInstallationObjectProcess(4512);
```

## 4. Наблюдаемый результат

Команда возвращает утверждённый успешный результат `ORDER-PREPARE-002`:

```text
accepted = true
assignmentOrderVersion = 1
status = prepared
assignmentOrderDate = 2026-08-27
organizationType = individual
```

Проекция, прочитанная новым экземпляром, содержит:

- состояние `assignment_order_prepared`;
- ровно одну версию распоряжения `1` в статусе `prepared`;
- неизменяемый снимок объекта монтажа из предусловий;
- снимок монтажника `1042` и инженера `73`;
- метаданные ровно двух сформированных артефактов и их утверждённые SHA-256;
- предварительные назначения монтажника и инженера на версию `1`;
- ровно одно событие `assignment_order_prepared` с актором `18` и временем из предусловий;
- отсутствие открытых задач и отсутствие факта открытия работ.

Полный литеральный ожидаемый результат и снимки наследуются из примера A `ORDER-PREPARE-002`; тест не вычисляет их из SQL-схемы, adapter или renderer.

## 5. Сохранение и атомарность

Production persistence adapter сохраняет в документированных `fm2_*` process-таблицах новое состояние монтажного дела, версию распоряжения, снимки состава, метаданные артефактов, предварительные назначения и событие успеха. SQL adapter не создаёт и не читает параллельные копии `fm_maintable`, Workforce-каталога или `users`.

Читатель не должен наблюдать частично подготовленное распоряжение. После подтверждённого `COMMIT` все перечисленные факты доступны новому экземпляру; после подтверждённого `ROLLBACK` не доступен ни один из них.

Process-таблицы являются источником истины. Legacy `fm_maintable.installator*` в этом срезе не обновляется и не используется для восстановления состава распоряжения.

## 6. Граница первого persistence-среза

Этот tracer bullet доказывает только долговечный успешный путь: все публичные факты утверждённого примера доступны через новый экземпляр модуля и новое DB-соединение.

Optimistic concurrency, атомарность при ошибке, сохранение `preparationOperationId` и DB-reconciliation реализуются следующими отдельными persistence-срезами с собственными чувствительными тестами. Их пользовательские результаты уже заданы `ORDER-PREPARE-006` и `ORDER-PREPARE-008`–`ORDER-PREPARE-010`, но этот тест их не заявляет и не доказывает.

## 7. Публичный seam теста

Интеграционный тест создаёт реальный production persistence adapter и вызывает только публичные методы `InstallationProcess` для действия и наблюдения. Прямая запись в БД разрешена только fixture-у для создания предусловия в документированных process-таблицах; SQL-запросы к ним не используются как assertions. Внешние снимки предоставляет детерминированный составной делегат, не выдаваемый за production legacy/Workforce/UserDirectory adapter.

Стабильность проверяется новым экземпляром модуля и новым DB-соединением, поэтому тест чувствителен к отсутствию реального persistence и не может пройти на состоянии PHP-процесса. Fixture создаёт уникальный безопасный префикс таблиц для каждого запуска и удаляет только таблицы с этим точным префиксом, поэтому параллельные запуски не изменяют данные друг друга, demo или legacy.

## 8. Отказы

Новых предметных кодов отказа нет. Ошибки MariaDB, rollback и неизвестный исход `COMMIT` не входят в этот успешный tracer bullet и должны получить отдельные persistence-срезы. Текст SQL, параметры подключения и сообщения драйвера наружу в любом случае не возвращаются.

## 9. Не входит в срез

- подключение controller/HTTP/UI к модулю;
- production-реализации LegacyInstallationObject, Workforce, UserDirectory, authorization, clock и DocumentRenderer adapters;
- запись совместимой legacy-проекции `installator*`;
- хранение байтов артефактов или файловая стратегия (сохраняются утверждённые метаданные и хэши);
- подготовка бригадного распоряжения и изменяющих версий;
- регистрация номера, открытие работ и чек-лист;
- импорт противоречивых legacy-объектов;
- развёртывание миграции в legacy production database;
- проверка optimistic concurrency и точного изменения ревизии;
- сохранение и поиск результата по `preparationOperationId`;
- подтверждённый rollback и неизвестный исход `COMMIT` на реальном adapter;
- новые бизнес-решения или пользовательские сообщения.
