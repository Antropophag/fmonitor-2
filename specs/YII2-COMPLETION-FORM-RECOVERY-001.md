# YII2-COMPLETION-FORM-RECOVERY-001 v1

## Простыми словами

Если акт ПТО или декларация не сохранились, пользователь остаётся в карточке
того же объекта, видит понятную причину и исправляет уже заполненную форму.
Изменение касается только четырёх существующих форм документарного закрытия и
не меняет порядок ПТО → декларация, предметные команды или историю документов.

## Seam и границы

Публичный seam — GET `/pilot/objects/{id}` и POST
`/pilot/objects/{id}/completion` через Yii, с существующими session, CSRF,
capability, `MariaDbInstallationCompletion::record/correct` и HTTP-статусами.
Формы: `record_pto`, `record_declaration`, `correct_pto`,
`correct_declaration`. Root пишет контракт и тесты; отдельный sol/low executor
пишет production; независимые sol/low reviewers принимают требуемые planner'ом
Gate 3/5. Соседние редактор карточки, checklist/photo/offline, стройконтроль,
статусы, ОТиЗ, readiness и работа #172 не меняются.

## A1. Исправимая серверная валидация без JavaScript

Для распознанной ошибки полей при доступном приложении POST возвращает тот же
неуспешный статус `422` и HTML карточки того же объекта, а не отдельный plain-text
ответ. В HTML сохранены только поля отправленной формы: дата ПТО либо дата и
реквизиты декларации, а для correction также причина. Значения не попадают в
другую форму или объект. Конкретная ошибка связана с полем через доступные
`aria-invalid`/`aria-describedby`; общая ошибка находится внутри отправленной
формы, имеет live/alert semantics и доступную цель фокуса.

Для correction соответствующий `details` открыт сервером. Панель карточки,
содержащая `#completion`, активна и не скрыта. В документе есть однозначная цель
фокуса: первое ошибочное поле, иначе блок общей ошибки. Повторный исправленный
POST проходит обычную серверную валидацию и только реальный успех даёт `303` на
`/pilot/objects/{id}#completion` и ожидаемые новые root/correction/history facts.

## A2. Предметные конфликты и доступ

Распознанные предметные отказы `CASE_NOT_WORKING`, `CHECKLIST_INCOMPLETE`,
`PTO_REQUIRED`, `FACT_ALREADY_RECORDED`, `FACT_NOT_FOUND` показываются в блоке
отправленной формы на карточке со своим исходным `409` и объясняют следующий
шаг. Они не создают facts и не изображают успех.

`403` при утрате capability/активности и истёкшая session остаются отдельными
access/session результатами: защищённые данные не дорисовываются и сохранённый
browser input не даёт выполнить запрещённую команду. `404`, malformed transport,
CSRF и неизвестная action не превращаются в заполненную карточку.

## A3. Неподтверждённый результат и защита от двойной отправки

Адресный same-origin module перехватывает только четыре completion-формы. На
submit он блокирует повторную отправку именно этой формы до результата. При
полученном `422/409` HTML он заменяет карточку актуальным серверным фрагментом,
раскрывает correction, активирует содержащую вкладку, прокручивает раздел и
фокусирует поле/ошибку; после этого форму можно исправить и отправить снова.

При network error, invalid/non-HTML response или ином неподтверждённом результате
DOM формы и введённые значения остаются на месте, кнопка снова доступна,
автоматического POST нет. В форме показывается: «Результат сохранения не
подтверждён. Проверьте актуальные документы перед повторной отправкой.» Нельзя
утверждать, что сервер ничего не сохранил. Подтверждённый success — только
реальный redirect/navigation к актуальной карточке; JS не синтезирует успех.

## A4. Инварианты и regression

Все существующие правила дат, 85%, последовательности ПТО → декларация,
обязательной причины correction, immutable roots и append-only correction
history сохраняются. Никаких retry/idempotency framework, DDL, бизнес-статусов,
финансовых команд или DML из controller/JS. Реальные поля и действия проверяются
таблично через HTTP и одним связанным browser-сценарием. Адресные regression
проверки подтверждают неизменность редактора реквизитов и исправленных #236
статусов; exact-source CI покрывает остальной текущий application matrix.
