# ORDER-PREPARE-009 — восстановление успешного результата после неизвестного исхода commit

- Статус: `APPROVED — унаследованный сквозной инвариант`
- Версия: `0.1`
- Дата: `2026-08-28`
- Актор: сотрудник ФКР с полномочием `assignment_order.prepare`
- Публичный командный шов: `InstallationProcess.prepareAssignmentOrder(installationObjectId, installerTabIds[], controlEngineerUserId, actorId)`
- Публичный шов наблюдения: результат команды и `InstallationProcess.getInstallationObjectProcess(installationObjectId)`

## 1. Цель

Не создавать дубль и не возвращать ложный отказ, если атомарное сохранение подготовленного распоряжения фактически завершилось успешно, но persistence потерял подтверждение `COMMIT` и сообщил вызывающему модулю неизвестный исход.

Модуль устанавливает результат той же операции через внутренний persistence-seam и возвращает уже сохранённый успешный результат. Публичная сигнатура команды и обычный успешный ответ не меняются.

## 2. Предусловия и порядок

- авторизация, обязательный состав, отсутствие актуальной версии, реквизиты объекта и допустимость людей успешно проверены;
- renderer один раз вернул полный комплект распоряжения и приложения;
- до атомарного сохранения модуль один раз создаёт непрозрачный уникальный `preparationOperationId` для этого вызова;
- `preparationOperationId` передаётся внутреннему persistence-seam вместе с полным атомарным изменением, но не передаётся клиентом и не показывается в публичной процессной проекции;
- persistence фактически фиксирует версию, назначения, метаданные артефактов, событие успеха, состояние дела и задачу одной транзакцией;
- подтверждение `COMMIT` теряется, поэтому persistence сообщает типизированный неизвестный исход;
- модуль не повторяет renderer или сохранение, а один раз запрашивает результат по тому же `preparationOperationId`;
- persistence находит полностью зафиксированный результат этой операции.

```text
all approved validations
→ create one internal preparationOperationId
→ renderer once
→ atomic persistence with preparationOperationId
→ commit succeeds, acknowledgement is lost
→ reconcile once by the same preparationOperationId
→ return the stored success
```

## 3. Наблюдаемый результат

Команда возвращает тот же успешный результат, который был бы возвращён при обычном подтверждённом `COMMIT`:

```text
accepted = true
assignmentOrderVersion = 1
status = prepared
assignmentOrderDate = 2026-08-28
organizationType = individual
```

Ответ не раскрывает `preparationOperationId`, факт потери подтверждения, имя таблицы, SQL, параметры подключения, exception message или stack trace.

## 4. Состояние и аудит

Публичная проекция содержит ровно один полностью сохранённый результат операции по правилам `ORDER-PREPARE-002`:

- одну версию `1` в статусе `prepared`;
- утверждённые снимки объекта монтажа и состава;
- ровно два артефакта и их хэши;
- предварительные назначения;
- закрытую исходную задачу;
- ровно одно событие `assignment_order_prepared`.

Не создаются вторая версия, дубли назначений или артефактов, дополнительное событие успеха либо событие `assignment_order_prepare_rejected`. Технический `preparationOperationId` не входит в публичную процессную проекцию или предметный audit payload.

## 5. Исполняемый пример A

Сотрудник `18` вызывает `prepareAssignmentOrder(4512, [1042], 73, 18)`. Внутренний генератор возвращает `prep-op-9f4c`. Все проверки и renderer проходят один раз. Persistence атомарно сохраняет утверждённую версию `1` относительно ревизии `7`, переводит ревизию в `8`, связывает технический результат с `prep-op-9f4c`, затем сообщает `commit outcome unknown` из-за потерянного подтверждения.

Модуль один раз запрашивает результат `prep-op-9f4c`. Persistence возвращает сохранённый успешный результат. Команда возвращает точный ответ раздела 3, а публичная проекция равна одному независимо заданному успешному результату раздела 4. Renderer, атомарное сохранение и reconciliation вызываются ровно по одному разу.

Ожидаемый успешный результат и публичная проекция задаются литералами спецификации и `ORDER-PREPARE-002`, а не вычисляются из production-реализации или технического индекса операции.

## 6. Сквозной инвариант и seam

Срез наследует утверждённый сквозной контракт безопасного повтора и конкретизирует его для одного неизвестного исхода persistence. Это не отдельное продуктовое согласование идемпотентности и не исключение из общего правила.

`preparationOperationId`, его генерация, передача при атомарном сохранении и reconciliation являются единым внутренним persistence-интерфейсом модуля. UI, HTTP и будущая интеграция не создают этот идентификатор и не реализуют recovery самостоятельно.

## 7. Не входит

- reconciliation не нашёл операцию или сам недоступен;
- persistence вернул частичный или противоречивый результат операции;
- безопасный повтор нового HTTP-запроса после разрыва соединения и transport idempotency key;
- автоматический повтор renderer или атомарной записи;
- очистка временных файлов renderer;
- production DB/legacy-адаптер, UI и HTTP;
- другие процессные команды.

## 8. Решения и доказательства

- `docs/fmonitor-2-primary-spec.md`: повторная или одновременная отправка не создаёт дубли; система возвращает уже применимый результат либо требует перечитать состояние.
- `ORDER-PREPARE-002`: точный контракт первой успешной версии.
- `ORDER-PREPARE-006`: атомарное сохранение по ревизии создаёт только одну первую версию.
- `ORDER-PREPARE-008`: неизвестный исход `COMMIT` нельзя преобразовывать в retryable-отказ без установления фактически сохранённого результата.
- `docs/fmonitor-2-session-handoff.md`: сквозной безопасный повтор наследуется без отдельного повторного продуктового согласования.

- Дата: `2026-08-28`
- Решение: `APPROVED`
- Комментарий: срез возвращает уже утверждённый успешный результат и не вводит новый пользовательский исход или исключение; отдельно согласовывать нечего.
