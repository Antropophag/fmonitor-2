# OTIZ-SETTLEMENT-V2-001 — Расчёты, обязательства и выплаты ОТиЗ

Этот файл и delta specs change `redesign-otiz-settlements-v2` являются самодостаточным нормативным контрактом. Числовые ожидания M01–M24 задаются literal integer cents и не вычисляются тестируемым кодом.

Порядок источников: этот контракт и handoff v2; issue #257 для composition mismatch; PRODUCT/CONTEXT и pilot contracts; канонические normative inputs. HTML v3 определяет компоновку и действия, но не суммы, состояние, CSS, localStorage или demo debt.

Особые fail-closed условия: UNKNOWN norm/identity/admission остаётся UNKNOWN; draft финансово нейтрален; acceptance создаёт claim один раз; payment закрывает сохранённое обязательство и не списывает work/fund повторно; #257 запрещает acceptance/current-payment-export/payment всего объекта и требует replacement после resolution; historical read остаётся доступен.

## Public commands and state

Единственный public application owner предоставляет команды create/refresh/delete draft, save/remove deduction, save former-employee decision, accept, cancel, create replacement draft, accept replacement, mark paid и reverse payment. Каждая команда повторно проверяет `otiz.manage`, membership, operation UUID/payload fingerprint и expected revision; одинаковый replay возвращает сохранённый результат, другой payload с тем же UUID возвращает `OPERATION_CONFLICT`. Ошибка не оставляет частичных facts.

`draft` финансово нейтрален. `accepted` создаёт immutable entitlement claims и recipient obligations. Устойчивое entitlement identity определяется самим исходным правом и не меняется от выбранной отчётной даты или новой версии того же накопительного source snapshot; acceptance под блокировкой повторно сверяет сохранённый draft с активным baseline и разрешает только доказанный прирост. `cancelled` сохраняет снимок и причину; accepted с payment/dependencies не отменяется простым маршрутом. Создание, просмотр, изменение, удаление или отказ от replacement draft не меняют исходный расчёт и его claims. Только явное acceptance полноценного replacement draft в одной транзакции отменяет допустимый неоплаченный исходник и принимает replacement; неполная замена запрещена. Payment создаёт один package fact с явно введённой небудущей фактической датой; reversal с причиной деактивирует его, но не claims/accepted amounts. Нулевой obligation без payment fact не получает статус «выплачено».

Acceptance, current payment export и payment используют один owner-level допуск сохранённого snapshot. После любого incident #257 старый accepted snapshot остаётся недействующим платёжным основанием даже когда текущий producer снова сообщает `allow`; восстановить действующий export/payment может только явно принятый replacement. Draft, подготовленный до incident или смены admission source, нельзя принять по одному лишь текущему `allow`. Historical export остаётся доступным и однозначно не является платёжным реестром.

Новый денежный объём распределяется только по attribution конкретных впервые признаваемых работ, а не по накопленному вкладу за всю историю объекта. Replacement-aware builder включает полное множество прав и денег заменяемого accepted расчёта без прав соседних расчётов; полнота проверяется при preview, refresh и atomic acceptance по rights/cents, но исправленный получатель не обязан совпадать с ошибочным прежним получателем.

Обычные allocation edits сохраняют admission snapshot черновика; refresh атомарно пересобирает canonical facts и admission. Отсутствующий обязательный snapshot запрещает acceptance. Draft содержит только объекты с новыми правами и допустимым admission; preblocked/UNKNOWN объекты попадают в immutable explanatory exclusions, объекты без delta не создают нулевых денежных строк, а полностью пустой документ отклоняется.

Baseline сравнивается со значением, полученным тем же locking read frontier. Cross-actor операции обязаны сохранять эту гарантию при штатной isolation и MariaDB REPEATABLE READ. Reversal различает ошибочную отметку без перечисления и финансовое сторно: только первый audited kind разрешает последующую отмену/замену расчёта, не удаляя payment/reversal history.

Production XLSX получает сохранённые share basis points, accepted actor/time, content hash и issues/exclusions. Квып форматируется как процент, Кшах/Ксс как коэффициенты. Экономика агрегирует obligations один раз по object/calculation и отделяет object contribution от calculation remaining.

## Acceptance matrix

### Уточнение проверки PR #285 — 2026-09-27

Обычная подготовка, refresh и replacement используют один набор устойчивых прав отдельных работ/документарных этапов и их доказанную атрибуцию. Изменение расчётной даты или хеша всего прогресса не доказывает смену исполнителей. Последняя операция не определяет бригаду остальных работ. Исправление исполнителей пункта меняет только этот пункт; снятие/повторное выполнение не создаёт повторного права. Сохранённые права соседнего утверждения остаются занятыми и неизменными. Прежние агрегированные основания без доказуемого разложения не превращаются в новые доступные права: совместимость должна быть доказана либо операция безопасно отклоняется, без backfill.

Контроль: фонд 10000000 коп., Ксс=10000; A/B выполнили по 10%, утверждены 1000000/1000000 без выплаты. Новый расчёт без работ не начисляет повторно; замена с другой датой сохраняет получателей. Новые 20% B дают только B=2000000. Замена может включить этот новый объём (A=1000000/B=3000000) либо оставить его следующему расчёту (A/B по 1000000), но не теряет старые права. После отдельного утверждения новых 20% замена исходника содержит только исходные 20%. Исправление отдельного пункта весом 2% с A на B даёт A=800000/B=1200000; соседний расчёт B=2000000 не меняется. Проверка через реальные источники использует действующий нормативный фонд fixture 65000000 коп. и те же доли (коэффициент масштаба 6,5), не добавляя несуществующую нормативную ставку 10000000.

Для двух объектов одного утверждения на 1500000 и 2500000 коп. строки экономики и objectContribution показывают соответственно 1500000 и 2500000; calculationRemaining отдельно равен 4000000. Refresh и acceptance замены повторно проверяют полноту после финансового допуска; исключение исходного объекта блокирует замену и сохраняет исходник целиком.

Серверный preview решения/удержания показывает до/после по затронутым объектам и получателям без изменения revision, receipts, решений и денег. Сохранение — отдельная команда с тем же контролем revision. Удержания имеют адресуемую identity: удаление в draft затрагивает ровно выбранный факт, даже если реквизиты документа пусты/совпадают. Решение уволенного отображается один раз по stable identity, сохраняет выбранное значение/причину после reload; доступно из обеих группировок. Подтверждение выплаты показывает полный неизменный scope, дату/номер и сумму расчёта и поясняет регистрацию выплаты вне FMonitor. Кнопка платёжного XLSX использует admission-проверяемый payment mode, отдельная история остаётся доступна. Документарные 10%/5% наследуют доказанные положительные веса вклада канонического `OTIZ-EXCEL-INPUTS-001` §§7–8; равные доли текущего состава не являются основанием. Для накопленных вкладов A=1500/B=2500, документарного G=9750000 и текущего канонического Ксс=10000 выплаты равны A=3656250/B=6093750. Прежний Ксс=5000 другого утверждения не уменьшает текущий коэффициент. Веса/источник фиксируются с самим документарным правом; отсутствие доказанного вклада блокирует его распределение. При совместном признании checklist/documentary права сохраняют свои собственные основания и относительную стоимость, не заимствуют единственный набор весов другого вида работ.

Обычная команда отмены отметки предназначена только для `erroneous_mark` с явным подтверждением отсутствия реального перечисления. Неподдержанное `financial` сторно отвергается `FINANCIAL_REVERSAL_UNSUPPORTED` без новых фактов; UI не предлагает выдуманный возврат денег. История общего реестра включает отменённые/заменённые, выплаченные и утверждённые с нулевым обязательством; после отмены ошибочной отметки действующий положительный остаток снова в ожидании. Год по умолчанию не скрывает старые обязательства; автор и причина финансовой остановки видимы рядом с остатком.

Ксс документарного права вычисляется `PremiumCalculationV2` по текущим доказанным сроку/справке/ПТО, без минимума по прошлым утверждениям. Явная замена пересчитывает по исправленным нормативным основаниям; она не копирует ошибочный старый коэффициент поверх текущего. При исправлении планового срока на дату ПТО canonical Ксс=1; для документарного G9750000 и вкладов1500/2500 получатели3656250/6093750. Старый snapshot с Ксс0,5 не переписывается. Отсутствие новых работ в HTTP create получает предметное объяснение «Новых работ для расчёта нет» и путь к старым неоплаченным обязательствам.

Перед acceptance сохранённого canonical input повторно проверяются версии именно выбранных прав, их атрибуция, нормативные основания и значимый кадровый snapshot. Изменение выбранного права до утверждения даёт `STALE_CALCULATION`, оставляет draft/claims/обязательства неизменными и требует явного refresh. После утверждения изменение относящихся к нему работ/денежных оснований запрещает текущую платёжную выгрузку и выплату с `SNAPSHOT_REPLACEMENT_REQUIRED`; historical read/export остаются доступны. Независимые новые работы, не входившие в утверждение, сами по себе прежнюю выплату не останавливают. Увольнение после утверждения также не снимает прежнее обязательство. Конфликт занятых прав сохраняет более конкретный `STALE_ENTITLEMENT_BASELINE`.

Удаление draft, отмена и подготовка замены имеют отдельные подтверждения с номером/scope расчёта и видимой обязательной причиной, не фиксированным hidden reason. Закрытие подтверждения не меняет фактов. Серверные команды сохраняют штатные проверки состояния/revision/прав.

Изменение фонда из подтверждённой технической характеристики не создаёт нового права по уже признанному пункту. Явная canonical replacement применяет текущий норматив ровно к принадлежащим исходнику работам; новая доказанная стоимость может быть выше или ниже старой, но поддельное уменьшение/пропуск части прав остаётся запрещено. Пример native norms: пассажирский630кг, Кшах1, Ксс1; права замены A8%/B13%. Исправление этажности9→15 даёт фонд84500000 коп. и A6760000/B10985000; исправление15→2 даёт фонд52000000 и A4160000/B6760000. Соседний утверждённый расчёт не пересчитывается, обычный новый расчёт не начисляет разницу нормы как новые работы.

### Полнота коррекции по финальному review

- Для checklist сохраняются именно канонические вклады каждого пункта из `OTIZ-EXCEL-INPUTS-001` §6, включая распределение остатка basis points в binary tab order. Реальный пункт200bp и три исполнителя7001/7002/800 дают67/67/66; при G1300000, Ксс1 обязательства435500/435500/429000 коп. Money-equal деление не заменяет эти веса. Сохранённые обязательства и HTTP XLSX совпадают.
- Preview и save удержания отвергают нулевую сумму `INVALID_MONEY` без новых фактов; отрицательная сумма также недопустима. `markPaid` принимает только точную существующую календарную дату `Y-m-d`; пустая строка, невозможный день и иные форматы дают `INVALID_PAYMENT_DATE` без записи, будущая дата остаётся `FUTURE_PAYMENT_DATE`.
- В исходном серверном HTML формы delete/cancel/replace уже находятся в закрытых подтверждениях с видимой обязательной причиной. JS может открыть/закрыть их, но не устраняет задним числом изначально активную разрушительную форму или выдуманную hidden-причину. Реестр показывает локализованные состояния и отдельно подписывает предварительные деньги draft.
- «Контроль» XLSX содержит сохранённые issues включённых объектов с их identity наряду с исключениями. Бизнес-даты XLSX являются числовыми Excel dates с правильным форматированием, а не строками с date style; default style определён, autoFilter охватывает строки данных. Исторические источники, суммы и identities не пересчитываются.

Один и тот же saved issue одного объекта выводится в «Контроль» ровно один раз, даже если передан и внутри объекта, и в общей коллекции. Одинаковый код другого объекта не теряется. Первая видимая строка основного листа содержит mode banner: «Черновик. Не основание выплаты», «Историческая выгрузка» либо «Реестр к выплате»; banner и заголовки колонок повторяются при печати/закреплены, filter начинается со строки заголовков, не с banner. Платёжный режим разрешён только для действующего положительного неоплаченного обязательства; paid/zero дают `PAYMENT_EXPORT_STATE_INVALID`, сохраняя historical read/export. Нулевое утверждение явно показывает «Суммы к выплате нет» и не предлагает невозможную отметку выплаты.

Конкурентная отмена или acceptance замены обязаны учитывать выплату другого пользователя, закоммиченную до получения объектной блокировки, даже если транзакция уже открыла REPEATABLE READ snapshot. Обе команды дают `PAID_CALCULATION`, сохраняют исходное утверждение, его права и выплату; замена остаётся draft, receipt отклонённой команды не создаётся. Это уточнение существующего M12, а не разрешение нового вида сторно.
