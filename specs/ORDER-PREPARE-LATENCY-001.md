# ORDER-PREPARE-LATENCY-001 — отзывчивая подготовка распоряжения

## Простыми словами

Окно подготовки распоряжения и поиск монтажников должны быстро отвечать на
действия пользователя. Исправляется подтверждённая задержка TCP-переходника
между приложением и MariaDB; правила состава, полномочия и история сохраняются.
Основание: замечания владельца #50/#51 и поручение выполнить #50 от 2026-09-08.

## Наблюдаемый контракт

- Авторизованный сотрудник ФКР открывает карточку без распоряжения, нажимает
  «Загрузить распоряжение», затем «Выбрать монтажников» и вводит минимум два символа.
- Форма и первая страница результатов доступны без задержек накопления небольших
  TCP-сообщений на настроенном Docker-переходнике БД. Сохранение состава остаётся
  отдельной командой; просмотр и поиск не создают предметных фактов.
- Существующие авторизация, кадровые ограничения, порядок результатов, максимум
  20 работников на странице, provenance и выбор инженера остаются прежними.
- Ошибки подключения не превращаются в успешный ответ. TCP-адреса, bind, порт,
  credentials и доступность БД извне сохраняют действующий контракт.

## Проверка

Публичный маршрут: карточка → GET prepare/selection → modal → GET installers.
`tools/diagnostics/measure-order-prepare.cjs` выполняет три прохода headless Chromium,
проверяет возможность выбрать найденного работника, запрещает POST и внешние
запросы, выводит только длительности и количества. Auth state хранится вне repo.
Первый и повторные проходы сообщаются отдельно. Бюджет медианы 1000 мс отдельно
для открытия формы и поиска — диагностический порог на локальном стенде, не SLA
для произвольной сети. Нестабильные wall-clock assertions не добавляются в общий CI.

Причина проверяется также на одинаковом синтетическом наборе с 23 работниками
без известной даты приёма, подтверждёнными полным кадровым снимком: прямое
соединение / штатный переходник / переходник с отключённым накоплением пакетов.
Контрольное изменение касается только TCP-параметров; SQL и данные одинаковые.
Это проверка реального production selection API, а не подмена его результатом.
Парный focused gate выполняет шесть проходов через каждое соединение, отбрасывает
первый cold-проход и вычисляет медиану `searchMs` по оставшимся пяти строкам
итераций. Переходник проходит gate, если его медиана превышает медиану прямого
соединения не более чем на 200 мс. Итоговая строка самого диагностического probe
в этот расчёт не входит: она сохраняет все проходы и порог 1000 мс для ручной
проверки отдельного стенда.

Соседние проверки: selection HTTP admission/flow/failures, installer search HTTP,
unknown-employment command и целостность bootstrap. Перед установкой — точный
образ, резервная копия БД/state, затем повтор исходного browser probe и проверка
сохранности данных/сессии после обновления и перезапуска. Повтор владельцем остаётся
отдельным критерием issue и не объявляется выполненным агентом.
