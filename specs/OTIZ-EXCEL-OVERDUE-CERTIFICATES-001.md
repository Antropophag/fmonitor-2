# OTIZ-EXCEL-OVERDUE-CERTIFICATES-001

Версия 0.2, 2026-09-09. Gate1 candidate.

## Простыми словами

Сотрудник или Руководитель ФКР прикладывает обязательную PDF-справку, её дату и новый срок к объекту. Следующий расчёт ОТиЗ использует применимую справку, effective native ПТО и подтверждённую Excel-последовательность; вся история остаётся воспроизводимой.

## Публичные seams

- `FMonitor2\DeadlineTransferCertificate\DeadlineTransferCertificates::submit(SubmitDeadlineTransferCertificate $command): array`. Command public fields: `string requestId` (lowercase UUID), `string mode` (`initial|correction`), `int installationCaseId>0`, `int actorId>0`, `int expectedVersion` (`0` initial, `>=1` correction), `string certificateDate`, `string newDeadline`, `?string correctionReason`, `DeadlineTransferCertificateUpload upload`. Upload содержит `DeadlineTransferCertificateByteStream`, original filename и exact media type `application/pdf`.
- Успешный submit возвращает exact keys `status` (`accepted|replayed`), `reasonCode=null`, `retryable=false`, `requestId`, `rootId`, `revisionId`, `revisionNumber`, `certificateDate`, `newDeadline`, `pdfSha256`, `byteSize`, `recordedAt`. Отказы возвращают те же keys, nullable document fields и `status` (`rejected|conflict|failed|unknown`), `reasonCode` из `authorization_denied|invalid_command|invalid_pdf|case_not_found|request_id_conflict|stale_revision|storage_unavailable|outcome_unknown`, `retryable=true` только для `storage_unavailable|outcome_unknown`.
- `DeadlineTransferCertificates::read(int $actorId,int $installationCaseId): array` возвращает current nullable revision и ordered history с теми же metadata без bytes/private path. `download(int $actorId,int $revisionId): DeadlineTransferCertificateDownload` возвращает media type, safe filename, byteSize/sha256 и readable byte stream.
- `FMonitor2\Otiz\PremiumCalculationV2::calculate(array $operands,array $paymentEvidence,array $exclusions=[]): array` и `allocate(int $poolCents,array $participants): array` — pure versioned seam с прежней source-envelope grammar; result содержит `version`, normalized operands/evidence, `daysLate`, `kssBp`, amounts (`fundCents,progressAmountCents,paidBeforeCents,remainingBeforePenaltyCents,deadlinePenaltyCents,poolCents`), formulaTrace/exclusions и ordered allocations.
- `FMonitor2\Otiz\SnapshotPublication::buildAndPublish(int $actorId,string $reportDate,string $operationId): int` сохраняет v2 result, создаёт fresh candidate-entitlement identities и supersession events. `accept(int $actorId,int $snapshotId): void` отдельно активирует candidates. `FMonitor2\Otiz\PaymentCompletion::complete(int $actorId,int $snapshotId,string $operationId): array` — единственный seam полной выплаты; exact result keys `status` (`completed|replayed|rejected|conflict|unknown`), `reasonCode`, `retryable`, `operationId`, `snapshotId`, `entitlements` (ordered objectId/entitlementIdentity/closureId/paidCents), `objectCount`, `paidCents`. Domain refusals: `FORBIDDEN`, `INVALID_INPUT`, `NOT_FOUND`, `BLOCKERS`, `STALE_CALCULATION`, `OBSOLETE_ENTITLEMENT`, `OPERATION_CONFLICT`, `ALREADY_PAID`, `OUTCOME_UNKNOWN`; retryable true только для unknown.

## Нормативные правила

1. Initial и correction принимают только активных пользователей с exact `deadline_certificate.write`; default grants получают только `fkr_operator` и `manager`. Read/history/download требуют exact `deadline_certificate.read`; default grants получают `fkr_operator`, `manager`, `otiz_specialist`. `construction_control_engineer`, `system_admin` и прочие роли не получают эти capabilities неявно. PDF обязателен, passive, 1..20 MiB; даты — реальные `YYYY-MM-DD`. Correction требует причину, новый PDF и актуальную expected version. Replay той же команды возвращает прежнюю revision; collision и stale не пишут фактов.
2. История append-only. Файл публикуется совместно с DB revision через staged/private storage protocol; ошибка до definite commit не активирует срок, ambiguous commit возвращает `OUTCOME_UNKNOWN` и разрешает безопасный replay.
3. При публикации выбирается текущая известная accepted non-void revision справки независимо от её документной даты. Без справки требуется доказуемый original deadline operand. Evidence сопоставляет raw `plan_finish_date` с Excel `T`, а `workdateendadjusted` с корректировкой `V`, которая не должна молча подменять T. `NEEDS_GRILL`: owner выбирает current-card capture на каждый snapshot, ранний immutable selection/application capture или отдельное подтверждение ФКР; до решения этот operand и его public seam не утверждены, а отсутствие доказанного значения блокирует расчёт. Excel применяет заполненное `DPn` без gate по дате справки `DOn`. Void-команда отсутствует в этом slice.
4. Comparison date — effective corrected `pto_act` date при наличии, включая дату после report date; иначе report date. Future-date исключение принадлежит только certificate/PTO document operands новой version: progress, payments и остальные факты сохраняют прежние report-date cutoffs. Version-1 replay возвращает сохранённый snapshot без повторного расчёта. Отсутствующий/повреждённый deadline или provenance блокирует объект.
5. `daysLate=max(0,comparison-deadline)` в календарных днях; Kss для 0/1/99/100/101 дней равен 10000/9900/100/0/0 bp.
6. `fund=HALF_UP(premium*shaft/10000)`; `progressAmount=HALF_UP(fund*progress/10000)`; `remaining=max(0,progressAmount-paidBefore)`; `penalty=HALF_UP(remaining*(10000-kss)/10000)`; `pool=max(0,remaining-penalty)`. HALF-UP применяется к неотрицательному значению на каждой указанной денежной границе согласно owner decision33. Для 49725000, 9360000 и 9 дней результат: remaining40365000, penalty3632850, pool36732150; 35889750 недопустим.
7. Allocation отдельно распределяет уже выбранный целочисленный pool: целые части, затем все оставшиеся копейки в порядке дробного остатка; tie-break — canonical installer tab identity по возрастанию. `SUM(allocation)=pool` всегда; этот pass не является правилом округления самого pool.
8. Новый snapshot хранит exact source locators/hashes/versions. Успешная publication под блокировкой installation-case rows создаёт fresh candidate-entitlement identity и сразу append-only supersede-ит прежний accepted-unpaid entitlement того же объекта независимо от периода/formula version. Candidate требует отдельной acceptance; до неё ни старый, ни новый не оплачивается. Суммы старых snapshots, allocations и closures не меняются. Paid entitlement не supersede-ится. Draft старой formula version нельзя принять.
9. Payment application блокирует те же installation-case rows в object-id order, повторно проверяет, что `(snapshot,entitlement)` остаётся последним несуперседированным accepted основанием каждого объекта, и суммирует net closures по object across all snapshots. Только после этих проверок он атомарно добавляет недостающие closure/event rows. Snapshot-local lock/count недостаточен и запрещён как единственная защита. Два snapshots одного объекта не могут оба выплатить один entitlement; replay operation identity не создаёт вторых closures.
10. `paidBefore` содержит только object-wide net `paid_cents`. Discipline holds сохраняются отдельно и уменьшают payable после formula pool. Nonzero legacy `deadline_cents` блокирует v2 до явного reversal, исключая double penalty и silent refund.
11. `NEEDS_GRILL`: literal cumulative Excel для fund100/progress100%/Kss0.9/paid90 даёт новый pool9 без нового progress, тогда как approved interval rule может требовать no-new-amount. Recurring-snapshot money semantics не утверждены до ответа владельца.
12. `$EU$2` не имеет реализации в этом slice. `NEEDS_GRILL`: если владелец разрешит waiver, он планируется отдельно как role/reason/validity/audit command; отсутствие ответа не блокирует справки и новую формулу без waiver.

## Исполняемые примеры

- Plan `2026-08-08`, report `2026-08-17`, no PTO/certificate → 9 days, 9100 bp.
- Plan `2026-07-18`, PTO `2026-07-20` → 2 days, 9800 bp.
- Plan `2026-07-29`, certificate deadline `2026-08-16`, PTO `2026-07-28` → 0 days, 10000 bp.
- Plan `2026-08-10`, report `2026-08-15`, PTO `2026-08-20` → 10 days, not 5.
- Initial/replay/collision and correction/stale race preserve one linear revision chain and byte-identical PDFs.
- Missing original deadline, unsafe/missing PDF, future-dated current certificate and corrected PTO provenance each have focused MariaDB + public seam tests.
- Allocation tests cover one unique largest remainder and an equal-remainder input presented in two orders.
- Новый v2 snapshot публикуется при accepted-unpaid v2 того же объекта: publication сразу supersedes первый, новый остаётся candidate до отдельной acceptance; payment первого получает `OBSOLETE_ENTITLEMENT`, после acceptance payment второго создаёт одну object-wide net closure; concurrent attempts сериализуются и replay не дублирует её.
